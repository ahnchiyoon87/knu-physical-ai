2026-09-15. 최신 사용자 지시를 반영한 설계 판단이다. 구현·새 UI 캡처·학생 배포 완료 보고가 아니다. 이전 비교안의 ‘우리 앱을 중심으로 참고 기능을 도입’하는 해석을 이 문서로 교체한다. 날짜·시수·반 구성은 고정이며, 두 반의 핵심 내용은 같다. 대본은 온라인 이론에만 둔다.

## 최신 확정 방향: 친절한 공통 사례에서 자기 확장으로

### 운영 방향 추가: 개인 PC 실행으로 중앙 자원 최소화

사용자는 중앙 서버 비용을 최소화하도록 요청했다. 권장 기본 구성은 **학생 PC마다 실습 플랫폼·분석/시뮬레이터·PostgreSQL·Neo4j를 실행하고, 중앙에는 모델 호출 중계·학생별 사용량 관리만 두는 것**이다. 설치·설정·실행 명령은 코딩 에이전트가 수행하며 학생이 서버 관리 명령을 암기하게 하지 않는다. 강사도 같은 로컬 환경으로 시연한다. 공통 실습 서버 상시 운영은 기본안에서 제외한다.

근거: 원천 `system/docker-compose.yml`에 PostgreSQL·Neo4j와 `app` 프로필의 hydops-api·lab-platform 네 서비스가 이미 정의돼 있다. 따라서 개인 PC 실행을 위해 별도 플랫폼을 처음부터 만들 필요는 없다. 다만 원천 교재는 강사 공유 서버를 전제하는 부분이 있으므로 학생별 실행·초기화·복구 지시로 바꿔야 한다.

로컬 구성과 운영상 확인할 사항:

- 학생 PC: 코딩 에이전트, 실습 UI/API, 시뮬레이터, DB. 별도 LLM 가중치를 내려받아 로컬 추론하는 구성은 아니다.
- 중앙: 모델 중계 서비스와 그 운영에 필요한 키·사용량 저장 등 부속 자원. ‘논리적 중계 서비스 하나’이지 물리 서버 한 대·비용 한 항목으로 확정한 것은 아니다. 모델 API 사용료도 별도다.
- 모델 호출: 코딩 에이전트와 실습 앱의 LLM/임베딩 요청을 각각 중계에 연결한다. 원천의 OpenAI 직접 호출 설정을 그대로 두고 중계가 적용됐다고 표시하지 않는다. 모델·임베딩 호환성을 실제 확인한다.
- 로컬화 작업: 최초 DB/그래프/SOP 초기화, 데이터소스 등록, 내부 컨테이너 주소와 브라우저 localhost 주소 구분, 플랫폼 모드, 볼륨 보존·당일 출발본 복구를 묶는다. 현재 Dockerfile은 reduced 데이터만 복사하므로 원본 CSV 실습 입력도 따로 제공/마운트해야 한다.
- 부하 확인: 학생 PC의 메모리·디스크·Docker 실행 가능 여부와 네 서비스 구동 시 실제 사용량을 먼저 확인한다. 검증 전 최소 RAM이나 60명 운영 비용을 확정하지 않는다. 필요 회차에만 서비스를 실행하고 종료할 수 있게 안내한다.
- 사양 부족 대응은 확인 후 정한다. 일부 학생용 대체 실행 공간이 필요할 수 있으나 처음부터 60명 전체의 클라우드 실습 환경을 상시 운영하지 않는다.

현재는 운영 설계 반영이다. Compose 수정·개인 PC 구동 검증·중계 배포는 미실행이며 설치 PDF는 아직 수정하지 않는다. 사용자 비용 측정 역할은 유지한다.

후속 대화에서 사용자는 대표님 플랫폼뿐 아니라 **냉각 이상 대응 시나리오도 공통 실습의 중심으로 채택**하는 방향을 수락했다. 대표님 결과물을 그대로 복제하지 않고, 비전공자용 설명·SDD·AI 코딩·단계별 합류·후반 PBL을 녹인다. 아래 4절과 6절의 ‘초반부터 우리 원천으로 전환’ 제안은 이 결정으로 대체한다. 우리 실제 제조 데이터는 후반 전이·확장에 활용하며, 처음부터 두 시나리오를 병행하지 않는다.

학생에게 플랫폼 전체를 맨땅에서 구현하게 하지 않는다. 플랫폼은 제공하고 다음처럼 도움을 점차 줄인다.

| 단계 | 학생에게 제공하는 도움 | 학생이 판단할 부분 |
|---|---|---|
| 처음 | 실행 가능한 플랫폼, 짧은 요구사항 예시, AI 요청 예시, 예상 결과 읽는 법 | 입력과 출력이 무엇인지, 원본과 결과가 맞는지 |
| 익숙해질 때 | 요구사항의 일부와 비교 기준 예시 | 조건 하나를 바꾸고 변화가 의도와 맞는지 |
| 후반 | 플랫폼의 연결 방법과 이전 단계 출발본 | 자기 기능의 입력·동작·확인 기준을 정하고 AI로 구현 |

SDD는 긴 설계 문서 작성 과제가 아니다. ‘무엇을 만들까 / 어떤 입력을 쓸까 / 어떻게 동작해야 할까 / 무엇으로 확인할까’를 짧게 정하고 AI 구현과 비교하는 방식이다. 문법 암기나 손코딩 분량으로 난이도를 올리지 않는다. 이미 제공된 테스트의 초록 표시만 보는 것도 충분하지 않으므로, 실제 표·그래프·근거에서 확인할 지점을 가이드에 붙인다.

첫 실습은 ‘플랫폼 화면에서 온도·압력·유량을 읽기 → 서로 측정 횟수가 다른 이유 이해 → 제공 명세로 1초 요약 함수를 AI와 수정 → 원본 일부와 평균·최솟값·최댓값·개수 비교’로 구성한다. DB·그래프·프로세스를 첫날 모두 설명하거나 새로 구현시키지 않는다. 매 실습은 현재 할 일 옆에 이유·입력·예상 관찰·오류 복구를 두어 위로 돌아가 읽지 않아도 진행되게 한다.

이번 결정은 제작 기준이며 첫날 실습·새 코드·전체 자료가 완성됐다는 의미는 아니다. 사용자가 표현한 ‘참고’가 폴더명인지 자료 참고의 의미인지 확인 중이므로 신규 작업 폴더를 임의로 확정하지 않았다.

## 3. Data Fabric에서 어디까지 가르칠 것인가

공통 범위는 **원천 연결 → 구조 확인 → 뜻과 품질 확인 → 읽기 질의 → 온톨로지 매핑 → 원천으로 돌아가 검증**이다. 현재 구현의 커넥터는 PostgreSQL이다. CSV는 어댑터가 원본을 보존하며 PostgreSQL에 적재한 뒤 연결한다. 여러 DB 엔진·실시간 CDC·전사 권한 관리까지 새로 만드는 것은 이번 핵심 범위에 넣지 않는다.

‘이 열은 무슨 뜻인가’를 LLM의 확정 답으로 처리하지 않는다. 데이터 사전, 제공 문서, 샘플, 단위, 범위와 분포를 함께 보여 주고 **후보 뜻·근거·미확인 사항**을 제안하도록 한다. 사람이 확인한 이름·단위·키·시간 의미만 매핑한다. 근거가 없으면 미확인으로 남기며, 확률 점수만으로 뜻을 확정하지 않는다. 숫자가 비슷하다는 이유로 설비·LOT를 연결하지 않는다.

이 의미 확인 기능은 현재 대표님 저장소의 완성 기능이 아니라 **추가 개발 범위**다. 1차 구현은 열 사전과 근거를 저장·편집하는 작은 화면 및 매핑 JSON으로 한정한다. 범용 자동 온톨로지 설계기로 확대하지 않는다.

Ontology Studio에는 수치 전체를 그래프로 옮기지 않는다. 원천 관측/검사 행은 PostgreSQL에 두고 virtual binding으로 읽으며, 설비·공정·LOT·문서 사이의 실제로 입증된 관계를 그래프에 둔다. 한 번 발행했다고 데이터나 관계가 옳아지는 것은 아니므로 다음 질문으로 확인한다.

- 이 판정은 어느 원본 행·LOT·설비에서 나왔는가?
- 해당 대상과 사건에 적용되는 절차의 근거는 무엇인가?
- 누가 무엇을 승인했고, 실제로 어떤 결과가 남았는가?

## 4. 우리 시나리오와 실제 데이터

주 시나리오는 ‘제조 현장의 이상 징후 또는 품질 문제를 근거와 연결해 처리하는 운영 앱’으로 유지한다. 플랫폼의 냉각 전용 이름과 기준값을 우리 데이터에 억지로 씌우지 않는다.

| 데이터가 허용하는 판단 | 실습의 연결 | 허용하지 않는 설명 |
|---|---|---|
| 실제 생산/검사 기록의 변화·이상 후보 | 원본 행/LOT → 조건/공정 관계 → 관련 점검 절차 → 사람 판단 → 점검 또는 재검사 업무 | 행 순서를 실제 초 단위 시간으로 바꾸기, 라벨 없는 고장 원인 확정 |
| 실제 후속 검사·조치 기록까지 연결되는 경우 | 조치 전후 기록을 같은 대상·조건으로 비교하고 한계를 설명 | 전후 차이만으로 인과관계 확정 |
| 조치에 반응하는 새 데이터가 없는 경우 | 점검 요청·처리 기록까지 실행, 설비 회복은 ‘확인 자료 없음’ | 같은 과거 CSV를 재조회한 것을 조치 후 회복으로 표시 |
| 제공된 교육용 냉각 시뮬레이터 | 승인 → 명령 → 새 관측 → 회복/미개선/보류를 직접 경험 | 합성 반응을 현장 실증이나 실제 설비 제어로 표시 |

권장 진행은 첫날 HydOps 완성 사례를 짧게 관찰하고, 같은 플랫폼에서 우리 데이터의 원천·관계를 구성하는 것이다. 냉각 시뮬레이터는 후반의 조치·재측정 원리를 검증하는 공통 실험으로 사용한다. 두 개의 독립 앱을 처음부터 끝까지 만들게 하지 않는다.

사용자는 우리 자료가 실제 현장 데이터임을 명시했다. 그 의도는 유지한다. 다만 현재 인계에는 원본 경로 확인 미결이 있고, 이번에 확인한 앱의 관계 CSV만으로 실제 원본의 열·시간·정답·조치 이력을 확정할 수 없다. 원자료 위치와 스키마를 실제로 대조한 다음 구체적 사건명·분석 방법·후속 행동을 확정한다. 이 확인 전에는 합성 자료를 실제 원본으로 승격하지 않는다.

## 6. 수업 흐름

아래는 공통 9단계의 개편 설계이며 아직 상세 시간표/덱에 적용하지 않았다. 실전 9일·통합 10일의 날짜/각 4시간을 유지한다. 통합의 추가 하루는 같은 핵심 결과를 개선·복구·전이하는 데 사용한다.

1. 완성 플랫폼의 사건을 관찰하고 자기 문제를 정한다. 제공 UI에서 데이터가 흘러가는 첫 경로를 연결한다.
2. 우리 원천을 읽고 품질·열 의미를 확인한다. Data Fabric에서 원본과 질의 결과를 대조한다.
3. 의미 사전과 클래스·관계·바인딩을 만들고 Ontology Studio에서 발행·질문 검증을 한다.
4. 데이터에 맞는 이상/품질 판정을 만들고 사건을 원본·대상에 연결한다. 규칙과 비교 방법 하나를 판단한다.
5. 해당 사건의 현행 SOP를 검색하고 근거·적용 대상·알 수 없는 부분을 표시한다.
6. 분석·검색을 MCP 도구로 연결하고 Skill을 고쳐 업무 에이전트를 구성한다.
7. Watch와 Process로 사건 접수·사람 승인·점검/조치 업무를 연결하고 거부·실패를 관찰한다.
8. 시뮬레이터의 새 관측으로 회복·미개선·자료 부족을 구분한다. 실제 데이터 업무의 종료 조건과 비교한다.
9. 자기 운영 앱을 수정·게시하고 새로운 원천/업무 하나에 적용한다. 기존 플랫폼에서 재사용한 부분과 바꾼 판단을 확인한다.

제공할 것은 플랫폼 공통 골격·구동 기준 예제·당일 이전 단계 출발본이다. 학생 과제는 코드 몇 줄의 정답 복사가 아니라 원천과 업무를 바꾸어 작동하는 확장이다. 매번 플랫폼 전체를 다시 제작하지 않는다. 수업별 240분 상세 설계에는 설명·실습·문제 해결·질문·휴식을 포함하며 자동 실행시간으로 시수를 채우지 않는다.

## 7. 구현 순서와 영향

1. **베이스 확정 및 원천 확인:** 원천 커밋 기록, 실제 제조 데이터 스키마 대조, 원본 보존, 적용할 사건/업무 정의. 기존 생성기 일괄 실행 금지.
2. **대표 경로 구현:** 우리 데이터 한 원천 → Fabric → Studio 매핑 → 질문 결과 → 운영 화면까지 한 경로를 먼저 구현. 이때 콘솔 하드코딩과 UI 가독성을 함께 수정한다.
3. **업무 확장:** 한 사건 → SOP → 도구 → 사람 판단 → 처리 결과를 연결. 시뮬레이터의 조치·재측정은 별도 원천 표시로 연결한다.
4. **화면 검증:** 연결된 브라우저에서 변경 전후 같은 데이터·크기·상태로 캡처. 정상/빈 결과/오류, 발행 전후, 승인/거부, 회복/미개선 화면을 확인한다. 현재 미실행이다.
5. **강의로 확장:** 검증한 경로에 맞춰 챕터·이론 덱·온라인 대본·가이드·일차별 코드/ZIP을 함께 재편한다. 대표 경로가 정해지기 전 19일 자료를 재생성하지 않는다.
6. **운영 환경·비용:** 학생 개인 카드 전제를 제거할 운영안은 유지하되 설치 문서 개정은 운영 방식 확정 후 진행한다. 사용자가 측정한다. 이전 앱의 출발본/호출량은 새 베이스의 비용 실측으로 사용하지 않는다. 준비 중인 측정 도구도 새 실행 경로·일차 기준으로 바꾼 뒤 사용한다.

현재 완료: 원천 동일성 확인, 구현 범위 대조, 제공 UI 캡처 5종 육안 확인, 채택·추가·제외 범위와 수업 방향 설계.

현재 미완료: 플랫폼 이식, 새 데이터 어댑터, UI 수정·신규 캡처, 개편 자료·배포 ZIP, 새 베이스 측정 환경의 최종 검증, 실제 비용 측정. 마지막 항목은 사용자가 수행한다.
