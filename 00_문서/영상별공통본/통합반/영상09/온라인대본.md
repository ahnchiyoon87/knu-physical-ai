## U07-S059 · 평가한 서비스를 다른 실행 환경에서도 확인합니다

### 발화

앞에서는 답과 근거, 모델별 결과를 같은 조건으로 평가했습니다. 다음에는 그 서비스를 다른 환경에서 사용할 수 있게 옮깁니다. 코드를 복사하는 것만으로 필요한 문서와 저장 상태가 함께 옮겨지는 것은 아닙니다.

프로그램이 실행되는 곳과 기록이 남는 곳, 자격 정보가 전달되는 경로를 구별하겠습니다. 새 주소가 열리는지와 대표 업무가 실제로 되는지를 나누어 확인하면 배포 과정에서 빠진 연결을 찾을 수 있습니다.

### 다음 장으로

주소 응답과 실제 업무 동작은 별도로 확인합니다. 다음에는 내 노트북의 주소와 서비스 주소는 다릅니다로 이어갑니다.

## U07-S060 · 내 노트북의 주소와 서비스 주소는 다릅니다

### 발화

localhost는 접속하는 컴퓨터 자신을 가리키는 주소입니다. 내 노트북에서 보이는 주소를 다른 사람에게 주면 그 사람의 컴퓨터를 가리키게 됩니다. 배포는 코드를 다른 실행 환경에 올리는 일과 필요한 저장소에 연결하는 일을 함께 포함합니다. 주소마다 누가 어디에서 접속하는지 표시하겠습니다.

localhost는 접속하는 컴퓨터 자신을 가리킵니다

## U07-S061 · localhost는 접속하는 컴퓨터 자신을 가리킵니다

### 발화

노트북의 DB 주소를 클라우드 설정에 그대로 쓰면 클라우드 인스턴스 자신의 DB를 찾을 수 있습니다. 로컬에 있던 저장소가 자동으로 따라오는 것이 아닙니다. 서비스, 표 저장소와 그래프 저장소의 실제 위치를 나누어 그립니다. 각 연결의 주소와 접근 권한을 확인합니다.

## U07-S062 · 친구에게 localhost 주소를 보내면 내 서비스에 접속할까요?

### 발화

친구에게 localhost 링크를 보내도 내 화면으로 연결되지 않습니다. 공유 가능한 서비스 주소와 그 주소에 접근할 조건이 필요합니다. 서비스 화면이 열리는 것과 뒤쪽 저장소가 같은 자료를 읽는 것도 따로 확인합니다.

### 다음 장으로

접속 환경이 바뀌면 프로그램 실행 환경도 함께 준비해야 합니다.

## U07-S063 · 컨테이너는 실행 환경을 함께 포장합니다

### 발화

컨테이너는 프로그램과 실행에 필요한 환경을 이미지로 묶어 일관되게 실행하도록 돕습니다. 운영 데이터와 비밀값까지 모두 이미지에 넣는다는 뜻은 아닙니다. 다시 만들어도 되는 실행 환경과 계속 남아야 하는 기록을 구분합니다. 이미지 버전과 실행 설정이 실제 서비스의 조건을 결정합니다.

### 다음 장으로

개발 환경의 서비스 코드를 컨테이너로 묶어 Cloud Run에서 실행하는 구조를 살펴봅니다

## U07-S064 · 개발 환경의 서비스 코드를 컨테이너로 묶어 Cloud Run에서 실행하는 구조를 살펴봅니다

### 발화

개발한 서비스 코드를 이미지로 만들고 Cloud Run에서 실행하는 구조를 보겠습니다. 코드가 담긴 이미지와 외부 DB 연결은 다른 구성입니다. 키를 이미지에 넣으면 배포물 안에 복제될 수 있으므로 실행 환경에서 읽게 합니다. 모델 파일을 이미지에 준비하는 선택도 크기와 시작 시간을 고려해야 합니다.

### 다음 장으로

컨테이너 이미지만 있으면 승인 기록도 자동으로 복원될까요?

## U07-S065 · 컨테이너 이미지만 있으면 승인 기록도 자동으로 복원될까요?

### 발화

인스턴스가 사라지면 승인 기록도 사라지는지는 기록 위치에 달려 있습니다. 로컬 파일에만 쓰면 영속 기록을 보장할 수 없습니다. 외부 저장소에 쓰고 새 인스턴스에서 같은 기록을 읽는 구조를 확인합니다.

### 다음 장으로

실행 환경을 포장했어도 사라지면 안 되는 기록은 따로 보관해야 합니다.

## U07-S066 · 재시작 뒤 남아야 할 것을 먼저 고릅니다

### 발화

재시작 뒤 남아야 할 상태부터 고르겠습니다. 표와 벡터, 그래프, 승인 대기와 결정 이력은 업무의 연속성에 필요합니다. 임시 파일과 캐시는 다시 만들 수 있는지 확인합니다. 저장 기능이 있다는 이름보다 어떤 위치에 어떤 수명으로 남는지가 중요합니다.

### 다음 장으로

표 데이터·벡터·그래프·승인 대기·결정 이력은 외부 저장 위치를 정합니다

## U07-S067 · 표 데이터·벡터·그래프·승인 대기·결정 이력은 외부 저장 위치를 정합니다

### 발화

승인 대기 제안이 메모리에만 있다면 프로세스가 종료될 때 잃을 수 있습니다. 영속 체크포인트와 제안 저장소를 연결해 같은 대상과 버전을 다시 읽게 합니다. 로그 파일도 로컬과 클라우드의 보관 방식이 다를 수 있습니다. 기록 종류별로 복구 방법을 정합니다.

### 다음 장으로

주소가 잘 열리면 데이터 보존도 확인된 것일까요?

## U07-S068 · 주소가 잘 열리면 데이터 보존도 확인된 것일까요?

### 발화

저장 버튼이 성공했다는 것만으로 재시작 보존을 확인한 것은 아닙니다. 실제로 기록한 뒤 인스턴스가 바뀐 상태에서 다시 읽는 확인이 필요합니다. 이번 제작에서 그 실행을 하지 않았다면 배포 검증은 미실행으로 남깁니다.

### 다음 장으로

영속 저장 위치를 정했으니 구조와 내용을 실제로 옮기는 과정을 봅니다.

### 발화

저장소 이전에는 구조와 내용이 모두 필요합니다. 테이블이 존재해도 행이 없을 수 있고 벡터가 있어도 원문 연결이 끊길 수 있습니다. 데이터베이스마다 이전 책임을 정하고 대표 질의로 의미가 유지되는지 대조합니다. 행 수 하나로 모든 관계를 검증할 수는 없습니다.

## U07-S070 · Supabase는 로컬에서 개발하고 클라우드 환경으로 연결할 수 있습니다

### 발화

Supabase의 표·벡터와 Neo4j의 그래프는 별도 저장 위치를 확인합니다. 식별자와 문서 버전이 양쪽에서 맞는지 봅니다. 원문 조각을 검색한 뒤 해당 문서로 돌아갈 수 있어야 합니다. 그래프의 대표 경로도 출처와 관계 종류가 유지되는지 확인합니다.

### 다음 장으로

새 데이터베이스에 표가 생겼습니다. 이전 완료라고 해도 될까요?

## U07-S071 · 새 데이터베이스에 표가 생겼습니다. 이전 완료라고 해도 될까요?

### 발화

테이블 이름만 같으면 빈 구조를 옮겼을 수 있습니다. 행 수, 대표 식별자와 질의 결과를 함께 대조합니다. 그래프 반영이 대기 중인 상태라면 모두 이전됐다고 표시하지 않습니다. 완료한 저장 범위와 남은 반영을 나누겠습니다.

### 다음 장으로

저장소와 모델에 연결할 인증 정보도 환경에 맞게 전달해야 합니다.

## U07-S072 · 비밀값은 코드 대신 실행 환경에서 받습니다

### 발화

비밀값은 API 키와 DB 접속 정보처럼 접근 권한을 가진 값입니다. 코드와 이미지에 적는 대신 실행 환경에서 필요한 서비스가 읽도록 구성합니다. 키를 입력하는 창이 가려져 있다는 사실과 실제 파일·로그에 남지 않는다는 사실은 다릅니다. 저장 위치를 기준으로 확인합니다.

### 다음 장으로

이미지나 공개 저장소에 키를 넣지 않고 서비스가 필요한 비밀만 읽게 구성합니다

## U07-S073 · 이미지나 공개 저장소에 키를 넣지 않고 서비스가 필요한 비밀만 읽게 구성합니다

### 발화

서비스가 필요한 비밀만 읽도록 연결하고 오류에 원문 키가 출력되지 않게 합니다. 예제 파일에는 실제 값 대신 설정 이름을 둡니다. 설정이 없는 상태에서는 부족한 항목을 알려 주고 임의의 서비스로 대신 연결하지 않습니다. 실행에 사용하는 계정의 권한도 해당 작업에 맞춰 정합니다.

### 다음 장으로

키를 화면에서 별표로 가렸지만 이미지 파일에 원문이 들어 있습니다. 보호됐나요?

## U07-S074 · 키를 화면에서 별표로 가렸지만 이미지 파일에 원문이 들어 있습니다. 보호됐나요?

### 발화

화면에 별표가 보여도 이미지나 저장소에 원문이 들어 있으면 보호가 끝난 것이 아닙니다. 실제 저장 위치와 로그를 확인합니다. 이미 넣은 키를 화면에서 숨기는 편집과 비밀을 외부에서 읽는 실행 구조를 구분해야 합니다.

### 다음 장으로

연결을 구성했으니 상태 응답과 실제 업무를 나누어 확인하겠습니다.

## U07-S075 · 정상 응답과 업무 완료는 다른 확인입니다

### 발화

기본 상태 요청의 성공은 서버가 특정 확인에 응답했다는 뜻입니다. 문서 검색이나 승인 저장까지 모두 완료됐다는 뜻은 아닙니다. 상태 점검이 실제로 무엇을 검사하는지 범위를 읽습니다. 대표 업무가 필요한 저장소와 권한을 통과하는지 별도로 확인해야 합니다.

### 다음 장으로

기본 상태 요청이 성공해도 문서 검색 저장소가 비었거나 승인 기록 저장이 실패할 수 있습니다

## U07-S076 · 기본 상태 요청이 성공해도 문서 검색 저장소가 비었거나 승인 기록 저장이 실패할 수 있습니다

### 발화

서버는 정상 응답하지만 문서 저장소가 비어 있는 경우를 생각해 보겠습니다. 질문 화면은 열려도 근거 검색은 충분하지 않을 수 있습니다. 문서 적재, 벡터 연결과 검색 권한을 차례로 확인합니다. 승인 업무는 저장과 재개까지의 동선이 다른 확인 대상입니다.

### 다음 장으로

상태 요청은 성공하지만 RAG 답에 근거가 없습니다. 어디를 볼까요?

## U07-S077 · 상태 요청은 성공하지만 RAG 답에 근거가 없습니다. 어디를 볼까요?

### 발화

문서 질문이 빈 결과라면 서버가 켜졌다는 사실만 반복해서 확인하지 않습니다. 자료가 있는지와 검색 조건을 살핍니다. 조회 성공 후 근거 없음과 연결 실패를 구별해 첫 실패 지점을 찾습니다.

### 다음 장으로

기능이 동작해도 요청이 늘어나는 상황에서는 대기와 비용을 살펴야 합니다.

## U07-S078 · 요청이 늘면 대기와 비용도 관찰합니다

### 발화

요청이 늘면 처리 시간뿐 아니라 대기와 자원 사용도 달라집니다. 잡 큐는 오래 걸리는 일을 접수와 분리해 처리 순서를 관리하는 구조입니다. LLM 프록시는 모델 호출을 공통 창구로 모으는 구조입니다. 서로 다른 역할이며 이 수업에서는 현업 확장 개념과 필수 구현을 구별합니다.

### 다음 장으로

잡 큐는 오래 걸리는 일을 접수와 분리해 처리 순서를 관리하는 구조입니다

## U07-S079 · 잡 큐는 오래 걸리는 일을 접수와 분리해 처리 순서를 관리하는 구조입니다

### 발화

요청 한 건의 대기, 검색, 생성과 저장 시간을 보면 병목을 찾기 쉽습니다. 서버를 더 늘리기 전에 DB 연결과 모델 호출 제한도 살핍니다. 사용량과 비용을 연결해 예상과 실제 차이를 봅니다. 측정하지 않은 수치를 운영 성능처럼 쓰지 않습니다.

### 다음 장으로

서버리스이므로 사용자가 늘어도 비용을 볼 필요 없을까요?

## U07-S080 · 서버리스이므로 사용자가 늘어도 비용을 볼 필요 없을까요?

### 발화

새 버전에서 확인할 동작과 실패했을 때 복구할 범위도 정합니다. 배포 명령이 성공했다는 기록과 사용자가 기능을 쓸 수 있음을 확인한 기록을 구별합니다. 자동화는 이 확인을 반복할 수 있게 돕는 절차입니다.

## U07-S100 · 이전 버전 복귀 시 데이터 구조 호환성을 함께 확인해야 합니다

### 발화

새 버전에 문제가 있으면 이전 프로그램으로 돌아가는 방법을 생각할 수 있습니다. 하지만 새 표나 필드에 기록이 생겼다면 이전 코드가 그 자료를 읽을 수 있는지 확인해야 합니다.

코드 버전뿐 아니라 데이터 변경과 설정의 호환성을 봅니다. 되돌릴 수 있는 변경과 별도 복구가 필요한 변경을 나누고 기록을 잃지 않는 경로를 정합니다. 이전 버전이라는 이름만으로 항상 안전한 복구가 되는 것은 아닙니다.

## U07-S101 · 새 표 구조가 필요한데 프로그램만 되돌리면 항상 복구될까요?

### 발화

이전 코드가 기대하는 열이 새 구조에 없거나 값의 의미가 바뀌었다면 실행 파일만 바꿔도 오류가 남을 수 있습니다. 어떤 변화가 호환성을 깨뜨렸는지 확인하고 정한 복구 절차를 적용합니다.

복귀 뒤에도 기본 응답과 실제 업무를 나누어 확인합니다. 이번 흐름은 주소에서 시작해 상태 보존, 비밀, 내용 이관과 반복 배포까지 이어졌습니다. 다음 에이전트 기능을 붙일 때도 이 연결과 확인 범위를 함께 유지하겠습니다.

사용자가 문서 질문을 하면 빈 결과가 나올 수 있습니다. 이때 서버가 켜졌다는 검사만으로 수업 서비스가 준비됐다고 하면 학생이 필요한 자료를 찾지 못합니다. 어떤 대표 행동을 확인해야 업무 준비를 판단할 수 있을지 정하겠습니다.

실제 문서 질문에서 근거를 찾고 해당 원문으로 연결되는지 확인해야 합니다. 원본 조회와 필요한 저장소의 자료 존재도 함께 봅니다. 헬스 응답은 그 경로가 응답한 범위의 증거이며 모든 업무 기능의 증거가 아닙니다.

실제 배포 시에는 사용할 자료와 계정으로 대표 동선을 확인하고 그 결과를 남겨야 합니다. 준비한 코드가 있는 것과 배포 환경에서 해당 기능이 작동하는 것은 별도로 확인합니다. 빈 저장소를 정상 답변으로 숨기지 않는 상태 처리도 확인 대상입니다.

한 컴퓨터에서 한 번 이어졌다는 사실만으로 여러 인스턴스의 상태가 일치한다고 볼 수 없습니다. 사용자가 보는 하나의 서비스 뒤에서 상태를 어디에 보관하는지 살펴보겠습니다.

현재 대기 상태와 재개 대상을 대조하고 재시작이나 다른 인스턴스의 요청에서도 같은 의미가 유지되는지 확인합니다. 이는 실제 해당 환경에서 검증할 운영 조건입니다. 코드에 저장 기능이 있다는 사실만으로 분산 실행을 확인했다고 보고하지 않습니다.

## U07-S107 · 프로그램과 구조의 호환성, 데이터 보존, 필요한 변환 절차가 필요합니다

### 발화

복귀 계획에 코드와 데이터 구조의 호환성, 보존할 기록, 필요한 변환 절차를 포함해야 합니다. 어떤 변경은 이전 코드가 읽을 수 있게 점진적으로 적용할 수 있고, 어떤 변경은 별도 복구가 필요합니다. 실제 변경에 맞춰 절차를 정합니다.

백업이 있다는 사실만으로 복원이 검증된 것은 아닙니다. 필요한 경우 검토 가능한 환경에서 복구 절차와 자료 보존을 확인해야 합니다. 운영 데이터를 되돌리기 전에 검토 가능한 환경에서 필요한 절차를 확인합니다. 실제로 확인한 범위와 아직 검증하지 않은 복귀 조건을 구별해 두어야 합니다.
