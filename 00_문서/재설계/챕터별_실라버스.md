# 챕터별 실라버스 · 설비 관측에서 근거 있는 행동까지

2026-09-14 재설계안. 새 ZIP·팀장 피드백·사용자의 설계 재량 지시에 따라 작성한 제작 기준이다. 학교의 확정 회신을 받은 문서라고 표시하지 않는다. 일정·시수·반 구성과 온라인 이론/오프라인 실습은 유지하며, 엑셀과 새 HTML의 제목·스택 배열은 검토 재료로 사용했다.

## 과정이 끝나면 학생이 할 수 있는 일

자기 문제를 사용자·입력·필요한 결과·판정 기준으로 설명하고, 코드 에이전트에게 서비스를 만들게 한다. 나온 결과를 원본·비교 기준으로 확인하고, 표·관계·문서·도구 중 필요한 것을 선택해 연결한다. 증거가 부족한 결론과 승인 없이 실행할 행동을 멈춘다. 다른 도메인에 적용할 때 데이터만 바꾸면 되는 부분과 다시 설계해야 하는 부분을 구별한다.

서비스는 ‘설비 이상 대응 어시스턴트’ 하나가 자란다. 처음부터 자율 에이전트를 만들지 않는다. 사람이 관측을 읽는 도구를 먼저 만들고, 검증한 조회·판단·기록 기능을 나중에 에이전트가 호출한다. 학생마다 화면과 구현은 달라도 된다. 난이도는 설치 개수나 손코딩 분량이 아니라 모호한 요구를 구체화하고 반례를 찾아 설계를 고치는 판단에 둔다.

## 왜 이 순서인가

**관측을 읽는다 → 관측을 믿을 조건을 정한다 → 같은 대상과 출처를 연결한다 → 검토할 변화를 찾는다 → 해당 대상의 절차를 찾는다 → 답과 연결이 맞는지 평가한다 → 승인 가능한 행동으로 묶는다 → 운영하고 다른 문제에 옮긴다.**

문서 검색의 시작 질문은 ‘회사 문서를 챗봇에 넣어 보자’가 아니다. 앞 챕터에서 찾은 변화에 대해 ‘어떤 대상의 어떤 현행 절차를 확인해야 하는가’다. 경로와 문서가 존재해도 실제 고장 원인이 증명된 것은 아니다. 관측 사실·가능한 설명·추가 확인·허용된 조치를 구별한다.

## 공통 챕터

### C1. 무엇을 만들고 무엇을 관측할 것인가

**학생이 답할 질문:** 이 서비스는 누구의 어떤 판단을 돕고, 현재 자료로 어디까지 답할 수 있는가?

온라인: LLM의 입력·출력, 토큰·컨텍스트·구조화 출력의 역할과 한계, 코드 에이전트와 서비스 모델의 차이. 센서값·샷 순서·LOT·조건 기록의 관계. 열 이름과 실제 뜻을 구별하고 시각이 없는 자료를 실시간 신호로 오해하지 않는다.

오프라인: 관심 문제의 첫 설명을 작성하고 공통 제조 자료로 최소 조회 화면을 만든다. 자연어 질문의 결과를 원본 일부와 대조한다. 열 뜻·단위·원천을 확인해 질문 또는 입력 사전을 개선한다. 첫날부터 전체 DB/그래프/평가 도구를 모두 설치시키지 않고 오늘 조회에 필요한 환경을 코드 에이전트가 구성한다.

입력→남는 것: 센서 표와 현장 기록 구조 → 출처를 보여 주는 첫 서비스, 질문과 실제 비교 결과, 개인 문제의 첫 정의.

판단: 답이 없을 질문에는 무엇이 부족한지 말할 수 있고, 허용된 열 번호로 나왔다는 사실만으로 답을 신뢰하지 않는다. 다음 챕터는 그 값과 비교 기준이 믿을 만한지 살핀다.

### C2. 값의 품질과 시계열을 함께 읽는다

**학생이 답할 질문:** 변화처럼 보이는 것이 실제 변화인가, 결측·수집 오류·운전 조건 차이인가?

온라인: 결측·이상치·중복·단위와 품질 규칙, 원본과 정제 결과의 분리. 추세·변동·분포·상관, 이동 통계와 다운샘플링의 손실. 실제 시간축과 순서축의 차이, LOT/운전 조건을 섞은 상관의 위험. 라벨이 없으면 정상/불량 성능을 확정할 수 없다.

오프라인: 원본을 보존한 품질 표시와 정제 뷰를 만들고 동일 구간의 원본/처리 결과를 비교한다. 이동 추세, LOT 내 변동, 두 채널의 관계를 읽는 화면을 만든다. 화면 개수보다 질문에 필요한 시각화를 선택한다. 처리에 따라 급변이 사라지거나 그룹 차이가 결론을 바꾸는지 확인하고 짧은 근거 보고를 만든다.

입력→남는 것: C1의 표와 출처 → 품질 기준·처리 계보·관찰 범위를 표시한 분석 화면과 보고.

판단: 단순히 버릴 값과 아직 뜻을 모르는 값을 구별한다. 상관을 원인으로 표현하지 않으며, 시간 간격이 없는 샷 순서에 초/Hz 단위 해석을 붙이지 않는다. 다음에는 분석의 대상과 원천을 일관되게 연결한다.

### C3. 온톨로지와 데이터 패브릭으로 대상·출처를 잇는다

**학생이 답할 질문:** 이 관측은 어떤 설비·LOT·조건 기록을 가리키며 어느 원천에서 왔는가?

온라인: 온톨로지는 대상 종류·뜻·관계·식별 규칙의 설계이고 그래프 DB는 이를 저장·조회하는 수단이다. 조인과 경로 탐색의 차이. 데이터 패브릭의 카탈로그·계보·품질·접근 정책을 작은 서비스에서 어떻게 드러낼지 설명한다. 모든 데이터를 한 DB에 복사했다고 데이터 패브릭을 완성한 것은 아니다.

오프라인: C1의 작은 관계표를 정리해 그래프에 반영하고 LOT→조건표/작업일지 경로를 조회한다. 원천 ID·열 뜻·품질 상태·변환 이력·읽기 권한을 같은 카탈로그에서 찾도록 만든다. 이름이 같고 실제로 다른 대상 하나를 구별하고 새 원천을 등록했을 때 무엇을 갱신할지 정한다.

입력→남는 것: C2의 품질·계보와 C1의 대상 키 → 대상 지도, 원천 카탈로그, 경로별 출처.

판단: 번호가 같은 다른 원천을 임의로 합치지 않고, 잘못된 관계를 따라 그럴듯한 답이 나오는지 원본으로 대조한다. 기업용 데이터 패브릭 전체를 구현했다고 주장하지 않는다. 다음 챕터의 이상 사건은 이 대상 지도에 붙는다.

### C4. 이상 판단과 재실행 가능한 분석을 만든다

**학생이 답할 질문:** 어떤 변화를 검토 대상으로 표시하고, 기준을 바꾸면 무엇을 더 찾거나 놓치는가?

온라인: 절대/상대/조합 규칙, 기준 구간과 판정 구간, 통지 억제. 규칙·통계적 이상 점수·예측의 출력 차이. 기준선과 평가 구간, 누수, 재실행과 단계 실패. 표 분류·비전 정상 학습·RUL을 같은 ‘AI 점수’로 섞지 않고 필요한 라벨과 검증 방식으로 비교한다.

오프라인 공통: 규칙과 시계열 분석 방법 하나를 같은 관찰 구간에서 비교하고 사건을 원본 행·LOT에 연결한다. 적재→판단→기록을 재실행 가능한 흐름으로 묶으며, 입력이 부족하면 다음 단계로 넘어가지 않게 한다. 학생이 선택한 비교 기준과 누락 범위를 읽을 수 있게 만든다.

선택 확장: 같은 메뉴를 두 반 모두에게 제공한다. 예측과 직전값 비교, 표 분류와 규칙 라벨의 한계, 이미지 이상 탐지, RUL 대체 데이터 중 자기 문제와 데이터 조건에 맞는 하나를 선택한다. 공통 이론에서 네 방법의 차이는 모두 다루되 모든 라이브러리의 별도 학습 완주를 공통 필수 과제로 만들지 않는다. 선택 확장이 공통 핵심 완성을 방해하지 않도록 독립 입력과 접속 규약을 제공한다.

입력→남는 것: C3 대상 지도와 검토할 관측 → 설명 가능한 이상 사건, 기준선 비교, 재실행 결과.

판단: 경보 없음과 정상 확인, 예측 임계 도달과 실제 수명, 열지도와 결함 확정을 구별한다. 다음 챕터에서는 사건에 맞는 확인 절차를 찾는다.

### C5. 사건에 필요한 현행 문서를 찾아 근거를 붙인다

**학생이 답할 질문:** 이 대상과 상황에서 어떤 절차를 근거로 무엇을 확인해야 하는가?

온라인: RAG의 파싱·청킹·임베딩·검색·생성, 문서 상태와 표 구조. 대상/조건에 맞는 검색 필터, 정확한 문서번호와 의미 검색의 차이. 단순 검색의 결과를 보고 필요할 때 하이브리드와 리랭크를 적용한다.

오프라인: C4 사건→C3 대상/관계→관련 현행 문서→확인 항목으로 연결한다. 근거가 있는 질문과 자료만으로 답할 수 없는 질문을 함께 비교한다. 문서 전체가 아니라 인용된 조항이 실제 답을 지지하는지 확인한다. 표의 머리글이나 예외 조건이 잘렸다면 그 단계부터 고친다.

입력→남는 것: 사건·관계·상태가 있는 절차 문서 → 관측 사실/문서 근거/추가 확인이 나뉜 답변.

판단: ‘연결된 문서가 있으니 원인은 X’라고 결론내리지 않는다. 자료가 없거나 적용 조건이 맞지 않으면 보류한다. 다음 챕터는 이 판단을 여러 질문과 후속 대화에서 비교한다.

### C6. 평가와 후속 대화로 서비스의 경계를 확인한다

**학생이 답할 질문:** 검색을 잘한 것과 답을 잘한 것은 어떻게 다르며, 새 질문에서도 같은 근거 범위를 유지하는가?

온라인: 질문별 기대 근거, 검색/인용/답변/거절 평가의 분리. 모델 평가자의 한계, 사람의 검토와 코드 검사의 역할. SQL/문서/관계의 경로 선택, 이전 문맥의 재사용과 새 요청의 범위. API/사내 모델의 지연·토큰·비용과 미측정 값.

오프라인: 앞 챕터부터 사용한 비교 사례에 학생이 고른 질문과 후속 질문을 보탠다. 같은 조건으로 변경 전후를 비교하고, 답이 좋아져도 근거가 잘못됐으면 개선으로 세지 않는다. 평가 프레임워크는 대표 하나로 연결하고 결정적인 회귀 조건은 작은 코드 검사로 남긴다. 두 모델은 사용 가능한 환경에서 같은 질문으로 비교하며 미제공 환경을 가짜 점수로 채우지 않는다.

입력→남는 것: C5의 근거 답변 → 질문/후속 대화 평가 묶음, 실패 분류, 필요한 개선 선택.

판단: 변경이 실제로 필요한지 판단할 수 있어야 한다. 이미 만족한 결과를 일부러 나쁘게 만들거나 모든 고도화 장치를 설치하는 과제로 바꾸지 않는다. 검증한 기능을 다음 챕터에서 도구로 감싼다.

### C7. 검증한 도구를 승인 가능한 에이전트로 묶는다

**학생이 답할 질문:** 어디까지 자동으로 맡기고, 무엇을 사람이 결정해야 하는가?

온라인: 함수/워크플로/에이전트의 차이, 도구 계약과 MCP, 상태·재개·걸음 상한. 근거 없는 제안의 보류, 사람 승인과 실행 권한의 분리, 반복 실행과 실제 설비 제어의 차이.

오프라인: 기존 조회·검색·관계·제안·기록 기능을 도구로 제공하고 관측→근거 확인→제안→사람 승인→기록→재관측을 연결한다. 승인 전 변경이 없는지, 재개/중복 요청이 의도하지 않은 두 번의 변경을 만들지 않는지 확인한다. 후속 질문이 이전 근거를 재사용하면서도 새 대상과 권한을 다시 확인하도록 만든다.

입력→남는 것: C6에서 검토한 기능 → 검토 가능한 제안, 승인/반려 기록, 변경 전후 관측.

판단: 도구가 none을 반환한 것을 정상으로 해석하지 않는다. 물리 설비를 조작하지 않고 승인된 소프트웨어 규칙·기록 범위만 다룬다. 다음에는 개인 컴퓨터 밖에서 이 상태를 유지한다.

### C8. 서비스를 배포하고 운영 조건을 설명한다

**학생이 답할 질문:** 다른 사람이 접속하고 서버가 다시 시작돼도 어떤 데이터와 판단 기록이 남아야 하는가?

온라인: UI/API/영속 저장소의 경계, 컨테이너와 외부 설정, 비밀값, 접근 권한, 오류·비용·관측, 배포와 모델 성능 검증의 차이.

오프라인: 학생 서비스의 실행 계약을 정리하고 같은 기능을 배포 환경에 연결한다. 재시작 뒤 남아야 할 원천·질문 근거·승인 기록을 확인하고, 다른 사용자가 불필요한 원문이나 키를 볼 수 없는지 점검한다. 유료 자원이나 실제 데이터 외부 업로드는 제공 계정·이용 조건이 확인된 범위에서 수행한다. 미제공 자원은 로컬 패키지와 필요한 배포 설정을 완성하고 실제 배포 미실행을 표시한다.

입력→남는 것: C7 서비스 → 재현 가능한 실행/배포 절차, 운영 조건과 제한.

판단: /health 정상과 전체 서비스의 정답 보장을 구별한다. 다음에는 이 구성에서 제조에 묶인 가정을 찾아 바꾼다.

### C9. 자기 문제로 옮겨 PBL을 시작한다

**학생이 답할 질문:** 내 문제에서는 무엇을 그대로 쓰고, 무엇을 새로 배워 바꿔야 하는가?

온라인: C8과 이어서 사용자 요구·데이터 조건·수용 기준을 세우고 기술을 덜 쓰거나 다른 방법으로 대체하는 판단을 다룬다. 새 기술 문서에서 필요한 기능과 최소 예제를 찾고 자기 데이터로 확인하는 절차를 보여 준다.

오프라인: C1부터 발전시킨 개인 문제 또는 제공된 비제조 사례로 새 서비스 일부를 처음부터 설계한다. 열 이름만 바꾸는 데서 끝내지 않고 대상 관계·문서 적용 조건·판정·승인 중 달라지는 가정을 찾아 수정한다. 동료/강사가 제시한 다른 입력에 결과를 설명하고 개선한다. 학생에게 같은 화면·주제·완성 프롬프트를 강요하지 않는다.

입력→남는 것: 자신의 요구와 새로운 자료 → 동작 범위를 설명할 수 있는 개인 프로토타입, 다음에 배울 것과 검증할 것.

판단: 도구 이름을 암기했는지가 아니라 ‘문제 정의→필요한 기술 선택→근거 확인→연결→한계 설명’을 스스로 수행하는지 본다. 별도 의무 회고문이나 고정 개수의 노트를 제출 조건으로 추가하지 않는다.

## 두 반의 구성과 수업 방식

두 반은 C1~C9와 같은 선택 확장 목록을 사용한다. 실전반은 챕터당4시간으로9회, 통합반은 같은9챕터에 C9 개선·전이4시간을 더해10회다. 통합반에만 비전/배포를 주거나, 실전반이 배우지 않은 챕터를 통합반 출발본에 몰래 넣지 않는다. 날짜별 연결은 함께 제공하는 편성표를 따른다.

오프라인4시간의 기본안은 출발20 + 실습45×4 + 휴식10×2 + 정리20=240분이다. 네 구간은 문제/비교 기준 정하기→만들기→관찰/개선→연결/다른 입력 확인으로 쓰되 내용에 따라 경계를 조정한다. 설명은 행동 옆에 짧게 넣는다. 이 시간은 수업 설계값이며 실제 학생 소요시간은 아직 측정하지 않았다. 휴식·오류 복구를 0분으로 전제하지 않는다.

온라인은 엑셀의 실전8편32H, 통합11편44H를 유지한다. 실전 영상1~7은 C1~C7, 영상8은 C8~C9다. 통합 영상1~8은 C1~C8, 영상9는 C9, 영상10~11은 같은 내용의 전이 사례와 실패 분석을 확장한다. 추가 영상은 신규 필수 스택이나 별도 학습목표를 더하지 않는다. 영상의 과제·정지 시간을 임의로 더해 실제 설명240분을 충족했다고 주장하지 않는다. 상세 장면/발화 시간은 후속 덱 설계에서 산정한다.

## 스택 선택과 학습 부담

| 역할 | 제작 기준 | 채택 이유와 경계 |
|---|---|---|
| UI/API | Vue + FastAPI | 한 서비스의 화면·데이터·도구 경계를 분명히 둔다. 학생은 구현 언어보다 요청/결과 계약을 다룬다 |
| 표·기록·벡터 | Supabase/Postgres + pgvector | 표 저장과 문서 벡터를 같은 운영 경계에서 다룬다. 별도 벡터DB를 추가 필수로 설치하지 않는다 |
| 대상/관계 | Neo4j, C3부터 | 관계표의 의미를 먼저 정하고 그래프 DB를 도입한다. 제품 비교 설치는 공통 과제가 아니다 |
| 모델 | 설정으로 분리한 API/사내 게이트웨이 | 실제 제공 모델·주소·비용 조건을 확인해 사용한다. 이름을 추측하거나 비싼 모델을 임의로 실행하지 않는다 |
| 시계열/선택 확장 | 규칙·이동 통계 + PyOD 중심 비교, Chronos/분류/비전/RUL 선택 | 방법 선택과 평가 조건을 가르친다. 모든 분석 패키지의 동시 설치/학습을 첫날 요구하지 않는다 |
| 문서 | 원문 구조 확인, 필요 시 Docling, 임베딩1종 + pgvector | 처음에는 단순 검색으로 비교 기준을 만들고 실제 필요에 따라 하이브리드/리랭크를 붙인다 |
| 평가 | 질문/기대 근거 + 코드 검사, 대표 모델평가 도구1종 | RAGAS와 DeepEval을 모두 별도 학습 목표로 강제하지 않는다. 평가자 점수는 실제 정답 판정과 구별한다 |
| 에이전트 | LangGraph + 필요한 기능을 감싼 MCP | 승인·상태·재개를 배울 때 도입한다. 첫날부터 프레임워크 전체를 설명하지 않는다 |
| 운영 | Docker, 제공 환경에 맞춘 Cloud Run/Supabase 배포 | 호스팅 제품 수보다 상태 보존·권한·비용과 재현성을 확인한다 |

기술 역할 확인 근거: [Supabase pgvector](https://supabase.com/docs/guides/database/extensions/pgvector), [Neo4j 시작 문서](https://neo4j.com/docs/getting-started/), [LangGraph 승인 중단·재개](https://docs.langchain.com/oss/python/langgraph/interrupts). 이 선택은 교육 설계 판단이며 성능 비교 실측 결과가 아니다. 정확한 버전과 설치 묶음은 실습 구현 단계에서 고정한다.

## 이전 안에서 바꾸는 핵심

- ‘AI 기술별 독립 실습’에서 한 서비스의 다음 판단에 필요한 기능으로 이어지는 구성으로 바꾼다.
- 시계열/온톨로지/패브릭을 RAG 앞에 두고 실제 대상·출처·상황으로 문서를 선택하게 한다.
- 품질과 시계열 해석을 묶되 모델 학습과 섞지 않는다. 판단 대상·라벨이 다른 비전/RUL은 선택 확장으로 둔다.
- 평가는 끝에서 새로 시작하지 않는다. C1부터 비교하고 C6에서 체계화한다. 개인 PBL 문제도 C1부터 자란다.
- ‘번호 출력이면 지어낼 수 없다’, ‘상관이면 조합 규칙의 근거다’, ‘그래프 경로면 원인이다’ 같은 단정은 채택하지 않는다.
- 모든 블록이 꼭 실패해야 한다거나 고정한 힌트 줄 수·노트 개수가 학습을 보장한다는 조건은 사용하지 않는다.

현재 문서는 챕터 설계와 날짜 편성의 기준이다. 기존767장·가이드·코드 ZIP은 이 설계에 맞춰 재판정할 후보이며, 그 파일 수나 과거 검사 통과는 이번 재설계의 완료율이 아니다.
