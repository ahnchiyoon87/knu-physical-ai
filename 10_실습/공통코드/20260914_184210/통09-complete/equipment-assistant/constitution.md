# 설비 이상 대응 어시스턴트의 계약

표·관계·문서의 근거를 확인하고 관측된 이상에 대한 검토안을 만든다. 사람이 승인한 소프트웨어 규칙 변경과 기록만 실행하며 실제 설비를 제어하지 않는다.

## 입력과 사실

- `mapping.json`이 원천 경로·열 이름·뜻·단위·LOT 규칙·라벨·문서 상태의 기준이다. 값과 열을 코드에 박지 않는다.
- 원본 파일을 이동·덮어쓰지 않는다. 등록한 파일을 읽어 데이터베이스에 적재하는 것은 허용하며 파일 해시·매핑 해시와 원본 행 번호를 남긴다.
- 근거·설계·교육용 합성을 구별한다. 합성을 실측으로 바꾸지 않고, 원본이 없을 때 다른 프로필로 자동 대체하지 않는다.
- 파일 순서와 경과시간, 관계 경로와 인과, 알람과 품질 라벨, 임계 도달 예상과 실제 잔여수명을 구별한다.

## 책임

`backend/data`는 표, `ontology`는 관계, `detect`는 감지·분석, `rag`는 문서, `eval`은 평가, `agent`는 흐름, `process`는 승인·기록, `common`은 설정·응답·관측을 맡는다. 각 층의 외부 호출은 해당 `gateway` 또는 역할이 드러난 `*_gateway`에 둔다. 모델 계산과 순수 함수는 별도 모듈로 나눌 수 있다. 상위 흐름은 하위 서비스를 조합하며 하위 서비스는 상위 흐름을 호출하지 않는다.

Postgres는 원천과 업무 기록 및 체크포인트의 정본이다. pgvector는 문서 벡터, Neo4j는 관계 투영을 저장한다. 두 저장소를 하나의 원자 트랜잭션처럼 설명하지 않는다. 그래프 반영 대기와 실패를 드러낸다.

## 응답

응답은 `rid`, `status`, `answer`, `evidence`, `reason`, `meta`를 포함한다. `ok` 외에는 이유가 필요하다.

| 상태 | 뜻 |
|---|---|
| ok | 요청한 결과가 있으며 적용 범위와 근거를 함께 제공 |
| none | 조회했으나 해당 결과가 없음. 정상 판정 아님 |
| insufficient | 필요한 입력·대상·기준 부족 |
| refused | 근거 또는 권한·적용 범위 조건을 만족하지 못해 답변/실행 보류 |
| failed | 실행 또는 검증 실패 |
| error | 잘못된 인자·설정·계약 |
| pending_approval | 사람의 결정 대기 |

문서 근거는 문서번호·조항·본문·현행 상태, 표 근거는 원천·SQL·행 수, 관계 근거는 대상 경로·관계 출처를 포함한다. 근거 번호가 존재하는 것만으로 주장 지지를 확정하지 않는다.

## 질의·모델

- 모델 SQL은 단일 SELECT·허용 표·허용 함수만 통과한다. 별도 읽기 전용 계정과 트랜잭션, 실행 시간 제한을 사용한다. 행 제한은 커서에서 적용하며 SQL 본문은 바꾸지 않는다. 표시가 잘렸으면 알린다.
- 열 번호·닫힌 출력은 형식을 제한하는 장치다. 허용된 잘못된 번호나 의미 오류까지 제거하지 않는다.
- 정찰 결과는 실제 적재된 LOT 범위를 보여 준다. 의미 심사의 PASS/FAIL/UNKNOWN을 코드로 집계하되 모델 심사를 정답으로 단정하지 않는다.
- 수리는 근거가 있는 불일치에 한 번만 수행하고 전후 SQL·심사·변경 이유를 남긴다. 실패를 반복 요청으로 숨기지 않는다.
- 모델 제공자는 API/사내로 분리한다. 실제 이름과 주소·키는 환경 설정으로 읽으며 다른 모델로 자동 전환하지 않는다.
- 호출은 명시적으로 켜야 하며 코드 에이전트와 서비스 모델은 별개다. 입력 상한은 자르기 대신 오류로 표시한다. 문자 상한은 운영 설정이고 모델 컨텍스트 실측값이 아니다.
- 모델 호출마다 이름·입출력 토큰·요금 정보에 근거한 비용·요청 시간을 남긴다. 정보가 없으면 null/미측정이며 0원으로 채우지 않는다.

## 문서·평가

표 문서 조각에는 머리글을 붙인다. 현재 질문의 근거에는 해당 프로필의 현행 문서만 사용한다. 근거 0이면 생성하지 않는다. 하이브리드 검색과 리랭크는 서로 다른 단계를 기록한다.

RAGAS 네 지표는 모델 심사이며, 계약 검사·DeepEval 회귀와 역할이 다르다. 거절 사례를 높은 답변 점수로 치환하지 않는다. 같은 질문·자료·설정을 고정해 비교하고 실패도 결과로 남긴다.

## 도구와 승인

MCP 서버 하나에 `query_events`, `search_docs`, `graph_path`, `propose_action`, `record_decision` 다섯 도구를 둔다. 일하는 에이전트용이며 만드는 에이전트에 자동 연결하지 않는다. 조회의 none은 에이전트에서 insufficient로 멈춘다.

제안은 대상 규칙·현재 버전·이벤트 근거·허용 범위를 확인한 뒤 승인 대기가 된다. 사람의 승인 경로는 서비스 접속 권한과 분리한다. MCP에는 승인 도구가 없다.

결정은 제안 ID·버전·내용 해시에 묶인다. 승인이 저장되지 않았거나 승인 후 대상 규칙이 달라졌으면 변경하지 않는다. 같은 결정을 재요청해도 규칙 버전을 다시 올리지 않는다. 승인·규칙·결정 기록은 하나의 DB 트랜잭션으로 연결한다.

에이전트는 Postgres 체크포인트로 대기·재개하고 걸음 상한과 반복 감지를 적용한다. 이전 대화의 승인이나 대상이 새 요청에 자동 적용되지 않는다.

## 화면과 운영

표 질문, 품질, 관계, 감지, 문서 근거, 평가, 승인, 관측을 구분한다. 답·근거·상태와 사용한 모델을 확인할 수 있어야 한다. `/health`의 서버 상태를 모든 모델 기능의 성공으로 표시하지 않는다.

인증 키·원문 전체·개인정보를 로그에 넣지 않는다. `/trace`는 동일 요청의 단계 기록을 보여 준다. 실제 실행·예상 결과·단순 검사를 구별하고 실행하지 않은 것을 성공으로 기록하지 않는다.
