## 숫자에 뜻을 붙여 첫 서비스를 만듭니다

만들 결과: **내 말로 물으면 선택한 표에서 답을 찾고, 어느 열을 썼는지 확인할 수 있는 서비스**

오늘은 완성된 앱을 실행하는 날이 아닙니다. 출발본에는 폴더·계약·자료가 있고 앱 코드는 없습니다. 코딩 에이전트가 코드를 쓰고, 여러분은 질문과 확인 기준을 정합니다. 화면의 모양은 달라도 됩니다. 어떤 자료에서 무엇을 계산했는지가 보여야 합니다.

### 1. 한 행을 읽고 첫 화면을 부탁합니다 · 약 50분

사출의 샷은 한 번의 성형 동작입니다. LOT는 함께 관리하는 생산 묶음입니다. 이 자료의 LOT는 시각이 아니라 No_Shot이 0으로 돌아오는 경계에서 붙인 번호입니다. 숫자 22는 열 번호이고, 쿠션이라는 뜻과 mm라는 단위는 열 사전에서 읽습니다.

data의 입력과 mapping.json을 열어 한 행·쿠션 열·순서 열을 찾아봅니다. 에이전트에게 파일을 읽는 화면과 원천별 적재 기능을 자신의 말로 요청하세요. raw 파일은 보존하고 화면에서 원천 이름·행 수·열의 뜻·단위를 볼 수 있게 합니다. 코드 문법을 직접 채우는 과제는 아닙니다.

**빈 폴더에서 첫 화면까지.** 코딩 에이전트에게 먼저 `AGENTS.md`와 `constitution.md`를 읽고 오늘의 표 적재·조회만 작은 순서로 만들도록 요청합니다. 전체 과정의 기능을 한 번에 만드는 요청으로 넓히지 않습니다. 화면은 Vue, 서버는 FastAPI, 표 저장은 PostgreSQL이라는 준비된 방향을 사용하되 코드 구조와 구현은 에이전트가 맡습니다. 첫 결과는 프로필·원천 선택, 파일 읽기, 행 수와 열 사전 보기입니다.

합성 자료를 선택했다면 `mapping.json`의 `profiles → synthetic → sources → shots`에서 경로가 `data/generated/shots.csv`인지 읽고 실제 파일을 엽니다. `conditions`와 `worklog`는 별도 원천입니다. 원본을 선택했다면 해당 원천의 실제 파일 경로와 존재 여부부터 확인합니다.

**만든 뒤 실행합니다.** 첫날 뼈대에는 아래 명령에 필요한 파일도 아직 없습니다. 에이전트가 `pyproject.toml`·`uv.lock`, `frontend/package.json`·잠금 파일, `scripts/bootstrap.py`·`scripts/serve.py`를 만들고 실행 순서를 README에 적었는지 먼저 확인합니다. 파일이 없으면 명령을 반복하지 말고 구현 요청의 빠진 연결로 되돌아갑니다.

1. `.env.example`을 로컬 `.env`로 복사합니다. 기존 파일은 덮지 않습니다. SERVICE_TOKEN은 자신이 정한 접속 값이고 모델 키와 다릅니다. 모델 호출은 아직 꺼 둡니다.
2. 설치 PDF에서 준비한 Docker를 켜고 프로젝트 루트 터미널에서 `npx supabase@2.117.0 start`를 실행합니다. `supabase/config.toml`이 없는 첫 설정에만 `npx supabase@2.117.0 init`을 먼저 합니다. 표시된 DB 주소를 DATABASE_URL에 넣고, 별도 읽기 전용 계정 주소를 READONLY_DATABASE_URL에 준비하도록 에이전트의 README와 대조합니다.
3. 아래는 참고 구조의 순서입니다. 자기 구현에서 명령을 바꿨다면 같은 역할을 하는 명령을 에이전트와 확인하고 README에 남깁니다.

```powershell
uv sync --frozen --extra dev
uv run --env-file .env python scripts/bootstrap.py
npm.cmd --prefix frontend ci
npm.cmd --prefix frontend run build
uv run --env-file .env python scripts/serve.py
```

`http://localhost:8000`을 열고 연결 칸에 자신의 SERVICE_TOKEN을 넣습니다. 서버 터미널은 켜 둡니다. 상태 응답을 본 뒤 합성 프로필의 shots를 적재해 표를 읽습니다. 모델이 꺼져 있어도 이 파일·표 단계는 확인할 수 있어야 합니다. 주소가 열리지 않으면 터미널의 첫 오류, 401이면 토큰, DB 오류면 저장소 상태와 bootstrap 결과부터 에이전트와 확인합니다.

**결과를 읽습니다.** 화면에 교육용 합성인지 원본인지 표시되고, 같은 파일을 다시 넣어도 행 수가 늘지 않아야 합니다. 파일이 없으면 없다고 나와야 합니다. 파일 경로만 존재하는 설정을 적재 성공으로 읽지 마세요.

**막히면 여기서 확인합니다.** 파일을 못 읽으면 앱 전체를 다시 만들지 말고 선택한 원천 ID, mapping의 path, 파일 첫 줄 순서로 에이전트와 확인합니다.

표를 열 수 있어도 질문의 뜻을 잘못 읽을 수 있습니다. 다음에는 같은 표를 자연어로 묻습니다.

### 2. 그럴듯한 답을 표와 대조합니다 · 약 50분

LLM은 문장을 이어 만드는 모델입니다. SQL은 표에서 필요한 행을 고르고 계산하는 문장입니다. 모델에게 계산값을 외워 답하게 하지 않고 SQL을 만들게 하되, 실행 가능하다는 사실과 질문에 맞다는 사실을 나눠 봅니다.

질문셋의 첫 질문 하나를 골라 자기 말로 바꿉니다. 선택한 원천에서 SQL을 만들고 읽기 전용으로 실행하는 질문 칸을 요청하세요. 먼저 결과표와 SQL을 함께 봅니다. 질문 10개를 한꺼번에 맡기지 말고 하나씩 대상·범위·계산을 확인합니다. 답을 확신할 수 없는 질문도 포함합니다.

**지금 모델을 연결합니다.** 코드를 작성하는 에이전트와 이 서비스가 질문에 답할 때 호출하는 모델은 별개입니다. 수업에서 정한 모델의 이름·주소·키를 로컬 `.env`의 API_MODEL_NAME·API_MODEL_BASE_URL·API_MODEL_KEY에 넣습니다. 지원 응답 형식과 비용을 확인한 뒤에만 ALLOW_MODEL_CALLS=true로 켭니다. 값이 없는 예시 파일만으로 모델이 준비된 것은 아닙니다. 사내 모델을 쓰기로 했다면 별도 INTERNAL_MODEL 설정을 사용하며 API로 자동 우회하지 않습니다.

설정을 바꿨으면 서버 터미널에서 Ctrl+C로 종료한 뒤 같은 실행 명령으로 다시 시작합니다. 첫 질문 하나만 보내 SQL과 결과표를 봅니다. 연결이 실패하면 공급자·주소·모델 이름과 오류 이유를 확인하고, 성공한 다른 모델 결과로 바꾸어 표시하지 않습니다. 질문에는 키를 붙여 보내지 않습니다.

**작은 범위로 답을 확인합니다.** 질문이 가리킨 열과 LOT를 결과 SQL에서 찾고, 선택된 원본 행의 값과 계산을 대조합니다. 평균이면 어떤 행을 더해 몇 건으로 나눴는지, 상위 10개이면 어떤 열로 정렬했는지 확인합니다. 조건표나 작업일지가 필요한 질문은 해당 원천을 별도로 적재해야 합니다. 검사 라벨이 없는 표에서 불량 수를 지어내지 않습니다. 열 이름·뜻·단위의 힌트를 바꾸기 전 같은 질문의 입력과 결과를 남겨 다음 단계 비교에 씁니다.

**결과를 읽습니다.** 쿠션을 물었는데 다른 위치 열을 쓰거나 LOT별 질문에 전체 평균 하나만 내면 오답입니다. 정답 문장 암기가 아니라 사용한 열·묶음·단위가 맞는지 봅니다. 조건이 없는 질문은 추가 조건이 필요하다고 나와도 좋습니다.

**막히면 여기서 확인합니다.** 모델 연결 오류는 추론 능력 평가가 아닙니다. 공급자 이름·주소·JSON 응답 지원부터 확인합니다. 키는 화면 캡처나 질문 내용에 넣지 않습니다.

틀린 답이 있다면 어떤 정보가 빠졌는지 가릅니다. 처음부터 맞았다면 그 질문과 결과를 기준으로 유지하고, 다음 단계에서 사전이 필요한 다른 질문이 있는지 확인합니다.

### 3. 열 이름 추측을 열 사전으로 바꿉니다 · 약 50분

열 사전은 이름·뜻·단위·근거를 한데 둔 설명표입니다. 모델이 뜻을 추측하는 대신 이 사전을 읽게 합니다. 모델은 등록된 열 번호를 선택하고 코드는 실제 열로 연결합니다. 번호가 있다고 의미까지 맞는 것은 아닙니다.

방금 사용한 질문을 그대로 남깁니다. 열 선택 오류가 있었다면 열 뜻과 단위를 전달하도록 요청을 한 번 바꿉니다. 오류가 없었다면 이미 맞는 결과를 보존하고 사전이 필요한 질문을 비교합니다. Injection_Pressure_Real_Time을 압력으로 읽었는지, Screw_Position과 Minimum_Cushion을 서로 다른 값이라고 여겼는지 확인합니다. 모르는 단위는 빈 추측으로 메우지 않습니다. 이후 실제 LOT 수를 조회한 결과도 질문 입력에 연결합니다.

**결과를 읽습니다.** 수정 전후에 같은 질문을 사용합니다. 좋아진 항목과 여전히 불확실한 항목을 구분하면 됩니다. 모델이 사전에 없는 열 번호를 냈을 때 SQL을 실행하지 않는지도 확인합니다.

**막히면 여기서 확인합니다.** 모든 뜻을 한 번에 다시 쓰기보다 틀린 열 하나의 원문 근거부터 확인합니다. 사전 자체가 틀렸으면 모델 프롬프트만 고쳐서는 해결되지 않습니다.

뜻을 아는 표가 생겼습니다. 이제 표와 작업 기록이 어떻게 연결되는지 지도로 옮깁니다.

### 4. 관계 한 줄을 추가하고 길을 읽습니다 · 약 50분

온톨로지는 이 서비스에서 무엇을 어떤 대상으로 부르고 어떻게 연결할지 정한 약속입니다. 관계표의 한 줄은 출발 대상·관계 이름·도착 대상·근거입니다. 선이 있다는 이유만으로 원인이 증명되지는 않습니다.

ontology의 관계표에서 샷 원천, LOT, 조건표, 작업일지를 찾아봅니다. 자기 질문에 필요한 관계 한 줄을 정하고, 화면에 두 대상을 연결한 경로를 보여 달라고 요청합니다. 교육용 LOT 4와 작업일지의 관계를 먼저 읽습니다. 원본을 사용할 때는 실제 자료에서 확인한 LOT 번호로 바꿉니다.

**관계표를 먼저 읽습니다.** 첫날 참고 구현은 `ontology/synthetic.csv`를 읽어 경로를 찾는 방식입니다. 이 단계에 Neo4j를 새로 띄울 필요는 없습니다. 행의 `source`·`relation`·`target`·`provenance`가 각각 출발 ID·관계·도착 ID·근거입니다. 화면에서 관계표를 읽은 뒤 `synthetic:shots:lot:4`에서 `synthetic:worklog:lot:4`로 가는 경로를 확인합니다. 두 ID는 오늘 제공된 합성 관계표에서 읽은 예시입니다.

새 관계는 실제 자료에서 근거를 확인한 경우에만 추가합니다. 이미 있는 행을 그대로 복제하지 말고 자기 질문에 필요한 연결을 고릅니다. 확인할 관계가 더 없으면 기존 경로의 뜻을 설명하는 데서 멈추어도 됩니다. CSV를 고쳤다면 화면의 관계표 읽기를 다시 요청하고 같은 두 ID로 변경을 확인합니다. 나중에 그래프 DB로 옮기는 것과 오늘 관계의 뜻을 확인하는 일은 구분합니다.

**결과를 읽습니다.** 관계의 양 끝 ID가 실제 대상과 같고 출처가 표시되어야 합니다. 존재하지 않는 대상을 물었을 때 빈 경로를 고장 원인으로 설명하면 안 됩니다. 오늘 만든 표 질문과 관계 화면을 각각 한 번 설명해 봅니다.

**막히면 여기서 확인합니다.** 선이 안 보이면 그래프 색이나 배치보다 두 ID의 철자·프로필 접두어·적재 여부를 먼저 확인합니다.

데이터를 연결했지만 깨끗한지는 아직 모릅니다. 다음 단계는 이상한 숫자를 지우기 전에 뜻부터 확인하는 일입니다.

현재 폴더와 실행 설정을 저장하고 오늘 확인한 대표 입력을 다시 찾을 수 있게 둡니다. 아직 실행하지 않은 모델이나 부족한 자료는 성공 결과로 바꾸지 않습니다. 다음 시간에는 자기 프로젝트를 이어가거나 그날 출발본으로 합류할 수 있습니다.
