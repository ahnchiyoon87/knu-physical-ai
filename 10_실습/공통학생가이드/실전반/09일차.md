## 오늘 작업을 엽니다 · 20분

잘 이어지는 자기 프로젝트는 그대로 사용합니다. 결석했거나 진행이 막혔다면 오늘 배포받은 출발본을 새 폴더에서 엽니다. 자기 작업을 삭제하거나 덮지 않습니다. 두 폴더의 서버를 동시에 실행하지 않습니다.

VS Code에서 작업 폴더를 열고 README와 실행 연결 안내 순서로 이전 단계의 서버와 자료 연결을 확인합니다. 오늘 기능은 그 위에 코딩 에이전트에게 목적과 확인 기준을 설명하며 만듭니다.

설치가 남았다면 [Google Cloud](../../../실습가이드핸즈온문서/1_GoogleCloud세팅.pdf), [VS Code와 코딩 에이전트](../../../실습가이드핸즈온문서/2_VSCode설치및_코딩에이전트세팅.pdf), [Docker](../../../실습가이드핸즈온문서/3_도커설치및세팅.pdf), [의존성](../../../실습가이드핸즈온문서/4_실습의존성설치.pdf) 중 필요한 단계를 마칩니다. 설치 뒤에는 [실행 연결 안내](../../학생가이드/실행_연결_안내.md)를 확인합니다.

synthetic은 교육용 합성, kamp는 직접 연결한 원본입니다. 원본 경로가 없으면 자료를 준비해야 합니다. 합성을 사용했다면 결과에도 표시합니다. 모델 호출 전 사용할 계정과 모델, 예상 비용을 확인하고 허용하지 않은 실행은 시작하지 않습니다.

연결 이론: [8. 도구와 승인, 재관측](<../../../00_문서/공통강의/08_도구와 승인, 재관측/이론덱.md>). 아래 행동에 필요한 설명은 이 문서에도 있으므로 이론을 보지 않았어도 현재 단계부터 읽습니다.

## 제안과 실행 사이에 사람의 결정을 둡니다

만들 결과: **다섯 도구·중단 가능한 흐름·사람 승인·정확한 버전 기록·동일 입력 재생**

코딩 에이전트는 여러분의 요청으로 코드를 만드는 도구이고, 서비스 에이전트는 서비스 안에서 관측과 근거를 읽는 구성입니다. 오늘은 후자를 연결합니다. 조건 확인·원인 조사·변경 제안·검사·정비 요청·기록 중 무엇을 자동으로 하고 무엇을 사람이 결정할지 먼저 나눠 봅니다.

### 1. 다섯 도구가 같은 약속으로 응답하게 합니다 · 약 25분

MCP는 도구를 공통 방식으로 발견하고 호출하는 규격입니다. 도구가 위험을 대신 판단하지는 않습니다. 업무 도구의 입력·출력과 서버의 권한 검사가 필요합니다.

query_events, search_docs, graph_path, propose_action, record_decision의 입력과 응답 상태를 읽습니다. 기존 API를 감싸는 MCP 서버로 묶고 관측 요청 번호를 유지하도록 명세를 씁니다. 사람 승인 도구는 제공하지 않습니다. 빈 사건·없는 대상·승인되지 않은 결정 기록을 각각 다르게 처리하게 합니다.

**결과를 읽습니다.** 다섯 도구만 노출되고, record_decision 호출만으로 승인 상태가 생기지 않아야 합니다. none을 받은 뒤 원인이 없다고 단정하는 문장이 나오면 응답 계약부터 고칩니다.

**막히면 여기서 확인합니다.** MCP 연결 실패는 도구 결과 없음과 다릅니다. 로컬 주소·포트·API 응답 형식을 먼저 확인합니다.

도구를 준비했으니 언제 어떤 도구를 쓸지 순서를 연결합니다.

합성 관계표의 LOT → 작업일지 → `synthetic:document:FOURM` → `synthetic:document:FIRST`는 조사할 절차를 연결한 교육용 설계입니다. 실제 조건 변경의 증거는 아닙니다. 관계표를 적재한 뒤 끝 대상 ID를 입력합니다.

### 2. 진전이 없으면 멈추는 흐름을 만듭니다 · 약 25분

LangGraph는 상태와 다음 단계를 명시하는 실행 흐름입니다. 체크포인트는 어디까지 진행했는지를 저장합니다. 승인 대기는 잠깐 기다리는 문장이 아니라 재개할 상태가 DB에 남아 있는 것입니다.

사건 조회→관계 경로→문서 근거→세 종류 초안→승인 대기→기록→재생을 연결합니다. 관계 화면에서 실제 끝 대상 ID를 확인하고 입력합니다. 자율성 0은 근거 조회, 1은 조건 변경·초물검사·4M 초안, 2는 소프트웨어 상대 규칙 폭 변경을 사람 승인에 연결합니다. 이는 교육용 정책입니다. 어떤 수준에서도 실제 검사·신고·설비 변경을 수행했다고 표시하지 않습니다. 전체 걸음은 8 이하로 정합니다.

**결과를 읽습니다.** 근거가 부족하면 제안 전에 멈추고, 같은 단계에서 반복하면 종료 이유가 남아야 합니다. thread_id를 저장하고 서버 재시작 뒤 승인 대기가 남는지 실제 수업 실행에서 확인합니다.

**막히면 여기서 확인합니다.** 결정 기록이 두 번 생기면 재개 때 다시 실행되는 노드 안에 부수 효과가 있는지 봅니다. 중단 전 준비와 중단 후 기록을 분리합니다.

이제 사람이 실제로 무엇에 동의하는지 정확히 묶습니다.

### 3. 승인한 바로 그 제안만 기록합니다 · 약 25분

가드레일은 제안 뒤 실행 전에 약속 위반을 확인하는 조건입니다. 버전과 해시는 승인 대상이 바뀌지 않았는지 확인하는 표식입니다. 승인 버튼을 눌렀다는 사실만으로 모든 미래 제안을 승인한 것이 아닙니다.

사람 승인 화면에서 제안의 대상·기존 값·새 값·근거·버전·해시를 읽습니다. 별도 승인 토큰으로 승인 또는 반려하고 이름과 이유를 남깁니다. 에이전트 화면에서 같은 thread_id와 proposal_id로 재개합니다. 승인 전 규칙이 바뀌지 않는지, 오래된 버전이면 다시 판단을 요구하는지 확인합니다.

**결과를 읽습니다.** 승인·기록·규칙 변경이 같은 제안을 가리켜야 합니다. 같은 재개를 반복해도 변경이 한 번만 기록됩니다. 표 질문의 후속 문맥은 원천을 바꾸면 초기화하고 이전 필터를 몰래 적용하지 않습니다.

**막히면 여기서 확인합니다.** 승인 토큰을 서비스 모델이나 도구 인자로 보내지 않습니다. 승인 후 실패라면 결정 저장 여부와 재생 실패를 나눠 읽습니다.

한 바퀴가 끝났는지 통지 수 하나가 아니라 요청 전체로 확인합니다.

### 4. 기록을 따라 한 바퀴를 설명합니다 · 약 25분

폐루프는 관측→판단→조치→다시 관측의 연결입니다. 이 수업의 조치는 교육용 규칙 갱신과 동일 입력 재생입니다. 실제 설비를 제어하거나 생산 품질 개선을 검증한 것은 아닙니다.

요청 관측에서 어떤 단계가 모델이고 어떤 단계가 코드인지 찾아봅니다. 변경 전후 규칙 버전과 같은 입력의 경보 수를 비교합니다. 초안 묶음 번호로 ‘초물검사만 보기’를 눌러 같은 대상의 일부 초안을 다시 읽습니다. ‘8D로 읽기’에서 관측·검토안·승인된 규칙 변경·미확인 효과를 구분합니다. 통합반은 이번 변경을 배포본에 반영하는 마지막 절차도 진행합니다.

**결과를 읽습니다.** 통지 수 변화와 품질 개선을 구분할 수 있어야 합니다. 자신이 정한 사람 판단 지점이 실제 승인 화면과 같은지 설명하고, 내 PBL에 옮길 때 바뀔 대상과 도구를 말해 봅니다.

**막히면 여기서 확인합니다.** 재생이 실패했으면 결정까지 취소됐다고 가정하지 않습니다. 서버 기록의 실제 상태를 읽고 이어서 할 작업을 정합니다.

다음 주제로 옮길 때 남는 것은 함수 이름보다 자료·근거·권한·확인의 약속입니다.

## 다른 데이터에서도 쓸 수 있는 능력을 확인합니다

만들 결과: **새 원천 연결, 제조 가정 수정, 다른 주제의 작은 서비스와 사용 설명**

오늘은 정해진 화면을 똑같이 만드는 날이 아닙니다. 같은 기술로 다른 문제를 해결하는 것이 목적입니다. 힌트를 늘리기보다 무엇이 작동하고 무엇이 아직 안 되는지 스스로 구분합니다.

### 5. 새 원천의 기능 전제를 읽습니다 · 약 25분

이식은 입력 자료를 바꿔도 기존 기능이 성립하는지 확인하는 일입니다. 파일을 읽을 수 있다는 사실만으로 라벨·시간·관계가 필요한 모든 기능을 쓸 수 있는 것은 아닙니다.

기업에서 제공받은 사용 가능한 자료 또는 공개 자료 한 벌을 고릅니다. 없다면 제공한 transfer 자료부터 시작합니다. mapping의 원천·열·키·단위·라벨·문서 상태를 작성하고 data_check를 실행합니다. 기능별 됨·안 됨·부분과 이유를 읽습니다.

**결과를 읽습니다.** 준비되지 않은 기능을 합성 값으로 채워 초록으로 만들지 않습니다. 실제 파일과 설정이 맞는지, 없는 전제가 무엇인지 구분할 수 있어야 합니다.

**막히면 여기서 확인합니다.** 경로 오류와 데이터에 없는 개념을 구분합니다. 이 블록은 정답 구현 힌트 없이 자신의 기준으로 진행합니다.

읽을 수 있는데도 실패하는 기능에서 숨은 가정을 찾습니다.

### 6. 데이터에 묶인 가정을 고칩니다 · 약 25분

전이는 배운 판단 방법을 다른 문제에 적용하는 일입니다. 제조용 ‘LOT’는 도서관의 ‘대출’과 같은 개념이 아닙니다. 이름만 바꾸면 의미가 달라진 계산이 그대로 남을 수 있습니다.

표 질문·그래프·규칙 중 새 원천에서 깨지는 기능 하나를 고릅니다. 코드의 고정 열 번호, LOT 접두어, 단위, 기준값 중 어떤 가정 때문인지 찾습니다. 명세와 관련 검사를 먼저 바꾸고 수정 전후를 비교합니다.

**결과를 읽습니다.** 새 주제에서 맞는 기능과 제조에서만 맞는 기능이 구분되어야 합니다. 기존 제조 기능도 유지할 필요가 있다면 원천별 설정으로 나누고 관련 검사를 확인합니다.

**막히면 여기서 확인합니다.** 모든 제조 단어를 일괄 치환하지 않습니다. 같은 단어라도 UI 표현인지 계산 조건인지 먼저 가릅니다.

이제 다른 주제의 실제 질문과 기준을 넣습니다.

### 7. 표·문서·규칙을 새 문제로 연결합니다 · 약 25분

서비스의 규칙은 데이터 숫자에서 저절로 나오지 않습니다. 도서관의 연장 가능 여부는 대출 기간뿐 아니라 규정과 상태가 필요합니다. 없는 정보는 부족하다고 말하는 기능도 결과물입니다.

books·loans와 규정 문서를 읽고 해결할 질문 하나를 정합니다. 예를 들어 어떤 대출이 확인 대상인지, 연장 가능 판단에 무엇이 더 필요한지 묻습니다. 열 사전·관계·문서·질문셋을 새 목적에 맞춰 바꿉니다. 제공 days_from_due는 설계된 기준일 대비 값이며 오늘 날짜가 아닙니다.

**결과를 읽습니다.** 모든 기록은 가상임을 표시하고, 필요한 기준일이나 상태가 없으면 확정 답변을 내지 않습니다. 대규모 스키마 검색 카드는 표가 많아질 때의 다음 학습 방향으로만 읽습니다.

**막히면 여기서 확인합니다.** 한 번에 서비스 전체를 옮기기 어렵다면 사용자가 할 수 있는 한 작업을 끝까지 연결합니다. 연결하지 않은 기능은 설명에서 제외합니다.

마지막에는 다른 사람이 사용할 수 있게 결과를 설명합니다.

### 8. 내 서비스의 범위와 다음 한 걸음을 말합니다 · 약 25분

사용 설명은 구현한 함수 목록보다 누가 어떤 상황에서 무엇을 할 수 있는지 알려 주는 글입니다. 잘 안 되는 조건과 더 필요한 자료를 함께 쓰면 다음 개발의 출발점이 됩니다.

README에 사용자·상황·입력·행동·확인할 결과·제한을 적습니다. ‘나는 무엇을 만들었고, 누가 언제 쓰며, 무엇이 어려웠고 어떻게 풀었으며, 무엇은 더 필요한가’를 자신의 사례로 설명합니다. 완성 화면이 다른 학생과 같을 필요는 없습니다.

**결과를 읽습니다.** 실제로 만든 기능과 예정 기능을 나눠 설명할 수 있어야 합니다. 다른 주제에서 그대로 쓴 약속과 고친 가정을 각각 보여 주면 됩니다. 추가 노트 제출 형식은 없습니다.

**막히면 여기서 확인합니다.** 작동하지 않은 부분을 숨긴 긴 기능 목록보다 확인한 작은 동선을 구체적으로 설명합니다.

이 결과가 개인 PBL의 첫 버전입니다. 다음에는 새 사용자의 질문으로 명세를 다시 고칩니다.

## 오늘 만든 것을 이어갈 준비 · 20분

참고 완성본과 화면이나 코드가 같을 필요는 없습니다. 원하는 입력과 결과가 연결되고, 근거와 한계를 설명할 수 있는지 확인합니다. 별도 회고문 제출이나 정해진 모양의 개인 노트는 요구하지 않습니다.
