## 미래 값을 예측하되 실제 수명을 지어내지 않습니다

만들 결과: **C-MAPSS RUL 기준 실험, 샷 임계 도달 예측, 불확실성 비교와 정비 판단의 범위**

RUL은 Remaining Useful Life, 정한 고장 기준까지 남은 수명입니다. 고장에 도달한 기록과 그 기준이 있어야 정답을 만들 수 있습니다. 사출 샷 자료에 그런 이력이 없다면 미래 쿠션 값의 임계 도달과 실제 고장 수명을 구분합니다.

### 1. 수명 정답이 있는 다른 자료에서 방법을 봅니다 · 약 25분

C-MAPSS는 항공엔진 열화 시뮬레이션 자료입니다. 장비별 마지막 사이클과 현재 사이클의 차이로 학습 RUL을 만들고, 평가 장비의 마지막 관측 뒤 남은 사이클 정답으로 확인합니다. 다른 도메인에서 방법을 배우는 실험입니다.

공식 자료의 train·test·RUL 파일을 mapping 경로에 준비합니다. FD001처럼 부분집합 하나와 센서 위치를 선택하고 RUL 분석을 실행합니다. 장비 ID와 정답을 입력 특징에서 제외하고 평가 장비가 학습 장비와 섞이지 않게 합니다.

**결과를 읽습니다.** MAE·RMSE의 단위는 cycle이며 사출 장비의 시간이나 잔여 샷 수가 아닙니다. 평가 장비 수와 정답 수가 맞아야 합니다.

**막히면 여기서 확인합니다.** 원본 파일이 없으면 이 블록의 실행을 미준비로 둡니다. 샷 합성 자료의 마지막 행을 고장 시점으로 가정해 대신 실행하지 않습니다.

방법을 배웠으니 우리 자료에서 실제로 답할 수 있는 질문으로 좁힙니다.

### 2. 임계에 도달할 샷 순서를 예측합니다 · 약 25분

Chronos의 미래 값에서 임계를 처음 넘는 위치를 찾으면 예측 범위 내 도달 순서를 얻습니다. 범위 안에서 넘지 않는 경우는 무한 수명이나 안전이 아니라 그 범위에서 도달 예측이 없다는 뜻입니다.

합성 변화 구간의 입력 끝과 임계값·방향을 정합니다. 분석 화면에서 threshold를 선택하고 중앙 예측·하한·상한의 도달 위치를 읽습니다. 원본의 완만한 변화에도 같은 질문을 하되 장기 마모의 증거가 없다는 제한을 함께 표시합니다.

**결과를 읽습니다.** 가로축은 다음 샷 순서입니다. null 도달 값을 0 또는 고장 없음으로 바꾸지 않습니다. 합성에서 관찰한 결과를 원본 설비 성능으로 보고하지 않습니다.

**막히면 여기서 확인합니다.** 모든 곡선이 바로 넘으면 입력 마지막 값이 이미 임계 밖인지 확인합니다. 기준을 결과에 맞춰 바꾸지 않습니다.

이 결과가 정비 요청을 뒷받침하려면 무엇이 더 필요한지 연결합니다.

### 3. 정비 계획과 관측 근거를 분리합니다 · 약 25분

예측은 판단 자료이고 정비 계획은 비용·가동 일정·검사 결과를 포함한 결정입니다. 예측 하나로 부품 교체 시점을 확정하면 빠진 전제가 많습니다.

예측 결과→대상 부품 또는 원천 관계를 정합니다. 작업일지의 실제 검사 기록이 있는 경우에만 대조하고, 없는 검사 결과를 새로 만들지 않습니다. 정비 계획 초안에는 예측 범위·확인할 검사·결정할 사람을 구분합니다.

**결과를 읽습니다.** 관측·예측·사람 결정이 서로 다른 항목으로 보입니다. C-MAPSS 결과에 사출 LOT 출처가 붙지 않아야 합니다.

**막히면 여기서 확인합니다.** 부품과 연결할 근거가 없으면 원천 수준의 결과로 남깁니다. 근거 없는 부품 이름을 그래프에 넣어 구체적으로 보이게 하지 않습니다.

한 번의 예측이 얼마나 흔들리는지도 확인합니다.

### 4. 입력 구간을 바꾸고 불확실성을 읽습니다 · 약 25분

예측 구간은 모델이 내놓은 분위수 범위입니다. 실제 값이 그 안에 몇 퍼센트 들어가는지는 별도 검증이 필요합니다. 입력 구간을 조금 바꿨을 때 결론이 뒤집히면 결정에 더 신중해야 합니다.

같은 목표 구간에 대해 학습에 제공하는 과거 길이를 두 가지로 정합니다. 중앙 예측과 범위 폭, 임계 도달의 변화가 보이게 비교합니다. ‘현장에 보여 준다면 어떤 제한 문구와 추가 검사로 설명할까’를 자신의 결과로 답합니다.

**결과를 읽습니다.** 예측값만큼 범위가 넓거나 도달 여부가 뒤집히면 그 불안정성을 숨기지 않습니다. 고장 확률을 추정할 근거가 없는 구현에서는 확률 숫자를 만들지 않습니다.

**막히면 여기서 확인합니다.** 비교의 목표 구간 자체가 달라졌는지 확인합니다. 입력 끝을 바꾸면서 서로 다른 미래를 같은 예측이라고 비교하지 않습니다.

다음에는 수집·감지·예측을 한 서비스에서 같은 상태 계약으로 연결합니다.

## 여러 기능을 하나의 확인 가능한 시스템으로 잇습니다

만들 결과: **명세·계획·할 일과 연결된 수집·감지·예측 흐름, 단계 실패 검사, 요청 단위 관측**

기능 버튼 세 개가 있다고 시스템이 연결된 것은 아닙니다. 같은 입력이 어느 단계를 거쳤고 어디서 멈췄는지 읽을 수 있어야 합니다. 오늘은 명세→계획→할 일→구현→확인을 한 번에 연결합니다.

### 5. 계획에 책임과 확인 기준을 적습니다 · 약 25분

spec은 원하는 행동, plan은 현재에서 그 행동으로 가는 구조와 책임, tasks는 실행할 일과 완료 근거입니다. 파일 세 개를 만드는 것이 목적이 아니라 바꿀 범위와 확인 방법을 함께 정하는 것입니다.

현재 수집·규칙·예측의 입력과 출력을 에이전트에게 읽게 합니다. 새 흐름을 spec에, 담당 모듈과 데이터 이동을 plan에, 확인할 결과를 tasks에 적습니다. 화면·로그·작은 검사 중 어떤 근거가 각 할 일에 맞는지 선택합니다.

**결과를 읽습니다.** ‘구현한다’만 있는 할 일을 실제로 무엇이 보이면 끝인지 바꿉니다. 모델 실행이 필요한 증거와 문법 검사만으로 가능한 증거를 구분합니다.

**막히면 여기서 확인합니다.** 에이전트가 현재 코드에 없는 동작을 설명하면 해당 파일과 주소를 확인하게 합니다. 계획 문장의 완료 시제를 사실로 받아들이지 않습니다.

가장 중요한 단계 실패 조건부터 연결합니다.

### 6. 한 단계가 비면 전체 완료를 멈춥니다 · 약 25분

시스템의 성공은 필요한 단계가 모두 계약을 만족한 상태입니다. 선택적으로 제외한 단계와 실행하다 실패한 단계를 같은 회색으로 가리지 않습니다.

행이 없는 입력, 기준 구간 부족, 예측 모델 미준비 중 하나를 선택합니다. 해당 단계가 insufficient 또는 failed로 끝나고 뒤 단계가 실행되지 않는 검사를 요청합니다. 정상 입력과 실패 입력을 각각 하나씩 둡니다. 예측 최소 입력 길이는 명세와 config에서 하나로 관리합니다.

**결과를 읽습니다.** 마지막 함수가 종료됐다는 이유만으로 전체 초록이 되지 않습니다. 입력 부족과 시스템 오류의 이유가 구분됩니다.

**막히면 여기서 확인합니다.** 검사에서 모델을 호출할 필요가 없다면 단계 경계만 확인합니다. 이 검사를 실제 예측 성공 증거로 쓰지 않습니다.

상태를 정했으니 화면과 관측 기록에 같은 의미로 보이게 합니다.

### 7. 요청 하나를 처음부터 끝까지 읽습니다 · 약 25분

관측은 서비스 안에서 어떤 단계가 얼마의 입력을 받아 무엇을 냈는지 남기는 일입니다. 요청 번호가 같아야 여러 기록을 한 실행으로 이어 읽을 수 있습니다.

한 실행의 적재·감지·예측 결과를 같은 화면에 놓고 단계마다 규칙 계산·모델 추론·사람 판단을 표시합니다. 요청 관측에서 단계·시간·입출력 수·모델명을 확인합니다. 키와 문서 원문 전체는 관측용으로 남기지 않습니다.

**결과를 읽습니다.** 실패한 단계가 어디인지 화면과 로그가 일치해야 합니다. 모델 호출이 없는 단계의 비용을 실제 0원 측정처럼 표시하지 않습니다.

**막히면 여기서 확인합니다.** 기록이 여러 요청에 섞이면 요청 번호가 중간 도구에서 바뀌는지 봅니다. 총 소요 시간만으로 모델이 느렸다고 단정하지 않습니다.

연결 뒤에도 앞서 얻은 결과가 유지되는지 확인합니다.

예측을 같은 실행에 묶으려면 `forecast.json`에 선택 LOT·열 번호·horizon을 넣도록 요청합니다. `uv run --env-file .env python scripts/reload.py --profile synthetic --source shots --rule cushion-relative --predict forecast --parameters forecast.json`으로 연결할 수 있습니다. 예측을 요청하지 않은 상태와 요청한 예측의 실패를 구별합니다.

### 8. 앞선 비교를 완료 근거로 다시 읽습니다 · 약 25분

통합하면 입력 필터나 상태 전달이 바뀔 수 있습니다. 개별 버튼에서 얻은 결과가 새 흐름에서 같은 조건인지 확인하는 것이 통합 검토입니다.

규칙·추세 비교와 임계 예측에서 사용한 입력을 고정합니다. 통합 흐름의 결과와 차이가 있다면 필터·분할·모델 설정을 먼저 대조합니다. tasks에는 실제 확인한 근거와 미확인 범위를 나눠 적습니다.

**결과를 읽습니다.** 완료 체크는 결과가 존재할 때만 합니다. 자료나 모델이 준비되지 않은 항목은 구현 파일이 있어도 실행 확인 대기로 둡니다.

**막히면 여기서 확인합니다.** 수치를 맞추려고 이전 기록을 바꾸지 않습니다. 조건 차이가 있으면 그 이유를 남깁니다.

다음에는 이 사건에 관련된 문서 근거를 서비스에 붙입니다.

## 오늘 만든 것을 이어갈 준비 · 20분

현재 폴더와 실행 설정을 저장하고 오늘 확인한 대표 입력을 다시 찾을 수 있게 둡니다. 아직 실행하지 않은 모델이나 부족한 자료는 성공 결과로 바꾸지 않습니다. 다음 시간에는 자기 프로젝트를 이어가거나 그날 출발본으로 합류할 수 있습니다.

참고 완성본과 화면이나 코드가 같을 필요는 없습니다. 원하는 입력과 결과가 연결되고, 근거와 한계를 설명할 수 있는지 확인합니다. 별도 회고문 제출이나 정해진 모양의 개인 노트는 요구하지 않습니다.
