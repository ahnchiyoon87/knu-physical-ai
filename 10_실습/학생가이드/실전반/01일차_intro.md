# 실전반 1일차 · 숫자에 뜻을 붙여 첫 서비스를 만듭니다

## 0:00–0:20 · 오늘 작업을 엽니다

오늘은 완성된 앱을 실행하는 날이 아닙니다. 출발본에는 폴더·계약·자료가 있고 앱 코드는 없습니다. 코딩 에이전트가 코드를 쓰고, 여러분은 질문과 확인 기준을 정합니다. 화면의 모양은 달라도 됩니다. 어떤 자료에서 무엇을 계산했는지가 보여야 합니다.

ESNS에서 오늘 공개된 Drive 링크의 **실01-start**와 이 가이드를 받습니다. 잘 이어지는 자기 프로젝트가 있으면 그것을 씁니다. 출발본은 이전 단계의 코드이므로 오늘 기능은 직접 요청해 만듭니다. 내 작업이 막혔다면 기존 폴더는 보존하고 출발본을 새 폴더에 풉니다. 두 폴더에 같은 서버를 동시에 띄우지 않습니다.

VS Code에서 오늘 작업 폴더를 열고 README의 실행 순서를 확인합니다. 이미 만든 서비스는 연결 확인에서 서버·DB 상태를 읽고, 오늘 필요한 원천 파일과 모델 준비 여부를 따로 확인합니다. 첫날 코드 없는 뼈대에서는 아직 앱 화면이 없는 것이 맞습니다. 설치가 남았다면 아래 네 문서 중 해당 단계만 마칩니다.

- [Google Cloud 세팅](../../../실습가이드핸즈온문서/1_GoogleCloud세팅.pdf)
- [VS Code와 코딩 에이전트](../../../실습가이드핸즈온문서/2_VSCode설치및_코딩에이전트세팅.pdf)
- [Docker 설치](../../../실습가이드핸즈온문서/3_도커설치및세팅.pdf)
- [실습 의존성 설치](../../../실습가이드핸즈온문서/4_실습의존성설치.pdf)

설치 뒤의 서버·자료 연결은 [실행 연결 안내](../실행_연결_안내.md)에 모았습니다. 이 문서는 설치 프로그램 설명을 반복하지 않고 실제 프로젝트의 실행과 오류 위치를 이어 줍니다.

자료를 선택할 때 synthetic은 교육용 합성, kamp는 직접 연결한 KAMP 원본입니다. 원본을 선택했는데 파일이 없으면 원본 경로를 먼저 준비합니다. 합성을 썼다면 결과에도 합성이라고 표시합니다. 특정 LOT의 실제 숫자가 가이드와 같아야 통과하는 수업은 아닙니다.

## 0:20–1:10 · 한 행을 읽고 첫 화면을 부탁합니다

사출의 샷은 한 번의 성형 동작입니다. LOT는 함께 관리하는 생산 묶음입니다. 이 자료의 LOT는 시각이 아니라 No_Shot이 0으로 돌아오는 경계에서 붙인 번호입니다. 숫자 22는 열 번호이고, 쿠션이라는 뜻과 mm라는 단위는 열 사전에서 읽습니다.

**지금 해 볼 일**

data의 입력과 mapping.json을 열어 한 행·쿠션 열·순서 열을 찾아봅니다. 에이전트에게 파일을 읽는 화면과 원천별 적재 기능을 자신의 말로 요청하세요. raw 파일은 보존하고 화면에서 원천 이름·행 수·열의 뜻·단위를 볼 수 있게 합니다. 코드 문법을 직접 채우는 과제는 아닙니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

화면에 교육용 합성인지 원본인지 표시되고, 같은 파일을 다시 넣어도 행 수가 늘지 않아야 합니다. 파일이 없으면 없다고 나와야 합니다. 파일 경로만 존재하는 설정을 적재 성공으로 읽지 마세요.

**막혔을 때**

파일을 못 읽으면 앱 전체를 다시 만들지 말고 선택한 원천 ID, mapping의 path, 파일 첫 줄 순서로 에이전트와 확인합니다.

표를 열 수 있어도 질문의 뜻을 잘못 읽을 수 있습니다. 다음에는 같은 표를 자연어로 묻습니다.

### 첫날 질문 10개

아래 질문을 그대로 답안처럼 외우지 않고 하나씩 자신의 말로 묻습니다. 어느 질문에 조건이 부족한지도 판단합니다. 샷·조건표·작업일지를 함께 쓰는 질문은 관련 원천을 모두 선택해야 합니다.

1. 실제 사출 압력이 가장 높은 샷 10개는?
2. 배럴 온도 네 구간 평균은?
3. LOT별 쿠션 평균은?
4. 평균 쿠션이 가장 낮은 LOT는?
5. 계량시간 평균은?
6. 데이터 마지막 LOT 기준 최근 다섯 LOT의 사이클 평균은?
7. 배압의 최댓값은?
8. 불량이 많은 LOT는?
9. 조건표의 기준과 다른 LOT는?
10. 쿠션이 8 mm 미만인 샷은 몇 개인가?

답을 평가할 때 **맞음 / 틀림 / 근거 없이 지어냄 / 답변 실패·조건 부족**을 구분합니다. 열 사전 없이 만든 첫 버전과 사전·정찰·관계를 하나씩 추가한 버전을 같은 질문으로 비교합니다. 번호 출력은 존재하지 않는 열을 코드가 거절하기 쉽게 만들 뿐 의미를 맞힌다는 보장은 아닙니다.

## 1:10–2:00 · 그럴듯한 답을 표와 대조합니다

LLM은 문장을 이어 만드는 모델입니다. SQL은 표에서 필요한 행을 고르고 계산하는 문장입니다. 모델에게 계산값을 외워 답하게 하지 않고 SQL을 만들게 하되, 실행 가능하다는 사실과 질문에 맞다는 사실을 나눠 봅니다.

**지금 해 볼 일**

질문셋의 첫 질문 하나를 골라 자기 말로 바꿉니다. 선택한 원천에서 SQL을 만들고 읽기 전용으로 실행하는 질문 칸을 요청하세요. 먼저 결과표와 SQL을 함께 봅니다. 질문 10개를 한꺼번에 맡기지 말고 하나씩 대상·범위·계산을 확인합니다. 답을 확신할 수 없는 질문도 포함합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

쿠션을 물었는데 다른 위치 열을 쓰거나 LOT별 질문에 전체 평균 하나만 내면 오답입니다. 정답 문장 암기가 아니라 사용한 열·묶음·단위가 맞는지 봅니다. 조건이 없는 질문은 추가 조건이 필요하다고 나와도 좋습니다.

**막혔을 때**

모델 연결 오류는 추론 능력 평가가 아닙니다. 공급자 이름·주소·JSON 응답 지원부터 확인합니다. 키는 화면 캡처나 질문 내용에 넣지 않습니다.

틀린 답 하나를 찾았으면 요청 전체를 길게 쓰기 전에, 어떤 정보가 빠졌는지 가릅니다.

## 2:00–2:50 · 열 이름 추측을 열 사전으로 바꿉니다

열 사전은 이름·뜻·단위·근거를 한데 둔 설명표입니다. 모델이 뜻을 추측하는 대신 이 사전을 읽게 합니다. 모델은 등록된 열 번호를 선택하고 코드는 실제 열로 연결합니다. 번호가 있다고 의미까지 맞는 것은 아닙니다.

**지금 해 볼 일**

방금 틀린 질문을 그대로 남기고 열 뜻과 단위를 전달하도록 요청을 한 번 바꿉니다. Injection_Pressure_Real_Time을 압력으로 읽었는지, Screw_Position과 Minimum_Cushion을 서로 다른 값이라고 여겼는지 확인합니다. 모르는 단위는 빈 추측으로 메우지 않습니다. 이후 실제 LOT 수를 조회한 결과도 질문 입력에 연결합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

수정 전후에 같은 질문을 사용합니다. 좋아진 항목과 여전히 불확실한 항목을 구분하면 됩니다. 모델이 사전에 없는 열 번호를 냈을 때 SQL을 실행하지 않는지도 확인합니다.

**막혔을 때**

모든 뜻을 한 번에 다시 쓰기보다 틀린 열 하나의 원문 근거부터 확인합니다. 사전 자체가 틀렸으면 모델 프롬프트만 고쳐서는 해결되지 않습니다.

뜻을 아는 표가 생겼습니다. 이제 표와 작업 기록이 어떻게 연결되는지 지도로 옮깁니다.

## 2:50–3:40 · 관계 한 줄을 추가하고 길을 읽습니다

온톨로지는 이 서비스에서 무엇을 어떤 대상으로 부르고 어떻게 연결할지 정한 약속입니다. 관계표의 한 줄은 출발 대상·관계 이름·도착 대상·근거입니다. 선이 있다는 이유만으로 원인이 증명되지는 않습니다.

**지금 해 볼 일**

ontology의 관계표에서 샷 원천, LOT, 조건표, 작업일지를 찾아봅니다. 자기 질문에 필요한 관계 한 줄을 정하고, 화면에 두 대상을 연결한 경로를 보여 달라고 요청합니다. 교육용 LOT 4와 작업일지의 관계를 먼저 읽습니다. 원본을 사용할 때는 실제 자료에서 확인한 LOT 번호로 바꿉니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

관계의 양 끝 ID가 실제 대상과 같고 출처가 표시되어야 합니다. 존재하지 않는 대상을 물었을 때 빈 경로를 고장 원인으로 설명하면 안 됩니다. 오늘 만든 표 질문과 관계 화면을 각각 한 번 설명해 봅니다.

**막혔을 때**

선이 안 보이면 그래프 색이나 배치보다 두 ID의 철자·프로필 접두어·적재 여부를 먼저 확인합니다.

데이터를 연결했지만 깨끗한지는 아직 모릅니다. 다음 단계는 이상한 숫자를 지우기 전에 뜻부터 확인하는 일입니다.
