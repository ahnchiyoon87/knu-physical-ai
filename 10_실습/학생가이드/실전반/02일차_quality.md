# 실전반 2일차 · 이상한 값을 지우기 전에 구분합니다

오늘 만들 것: **원천을 보존하면서 결측·0·음수·범위 의심을 구분하는 품질 카드와 검수한 열 뜻**

## 0:00–0:20 · 오늘 작업을 엽니다

지난번 서비스에서 표 사전과 질문을 엽니다. 원천을 보존한다는 말은 오류를 그냥 둔다는 뜻이 아닙니다. 원본, 해석 규칙, 화면에 사용하는 값의 관계를 남겨 같은 결과를 다시 설명할 수 있게 하려는 것입니다.

ESNS에서 오늘 공개된 Drive 링크의 **실02-start**와 이 가이드를 받습니다. 잘 이어지는 자기 프로젝트가 있으면 그것을 씁니다. 출발본은 이전 단계의 코드이므로 오늘 기능은 직접 요청해 만듭니다. 내 작업이 막혔다면 기존 폴더는 보존하고 출발본을 새 폴더에 풉니다. 두 폴더에 같은 서버를 동시에 띄우지 않습니다.

VS Code에서 오늘 작업 폴더를 열고 README의 실행 순서를 확인합니다. 이미 만든 서비스는 연결 확인에서 서버·DB 상태를 읽고, 오늘 필요한 원천 파일과 모델 준비 여부를 따로 확인합니다. 첫날 코드 없는 뼈대에서는 아직 앱 화면이 없는 것이 맞습니다. 설치가 남았다면 아래 네 문서 중 해당 단계만 마칩니다.

설치 뒤의 서버·자료 연결은 [실행 연결 안내](../실행_연결_안내.md)에 모았습니다. 이 문서는 설치 프로그램 설명을 반복하지 않고 실제 프로젝트의 실행과 오류 위치를 이어 줍니다.

자료를 선택할 때 synthetic은 교육용 합성, kamp는 직접 연결한 KAMP 원본입니다. 원본을 선택했는데 파일이 없으면 원본 경로를 먼저 준비합니다. 합성을 썼다면 결과에도 합성이라고 표시합니다. 특정 LOT의 실제 숫자가 가이드와 같아야 통과하는 수업은 아닙니다.

## 0:20–1:10 · 품질을 한 숫자로 뭉개지 않습니다

결측은 값이 비어 있는 상태이고 0은 값입니다. 0이 정지 기록인지 센서 오류인지는 열의 뜻과 기록 조건을 봐야 알 수 있습니다. 최댓값도 큰 값이라는 관측일 뿐 삭제 사유는 아닙니다.

**지금 해 볼 일**

품질 화면에 전체 행 수와 열별 결측·0·음수·최소·최대 건수를 요청합니다. 원본 열 하나를 골라 화면 숫자와 직접 대조하세요. 품질 점수를 만든다면 분모와 감점 항목을 먼저 한 문장으로 정하고 구성 항목도 함께 보이게 합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

화면의 건수와 원천의 집계가 맞고, 무엇을 의심으로 표시했는지 설명할 수 있어야 합니다. 0과 결측을 합친 숫자 하나만 있으면 다시 나눕니다.

**막혔을 때**

수치 열이 문자로 읽혔다면 쉼표·공백·인코딩을 확인합니다. 바뀐 값이 있다면 변환 규칙을 남기고 원본을 덮지 않습니다.

의심을 표시했으니, 이제 화면에 사용할 값을 만드는 규칙을 정합니다.

## 1:10–2:00 · 정제한 보기와 원본을 나란히 둡니다

뷰는 저장된 원본을 어떤 규칙으로 읽을지 정한 표의 보기입니다. 원본을 삭제하지 않고 정제 기준을 비교할 수 있습니다. 표시와 제외는 서로 다른 결정입니다.

**지금 해 볼 일**

음수 쿠션, 오류 코드, 라벨 표기 중 실제 입력에 존재하는 사례 하나를 고릅니다. 자료에 없는 오류를 관측했다고 만들지 마세요. 어떤 값은 표시만 할지, 어떤 집계에서만 제외할지 에이전트와 명세로 정합니다. 원본 건수·제외 건수·남은 건수를 같은 카드에 보이게 합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

원본 행 수는 그대로이고, 정제 전후 차이의 이유가 설명되어야 합니다. 의심값을 제외한 결과가 질문의 범위를 바꿨다면 답 옆에도 표시합니다.

**막혔을 때**

정제 뒤 값이 너무 깨끗하면 제외 조건이 넓은지 먼저 봅니다. 결측을 0으로 채운 뒤 평균이 달라진 경우도 별도로 확인합니다.

한 원천의 규칙을 다른 원천에 그대로 쓰면 어디서 깨지는지 비교합니다.

## 2:00–2:50 · 서로 다른 기록의 품질을 비교합니다

센서값과 검사 라벨은 만들어진 과정이 다릅니다. Y/N과 0/1은 겉모양만 다를 수도 있지만 무엇이 불량인지 정의가 다르면 같은 라벨이 아닙니다. 분포 차이는 수집 과정과 함께 읽습니다.

**지금 해 볼 일**

샷 원천과 분류용 원천을 각각 선택합니다. 원본 KAMP 두 벌이 준비됐다면 실제 검사 라벨을, 합성 프로필이면 생성 규칙 라벨을 명확히 표시합니다. 기계·제품 구분 열이 있는 입력에서만 필터를 추가합니다. 전체와 필터 뒤의 분모를 같이 보여 달라고 요청합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

두 원천의 품질 카드가 같은 정의로 비교되는지 봅니다. 원본 2020 자료의 알려진 통계와 다르다면 실제 파일 버전·필터를 확인하고 숫자를 맞추려고 행을 버리지 않습니다.

**막혔을 때**

선택한 파일에 기계·제품 열이 없다면 기능을 만들지 말고 필요한 자료로 표시합니다. 합성 입력이 원본의 품질 문제를 재현했다고 주장하지 않습니다.

통계는 값의 모양을 보여 줍니다. 열의 뜻은 어디서 가져올지 마지막으로 확인합니다.

정제 뷰를 실제 분석에 쓰기로 했다면 코딩 에이전트에게 mapping.json의 해당 원천에 `analysis_view: "clean"`을 지정하도록 요청합니다. 정제 뷰를 먼저 만든 뒤 서버를 다시 시작하면 질문·곡선·감지가 같은 정제 뷰를 읽습니다. `raw`는 원본 뷰입니다. 정제 뷰가 없으면 오류를 반환하며 원본으로 조용히 대신하지 않습니다.

## 2:50–3:40 · 모델이 쓴 열 뜻을 근거로 검수합니다

모델이 매끄럽게 쓴 설명도 근거가 없으면 사전에 채택하지 않습니다. 채우는 자리를 좁힌다는 것은 열 번호·뜻·원문 인용을 정한 형식으로 받고, 원문에 없는 뜻은 비워 두게 하는 것입니다.

**지금 해 볼 일**

뜻을 아직 확정하지 않은 열 2~3개와 설명서의 관련 문장을 고릅니다. 모델에 뜻 초안을 요청하되 열 번호를 바꾸지 못하게 합니다. 인용이 원문에 실제로 있는지는 코드로, 인용이 그 뜻을 지지하는지는 사람이 확인하게 요청합니다. 맞음·틀림·지어냄·빈칸을 구분합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

근거 없는 뜻이 자동 저장되지 않아야 합니다. 비어 있는 단위를 임의로 채우지 않고, 채택한 뜻 옆에는 확인한 출처가 남습니다.

**막혔을 때**

설명서 원문이 없으면 뜻 생성 실험을 잠시 멈추고 미확인 열로 남깁니다. 파일명이나 열 이름만으로 정답을 만들지 않습니다.

품질을 확인한 숫자를 이제 눈으로 비교합니다. 다음에는 축과 범위가 설명의 일부가 됩니다.
