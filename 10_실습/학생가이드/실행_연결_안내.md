# 설치 다음에 프로젝트를 연결하는 순서

이 문서는 기존 네 설치 PDF를 마친 뒤 사용하는 안내입니다. 일차 출발본의 README가 오늘 기능 범위를 정합니다. 첫날은 앱 코드가 없는 뼈대이므로 아래 서버 명령도 학생이 앱을 만든 뒤에 사용합니다. 이후 일차는 들어 있는 코드로 연결한 뒤 오늘 기능을 추가합니다.

## 1 · 작업 위치부터 맞춥니다

VS Code의 탐색기 맨 위가 오늘 사용할 프로젝트 폴더인지 확인합니다. 터미널도 같은 폴더에서 엽니다. `constitution.md`와 `mapping.json`이 보이면 프로젝트 루트입니다. 기존 작업을 이어갈 때는 기존 폴더를 사용하고, 출발본으로 합류할 때는 새 폴더를 사용합니다.

`.env.example`을 `.env`로 한 번 복사합니다. 이미 `.env`가 있으면 덮지 않습니다. 토큰·DB 암호·모델 키는 이 파일에서만 설정하고 공유 자료에 넣지 않습니다. `.env`를 바꾼 뒤에는 실행 중인 서버를 종료하고 다시 시작해야 반영됩니다.

## 2 · 표와 그래프 저장소를 시작합니다

Docker 엔진이 준비됐는지 확인한 뒤 로컬 Supabase를 시작합니다. Supabase는 PostgreSQL 데이터베이스와 관리 도구를 묶은 환경입니다. 여기에는 표와 문서 벡터가 들어갑니다.

```powershell
npx supabase@2.117.0 init
npx supabase@2.117.0 start
```

`supabase/config.toml`이 이미 있으면 init은 생략합니다. start가 표시하는 DB 주소를 DATABASE_URL에 넣습니다. READONLY_DATABASE_URL은 같은 DB를 사용하는 lab_reader 계정의 주소입니다. 별도 암호를 정하고, 아래 bootstrap이 계정과 읽기 권한을 만듭니다. 학생에게 DB 관리 SQL을 직접 쓰게 하는 과제는 아닙니다.

그래프 DB가 필요한 일차에는 `.env`의 NEO4J_PASSWORD를 정하고 다음을 실행합니다.

```powershell
docker compose up -d graph
```

Neo4j는 관계를 저장합니다. 같은 Docker 안에 보이더라도 Supabase와는 다른 저장소입니다. graph_data 볼륨은 로컬 재시작에서 관계를 보존합니다. 강제로 볼륨을 삭제하지 않습니다.

## 3 · 오늘 필요한 패키지를 설치합니다

처음에는 기본 패키지와 검사 도구만 설치합니다.

```powershell
uv sync --frozen --extra dev
uv run --env-file .env python scripts/bootstrap.py
```

규칙 파일이 포함된 출발본에서는 `uv run --env-file .env python scripts/seed_rules.py`로 최초 규칙을 등록합니다. 이 명령은 기존 규칙을 덮지 않습니다. 참고 코드의 기본 규칙은 합성 자료용 교육 기준입니다.

표 분류·PyOD·Chronos·비전 일차에는 models, RAG에는 documents, 평가에는 evaluation extra가 필요합니다. 같은 서비스에서 여러 기능을 유지할 때 필요한 extra를 함께 지정합니다.

```powershell
uv sync --frozen --extra models --extra documents --extra evaluation --extra dev
```

이 전체 명령은 모든 기능을 사용하는 일차에만 필요합니다. 설치는 모델 추론과 다릅니다. 공개 모델 파일도 자동으로 준비됐다고 가정하지 않습니다. RAG용 모델 준비는 프로젝트 README의 cache_models 순서를, 열화상은 해당 일차의 prepare_thermal·prepare_vision_weights 안내를 따릅니다.

## 4 · 화면과 서버를 엽니다

```powershell
npm.cmd --prefix frontend ci
npm.cmd --prefix frontend run build
uv run --env-file .env python scripts/serve.py
```

브라우저에서 `http://localhost:8000`을 엽니다. 연결 설정에 SERVICE_TOKEN을 입력합니다. 브라우저를 새로 열면 토큰을 다시 넣습니다. 이 구성은 토큰을 브라우저 영구 저장소에 남기지 않습니다.

화면을 수정하며 바로 보고 싶으면 frontend 폴더의 별도 터미널에서 `npm.cmd run dev`를 실행하고 `http://localhost:5173`을 엽니다. 백엔드 서버는 계속 켜 둡니다. 종료는 서버 터미널에서 Ctrl+C입니다.

## 5 · 준비됨의 범위를 읽습니다

연결 확인의 server가 ok면 HTTP 서버가 응답한 것입니다. database가 ok면 읽기 전용 연결의 작은 질의가 성공한 것입니다. 모델 호출·그래프 관계·문서 검색·오늘 실습 전체가 됐다는 뜻은 아닙니다.

이제 자료 프로필을 고르고 원천·열 사전 보기를 누릅니다. synthetic은 제공한 교육용 합성 자료, kamp는 직접 준비한 원본, transfer는 도서관 자료입니다. 원천 ID를 선택해 적재하고 상태와 행 수를 읽습니다. 모델 질문 전에 이 과정이 먼저입니다.

모델을 사용할 때만 실제 공급자 주소·이름·키를 설정하고 ALLOW_MODEL_CALLS=true로 켭니다. 준비된 사내 모델이 없으면 internal 경로는 미준비 상태입니다. 실패 시 API로 자동 우회하지 않습니다. 수업에서 선택한 저비용 모델과 지원 응답 형식을 확인합니다.

## 6 · 막힌 지점을 짧게 찾습니다

| 보이는 현상 | 먼저 볼 것 | 다음 한 걸음 |
|---|---|---|
| 주소가 열리지 않음 | 서버 터미널의 첫 오류와 포트 | 다른 폴더 서버를 종료하고 이 프로젝트 하나만 실행 |
| 401 | 화면 서비스 토큰 | 로컬 SERVICE_TOKEN과 같은지 확인 |
| 403 승인 | 사람 승인 토큰 | 서비스 토큰과 별개인 APPROVER_TOKEN 사용 |
| 파일 없음 | 프로필·원천 ID·mapping 경로 | 실제 파일을 연결하거나 준비 안 됨으로 남김 |
| DB 오류 | Supabase 상태·reader 계정·스키마 | bootstrap 단계의 실제 성공 여부 확인 |
| 모델 호출 꺼짐 | ALLOW_MODEL_CALLS | 실행할 모델·비용을 선택한 뒤 명시적으로 설정 |
| 모델 파일 없음 | 해당 모델 준비 단계 | 다운로드 의도를 정하고 사전 준비 후 다시 실행 |
| SQL 심사 실패 | 대상·범위·계산·의미 | 첫 실패 항목을 질문·결과표와 대조 |
| 근거 없음 | 문서 현행 상태·인덱스·검색 조각 | 근거가 필요한 질문인지 먼저 확인 |

에이전트에게 원인 확인을 부탁할 때는 현재 입력, 기대한 동작, 실제 상태, 요청 번호를 함께 줍니다. 모든 코드를 다시 만들거나 실패한 사실을 지우지 않습니다. 이 순서로 연결한 뒤 오늘 가이드의 첫 블록으로 진행합니다.
