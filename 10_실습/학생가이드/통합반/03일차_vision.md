## 0:00–0:20 · 오늘 작업을 엽니다

열화상 입력은 예쁜 사진이 아니라 온도 수치 배열입니다. 제공 원자료 설명은 837개·256×320·양품 616·불량 221을 제시하지만 실제 파일을 읽어 대조해야 합니다. 원본이 없으면 다른 사진으로 결과를 꾸며 만들지 않습니다. 입력 변환과 분할 명세를 먼저 준비할 수 있습니다.

ESNS에서 오늘 공개된 Drive 링크의 **통03-start**와 이 가이드를 받습니다. 잘 이어지는 자기 프로젝트가 있으면 그것을 씁니다. 출발본은 이전 단계의 코드이므로 오늘 기능은 직접 요청해 만듭니다. 내 작업이 막혔다면 기존 폴더는 보존하고 출발본을 새 폴더에 풉니다. 두 폴더에 같은 서버를 동시에 띄우지 않습니다.

VS Code에서 오늘 작업 폴더를 열고 README의 실행 순서를 확인합니다. 이미 만든 서비스는 연결 확인에서 서버·DB 상태를 읽고, 오늘 필요한 원천 파일과 모델 준비 여부를 따로 확인합니다. 첫날 코드 없는 뼈대에서는 아직 앱 화면이 없는 것이 맞습니다. 설치가 남았다면 아래 네 문서 중 해당 단계만 마칩니다.

- [Google Cloud 세팅](../../../실습가이드핸즈온문서/1_GoogleCloud세팅.pdf)
- [VS Code와 코딩 에이전트](../../../실습가이드핸즈온문서/2_VSCode설치및_코딩에이전트세팅.pdf)
- [Docker 설치](../../../실습가이드핸즈온문서/3_도커설치및세팅.pdf)
- [실습 의존성 설치](../../../실습가이드핸즈온문서/4_실습의존성설치.pdf)

설치 뒤의 서버·자료 연결은 [실행 연결 안내](../실행_연결_안내.md)에 모았습니다. 이 문서는 설치 프로그램 설명을 반복하지 않고 실제 프로젝트의 실행과 오류 위치를 이어 줍니다.

자료를 선택할 때 synthetic은 교육용 합성, kamp는 직접 연결한 KAMP 원본입니다. 원본을 선택했는데 파일이 없으면 원본 경로를 먼저 준비합니다. 합성을 썼다면 결과에도 합성이라고 표시합니다. 특정 LOT의 실제 숫자가 가이드와 같아야 통과하는 수업은 아닙니다.

## 0:20–1:10 · 모든 이미지에 같은 온도 기준을 씁니다

각 이미지의 최소·최대로 색을 따로 늘리면 같은 온도가 서로 다른 밝기가 됩니다. 공통 범위로 표현하고 잘린 값이 있으면 표시해야 비교가 가능합니다. 좌·우 제품은 서로 다른 모양이므로 분리합니다.

**지금 해 볼 일**

원본 설명과 실제 CSV 모양을 확인합니다. scripts/prepare_thermal.py의 help를 읽고 row_index·id·label·split·side가 있는 라벨 파일을 준비합니다. 전체 공통 온도 최소·최대를 정해 변환하고, 변환 기록의 행 수·범위·클리핑 수와 매니페스트를 읽습니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

한 샘플이 81,920개 값과 연결되고 같은 ID가 두 번 들어가지 않아야 합니다. 원본 열 순서를 바꾸거나 임의로 회전해 보기 좋은 모양으로 만들지 않습니다.

**막혔을 때**

81,920열이 아니면 인덱스·헤더가 들어 있는지 원자료 형식을 먼저 확인합니다. 크기를 맞추려고 값을 임의 삭제하지 않습니다.

표현을 고정했으니 학습과 평가의 이미지를 나눕니다.

## 1:10–2:00 · 정상만 학습하고 검증으로 임계를 정합니다

PaDiM은 정상 이미지의 특징 분포를 학습하고 다른 모습을 이상 점수로 표현합니다. 분류 정답을 모두 학습하는 방식과 다릅니다. 검증은 기준을 고르는 자료, 평가는 그 기준을 마지막으로 확인하는 자료입니다.

**지금 해 볼 일**

같은 이미지가 분할 사이에 중복되지 않게 train·validation·test를 고릅니다. train에는 정상만 둡니다. 사전에 준비한 특징 추출기 가중치를 명시해 PaDiM을 CPU로 실행합니다. 임계값을 바꿀 때 평가 자료를 반복해 맞추지 말고 검증 자료에서 놓침·오탐 비용을 비교합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

학습 정상 수와 검증·평가의 두 라벨 수가 보이고, 기준 선택에 평가 정답을 사용하지 않아야 합니다. 이상 점수가 높다는 것을 불량 확률 90%처럼 표현하지 않습니다.

**막혔을 때**

메모리나 시간이 부족하면 좌우를 섞거나 평가 데이터를 줄인 사실을 숨기지 않습니다. 명세에서 정한 작은 검토 범위로 줄였다면 그 범위를 표시합니다.

결과가 어느 제품의 어느 쪽인지 관계로 남깁니다.

## 2:00–2:50 · 이미지 결과를 제품 측면에 연결합니다

표의 LOT와 이미지의 제품 ID는 서로 대응하는 키가 있어야 연결할 수 있습니다. 원자료에 그 키가 없다면 억지로 연결하지 않는 것이 올바른 설계입니다.

**지금 해 볼 일**

이미지 ID·제품 측면·분할·점수·임계 판정을 저장합니다. 그래프에는 열화상 결과→제품 측면으로 연결하고 LOT 관계는 만들지 않습니다. 원래 온도 표현과 이상 점수를 함께 읽을 수 있는 결과 화면을 요청합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

좌우가 섞이지 않고, 임계값을 바꾼 결과도 같은 이미지로 추적되어야 합니다. 열지도에서 밝은 곳을 실제 고장 위치로 확정하지 않습니다.

**막혔을 때**

결과가 저장됐는데 이미지가 없으면 서버의 로컬 파일 경로와 브라우저 제공 경로를 구분합니다. 경로를 텍스트로 보여 주는 것만으로 이미지 표시 완료라고 하지 않습니다.

같은 평가 조건을 유지한 채 방법 하나를 바꿔 봅니다.

PatchCore는 정상 특징의 대표 집합과 가까운지를 비교합니다. 방법이 달라도 입력 표현과 분할이 달라지면 모델 차이만 볼 수 없습니다. 실행 시간과 저장 공간도 선택 기준입니다.

**지금 해 볼 일**

같은 좌측 또는 우측 자료, 동일 분할로 두 방법의 결과를 비교합니다. 준비·학습·평가 시간을 구분하고 실제 측정값만 씁니다. 반복한 정리 절차를 자신의 leave-notes 스킬로 만들어 보고 다음 작업에서도 필요한 결과를 찾아주는지 확인합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

더 나은 점수 하나보다 어느 조건에서 무엇을 선택할지 설명합니다. 두 방법 중 하나를 실행하지 못했으면 그 칸은 미실행으로 남깁니다.

**막혔을 때**

기본 임계와 사람이 조정한 임계가 섞이지 않았는지 먼저 봅니다. 같은 이름의 가중치라도 입력 변환이 다르면 비교 조건이 아닙니다.
