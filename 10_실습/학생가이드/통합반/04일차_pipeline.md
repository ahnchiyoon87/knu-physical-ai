# 통합반 4일차 · 새 입력이 와도 같은 절차로 확인합니다

## 0:00–0:20 · 오늘 작업을 엽니다

파이프라인은 적재→검사→감지처럼 순서가 있는 처리입니다. 매번 버튼을 누르는 일을 줄이되 중간이 비었을 때 다음으로 넘어가지 않아야 합니다. 통합반은 출발본에 들어 있는 규칙 화면을 먼저 읽습니다. absolute는 LOT 조건표의 기준 ±폭, relative는 LOT 앞 200행 평균 대비 변화율입니다.

ESNS에서 오늘 공개된 Drive 링크의 **통04-start**와 이 가이드를 받습니다. 잘 이어지는 자기 프로젝트가 있으면 그것을 씁니다. 출발본은 이전 단계의 코드이므로 오늘 기능은 직접 요청해 만듭니다. 내 작업이 막혔다면 기존 폴더는 보존하고 출발본을 새 폴더에 풉니다. 두 폴더에 같은 서버를 동시에 띄우지 않습니다.

VS Code에서 오늘 작업 폴더를 열고 README의 실행 순서를 확인합니다. 이미 만든 서비스는 연결 확인에서 서버·DB 상태를 읽고, 오늘 필요한 원천 파일과 모델 준비 여부를 따로 확인합니다. 첫날 코드 없는 뼈대에서는 아직 앱 화면이 없는 것이 맞습니다. 설치가 남았다면 아래 네 문서 중 해당 단계만 마칩니다.

- [Google Cloud 세팅](../../../실습가이드핸즈온문서/1_GoogleCloud세팅.pdf)
- [VS Code와 코딩 에이전트](../../../실습가이드핸즈온문서/2_VSCode설치및_코딩에이전트세팅.pdf)
- [Docker 설치](../../../실습가이드핸즈온문서/3_도커설치및세팅.pdf)
- [실습 의존성 설치](../../../실습가이드핸즈온문서/4_실습의존성설치.pdf)

설치 뒤의 서버·자료 연결은 [실행 연결 안내](../실행_연결_안내.md)에 모았습니다. 이 문서는 설치 프로그램 설명을 반복하지 않고 실제 프로젝트의 실행과 오류 위치를 이어 줍니다.

자료를 선택할 때 synthetic은 교육용 합성, kamp는 직접 연결한 KAMP 원본입니다. 원본을 선택했는데 파일이 없으면 원본 경로를 먼저 준비합니다. 합성을 썼다면 결과에도 합성이라고 표시합니다. 특정 LOT의 실제 숫자가 가이드와 같아야 통과하는 수업은 아닙니다.

## 0:20–1:10 · 한 명령 안에서 단계별 상태를 봅니다

단계 계약은 들어올 입력과 나가야 할 결과의 조건입니다. ‘프로그램 종료’와 ‘필요한 단계 성공’을 구분합니다. 같은 파일을 다시 넣어도 중복되지 않는 성질을 멱등성이라고 합니다.

**지금 해 볼 일**

적재·규칙 감지·그래프 반영을 하나의 reload 명령으로 묶는 명세를 씁니다. 입력 해시, 읽은 행, 저장한 사건, 반영 대기 수를 요청 번호로 연결하게 합니다. 같은 파일을 다시 넣었을 때 import 기록은 재사용하되 필요한 다음 단계가 무엇인지는 명시하게 합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

입력과 설정이 같으면 중복 사건이 늘지 않고, 그래프 반영이 남으면 남은 수가 보입니다. 한 단계 실패 뒤 다음 단계의 성공 표시가 만들어지지 않아야 합니다.

**막혔을 때**

전체가 실패했다는 문장만 보이면 첫 실패 단계와 이유를 보여 달라고 요청합니다. 로그에는 키나 원문 전체 대신 단계와 개수를 남깁니다.

정상 입력 다음에는 일부러 전제 하나가 없는 입력을 넣어 봅니다.

## 1:10–2:00 · 빈 설정을 이상 없음으로 읽지 않습니다

입력이 없거나 기준이 없으면 계산할 수 없습니다. insufficient는 계산이 완료된 none과 다릅니다. 이 차이는 화면의 색보다 먼저 응답 계약에 있어야 합니다.

**지금 해 볼 일**

별도의 새 폴더에서 조건이 누락된 교육용 입력을 만듭니다. cushion-absolute는 해당 LOT의 조건표 행이 없거나 적용 행이 여러 개이면 멈춰야 합니다. 어떤 개정을 쓸지 정하지 않고 임의의 한 행을 고르지 않습니다. 실패 조건 하나와 정상 조건 하나를 검사로 만들도록 요청합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

설정 누락을 0이나 기본값으로 바꾸지 않습니다. 조건을 채운 뒤 같은 요청을 다시 실행할 수 있고, 이전 실패 기록은 그대로 남아야 합니다.

**막혔을 때**

검사가 항상 초록이면 어떤 입력을 바꿨는지 확인합니다. 구현과 같은 문장을 반복하는 검사 대신 누락 시 다음 단계가 실행되지 않는지 봅니다.

데이터 흐름을 믿을 수 있게 했으니 다른 감지 방법을 연결합니다.

## 2:00–2:50 · 현재 분포와 미래 예측을 나눠 봅니다

PyOD의 이상 점수는 기준 분포와 얼마나 다른지 나타내고, Chronos는 과거 값에서 다음 값을 예측합니다. 이상 점수는 불량 확률이 아니고, 미래 예측을 현재 정답과 섞어 학습하면 비교가 무너집니다.

**지금 해 볼 일**

분석 화면에서 한 LOT·쿠션 열·기준 행 수를 정해 PyOD를 실행합니다. 학습 앞 구간과 평가 뒤 구간을 분리합니다. Chronos는 같은 LOT에서 예측할 마지막 부분을 따로 남기고 과거 구간만 입력하도록 명세를 작성합니다. 모델 준비와 CPU 실행 시간은 실제로 관측한 값을 사용합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

방법마다 사용 구간·점수 뜻·실행 시간이 보여야 합니다. 예측이 불가능한 짧은 구간을 자동으로 다른 모델에 넘기지 않습니다.

**막혔을 때**

가중치가 없으면 모델 파일 준비 문제입니다. 다운로드를 허용할지 정한 뒤 준비하고, 추론 중 공급자를 바꿔 성공처럼 만들지 않습니다.

방법 이름보다 어떤 변화를 찾고 놓쳤는지 비교합니다.

예측을 같은 실행에 묶을 때는 원하는 분석 설정을 JSON 파일로 저장하도록 에이전트에게 요청합니다. 예를 들어 `forecast.json`에 선택 LOT·열 번호·horizon을 넣고 `uv run --env-file .env python scripts/reload.py --profile synthetic --source shots --rule cushion-relative --predict forecast --parameters forecast.json`을 실행합니다. `--predict`를 빼면 예측을 요청하지 않은 실행이며, 요청한 예측이 실패하면 감지 완료와 예측 부족을 나눠 반환해야 합니다.

## 2:50–3:40 · 같은 사례의 비교표를 읽습니다

비교하려면 입력·구간·기준을 맞춰야 합니다. 정답 라벨이 없는 실제 자료에서는 참·거짓 경보를 확정할 수 없습니다. 합성 자료에서는 심어 둔 변화와 비교할 수 있지만 현장 성능으로 일반화할 수 없습니다.

**지금 해 볼 일**

급변·완만한 변화·변화를 넣지 않은 구간을 골라 규칙과 모델의 결과를 나란히 둡니다. 잡은 구간·놓친 구간·통지 수·실행 시간을 표시합니다. 합성의 생성 조건을 아는 평가와 원본에서의 탐색 결과를 표에서 분리합니다.

에이전트에게 줄 요청은 자신의 말로 씁니다. 원하는 행동과 무엇을 보면 됐다고 할지를 전달하고, 나온 이해가 다르면 바로잡습니다. 구현 문법을 직접 완성할 필요는 없습니다.

**됐는지 확인합니다**

가장 높은 숫자 하나로 승자를 정하지 않고, 어떤 입력에서 어떤 방법을 쓸지 이유를 설명하면 됩니다. 다음 단계에 넘길 것은 확정 원인이 아니라 근거가 붙은 의심 사건입니다.

**막혔을 때**

서로 다른 행 수를 비교했다면 점수 해석을 멈추고 범위를 맞춥니다. 누락된 실행은 0점이나 0초가 아니라 미실행으로 둡니다.

숫자는 변화를 알려 줍니다. 그때 무엇을 확인해야 하는지는 문서에서 찾습니다.
