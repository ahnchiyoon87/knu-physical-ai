## 좋아졌다는 말을 같은 질문으로 확인합니다

만들 결과: **기대 근거 질문셋, RAGAS 4지표·계약 검사, 모델별 관측, 라우터와 회귀 검사**

평가는 모델에게 ‘잘했니?’라고 묻는 일이 아닙니다. 질문, 기대 근거, 허용할 응답 상태를 먼저 정하고 결과와 대조합니다. 정답 문장을 외우게 하지 않고 문서의 어느 부분이 답을 지지하는지 정합니다.

[RAG 질문 20개](../../학생가이드/자료/RAG_질문20.json)와 [내 질문 작성틀](../../학생가이드/자료/내_질문30_작성틀.json)을 준비합니다. 빈 질문으로 평가하지 않고 자기 질문과 기대 근거를 넣습니다.

### 1. 질문셋을 직접 구성합니다 · 약 50분

질문셋은 반복 비교의 기준입니다. RAGAS는 답의 근거 충실성, 질문 관련성, 검색 근거의 정확성·포괄성을 나눠 봅니다. 이 점수도 모델 심사 결과이므로 사람의 검토를 없애지 않습니다.

제공 형식에서 질문 30개를 작성하거나 준비한 초안을 고칩니다. 답할 수 있는 것·문서에 없는 것·구판 유도·여러 근거가 필요한 것을 섞습니다. expected_documents와 reference는 실제 문서를 읽고 적습니다. scripts/eval.py의 help를 읽고 먼저 적은 수로 실행 범위를 확인한 뒤 같은 파일로 평가합니다.

**결과를 읽습니다.** 질문 파일 해시·모델·실행 번호·상태·근거가 결과에 남아야 합니다. 계약 검사와 RAGAS 4개 점수를 같은 종류의 정답률로 합치지 않습니다.

**막히면 여기서 확인합니다.** 평가 도구 import 오류와 낮은 답변 점수를 구분합니다. 설치가 실패한 질문을 오답으로 채우거나 실행하지 않은 점수를 만들어 넣지 않습니다.

점수가 낮은 질문을 같은 이유끼리 묶어 한 원인부터 고칩니다.

### 2. 현행 문서와 요청 비용을 함께 봅니다 · 약 50분

구판 배제는 문장이 비슷한지보다 문서의 상태를 보는 일입니다. 컨텍스트는 한 요청에 들어가는 지시·질문·근거의 전체 입력입니다. 상한을 넘었다고 조용히 뒷부분을 자르면 무엇을 근거로 답했는지 달라집니다.

COND-A와 COND-B의 상태가 다른 것을 확인합니다. 같은 질문에서 구판이 근거로 나오지 않는지 봅니다. API·사내 모델을 비교할 수 있다면 같은 질문 파일을 사용하고 호출 수·입출력 토큰·지연·비용을 나란히 놓습니다. 한 모델이 준비되지 않았으면 미실행으로 둡니다.

**결과를 읽습니다.** 화면에 실제 응답 모델이 표시되고 가격 미설정은 미측정으로 남아야 합니다. 입력을 줄였다면 무엇을 뺐는지와 점수 변화를 같이 확인합니다. 문자 상한을 모델의 실측 컨텍스트 길이라고 부르지 않습니다.

**막히면 여기서 확인합니다.** 응답이 잘렸다면 입력과 출력 상한, 공급자의 종료 상태를 봅니다. 다른 비싼 모델로 자동 전환하지 않습니다.

이제 질문을 받았을 때 어느 종류의 근거부터 찾을지 정합니다.

### 3. 표·문서·관계 중 필요한 길을 고릅니다 · 약 50분

라우터는 질문을 처리할 경로를 고르는 단계입니다. LOT별 수는 표 집계, 절차는 문서, 두 대상의 연결은 그래프가 적합할 수 있습니다. 경로를 골랐다는 사실과 충분한 답을 얻었다는 사실을 구분합니다.

세 종류 질문을 하나씩 정해 에이전트 화면의 라우팅을 요청합니다. 선택한 경로와 이유를 표시하고 각 경로의 응답 계약을 그대로 유지하게 합니다. 그래프 질문에는 출발·도착 대상이 필요합니다. 대상을 모르면 임의 ID를 만들지 말고 부족한 조건을 물어보게 합니다.

**결과를 읽습니다.** 라우터가 선택한 경로가 로그에 남고, 빈 결과가 정상 판정으로 바뀌지 않아야 합니다. 답의 근거가 표·조항·경로 중 무엇인지 구분할 수 있어야 합니다.

**막히면 여기서 확인합니다.** 모든 질문이 문서로 가면 세 질문의 요청과 라우터 선택을 먼저 비교합니다. 정해진 키워드 하나로 정답 경로를 외우게 하는 것이 목적은 아닙니다.

맞아진 동작을 다음 수정에서도 유지할 수 있게 검사로 남깁니다.

### 4. 한 성질을 회귀 검사로 만듭니다 · 약 50분

회귀 검사는 바꾼 뒤 예전에 되던 동작이 깨졌는지 확인합니다. DeepEval 계약 검사는 응답과 근거 형식을 확인하고, 모델 의미 심사는 별도입니다. 검사 이름만으로 범위를 넓혀 해석하지 않습니다.

‘구판을 인용하지 않는다’, ‘근거가 없으면 거절한다’, ‘잘못된 근거 번호를 공개하지 않는다’ 중 성질 하나를 골라 verify-property 스킬을 만듭니다. 정상 예와 실패 예를 함께 검사하게 합니다. 검색 설정 하나를 바꾼 후 관련 검사와 같은 질문셋을 다시 읽습니다.

**결과를 읽습니다.** 무엇을 검증했고 무엇을 검증하지 않았는지 검사 결과 옆에 설명할 수 있어야 합니다. 캐시·대규모 스키마 검색 카드는 필요한 상황을 이해하는 읽기 자료이며 오늘 의무 구현은 아닙니다.

**막히면 여기서 확인합니다.** 검사만 통과하고 사람이 본 답이 틀리면 기대 조건이 좁은지 봅니다. 의미 검토 결과를 검사 초록으로 덮지 않습니다.

찾고 설명하는 서비스가 준비됐습니다. 다음에는 실행 전에 사람의 판단을 받습니다.

## 오늘 만든 것을 이어갈 준비 · 20분

현재 폴더와 실행 설정을 저장하고 오늘 확인한 대표 입력을 다시 찾을 수 있게 둡니다. 아직 실행하지 않은 모델이나 부족한 자료는 성공 결과로 바꾸지 않습니다. 다음 시간에는 자기 프로젝트를 이어가거나 그날 출발본으로 합류할 수 있습니다.

참고 완성본과 화면이나 코드가 같을 필요는 없습니다. 원하는 입력과 결과가 연결되고, 근거와 한계를 설명할 수 있는지 확인합니다. 별도 회고문 제출이나 정해진 모양의 개인 노트는 요구하지 않습니다.
