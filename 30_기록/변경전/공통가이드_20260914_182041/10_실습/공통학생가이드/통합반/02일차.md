## 이상한 값을 지우기 전에 구분합니다

만들 결과: **원천을 보존하면서 결측·0·음수·범위 의심을 구분하는 품질 카드와 검수한 열 뜻**

지난번 서비스에서 표 사전과 질문을 엽니다. 원천을 보존한다는 말은 오류를 그냥 둔다는 뜻이 아닙니다. 원본, 해석 규칙, 화면에 사용하는 값의 관계를 남겨 같은 결과를 다시 설명할 수 있게 하려는 것입니다.

### 1. 품질을 한 숫자로 뭉개지 않습니다 · 약 25분

결측은 값이 비어 있는 상태이고 0은 값입니다. 0이 정지 기록인지 센서 오류인지는 열의 뜻과 기록 조건을 봐야 알 수 있습니다. 최댓값도 큰 값이라는 관측일 뿐 삭제 사유는 아닙니다.

품질 화면에 전체 행 수와 열별 결측·0·음수·최소·최대 건수를 요청합니다. 원본 열 하나를 골라 화면 숫자와 직접 대조하세요. 품질 점수를 만든다면 분모와 감점 항목을 먼저 한 문장으로 정하고 구성 항목도 함께 보이게 합니다.

**결과를 읽습니다.** 화면의 건수와 원천의 집계가 맞고, 무엇을 의심으로 표시했는지 설명할 수 있어야 합니다. 0과 결측을 합친 숫자 하나만 있으면 다시 나눕니다.

**막히면 여기서 확인합니다.** 수치 열이 문자로 읽혔다면 쉼표·공백·인코딩을 확인합니다. 바뀐 값이 있다면 변환 규칙을 남기고 원본을 덮지 않습니다.

의심을 표시했으니, 이제 화면에 사용할 값을 만드는 규칙을 정합니다.

### 2. 정제한 보기와 원본을 나란히 둡니다 · 약 25분

뷰는 저장된 원본을 어떤 규칙으로 읽을지 정한 표의 보기입니다. 원본을 삭제하지 않고 정제 기준을 비교할 수 있습니다. 표시와 제외는 서로 다른 결정입니다.

음수 쿠션, 오류 코드, 라벨 표기 중 실제 입력에 존재하는 사례 하나를 고릅니다. 자료에 없는 오류를 관측했다고 만들지 마세요. 어떤 값은 표시만 할지, 어떤 집계에서만 제외할지 에이전트와 명세로 정합니다. 원본 건수·제외 건수·남은 건수를 같은 카드에 보이게 합니다.

**결과를 읽습니다.** 원본 행 수는 그대로이고, 정제 전후 차이의 이유가 설명되어야 합니다. 의심값을 제외한 결과가 질문의 범위를 바꿨다면 답 옆에도 표시합니다.

**막히면 여기서 확인합니다.** 정제 뒤 값이 너무 깨끗하면 제외 조건이 넓은지 먼저 봅니다. 결측을 0으로 채운 뒤 평균이 달라진 경우도 별도로 확인합니다.

한 원천의 규칙을 다른 원천에 그대로 쓰면 어디서 깨지는지 비교합니다.

### 3. 서로 다른 기록의 품질을 비교합니다 · 약 25분

센서값과 검사 라벨은 만들어진 과정이 다릅니다. Y/N과 0/1은 겉모양만 다를 수도 있지만 무엇이 불량인지 정의가 다르면 같은 라벨이 아닙니다. 분포 차이는 수집 과정과 함께 읽습니다.

샷 원천과 분류용 원천을 각각 선택합니다. 원본 KAMP 두 벌이 준비됐다면 실제 검사 라벨을, 합성 프로필이면 생성 규칙 라벨을 명확히 표시합니다. 기계·제품 구분 열이 있는 입력에서만 필터를 추가합니다. 전체와 필터 뒤의 분모를 같이 보여 달라고 요청합니다.

**결과를 읽습니다.** 두 원천의 품질 카드가 같은 정의로 비교되는지 봅니다. 원본 2020 자료의 알려진 통계와 다르다면 실제 파일 버전·필터를 확인하고 숫자를 맞추려고 행을 버리지 않습니다.

**막히면 여기서 확인합니다.** 선택한 파일에 기계·제품 열이 없다면 기능을 만들지 말고 필요한 자료로 표시합니다. 합성 입력이 원본의 품질 문제를 재현했다고 주장하지 않습니다.

통계는 값의 모양을 보여 줍니다. 열의 뜻은 어디서 가져올지 마지막으로 확인합니다.

정제 뷰를 분석에 쓰려면 mapping.json의 해당 원천에 `analysis_view: "clean"`을 지정하도록 요청합니다. 정제 뷰를 먼저 만든 뒤 서버를 다시 시작합니다. `raw`는 원본입니다. 정제 뷰가 없으면 오류를 드러내며 원본으로 몰래 대신하지 않습니다.

### 4. 모델이 쓴 열 뜻을 근거로 검수합니다 · 약 25분

모델이 매끄럽게 쓴 설명도 근거가 없으면 사전에 채택하지 않습니다. 채우는 자리를 좁힌다는 것은 열 번호·뜻·원문 인용을 정한 형식으로 받고, 원문에 없는 뜻은 비워 두게 하는 것입니다.

뜻을 아직 확정하지 않은 열 2~3개와 설명서의 관련 문장을 고릅니다. 모델에 뜻 초안을 요청하되 열 번호를 바꾸지 못하게 합니다. 인용이 원문에 실제로 있는지는 코드로, 인용이 그 뜻을 지지하는지는 사람이 확인하게 요청합니다. 맞음·틀림·지어냄·빈칸을 구분합니다.

**결과를 읽습니다.** 근거 없는 뜻이 자동 저장되지 않아야 합니다. 비어 있는 단위를 임의로 채우지 않고, 채택한 뜻 옆에는 확인한 출처가 남습니다.

**막히면 여기서 확인합니다.** 설명서 원문이 없으면 뜻 생성 실험을 잠시 멈추고 미확인 열로 남깁니다. 파일명이나 열 이름만으로 정답을 만들지 않습니다.

품질을 확인한 숫자를 이제 눈으로 비교합니다. 다음에는 축과 범위가 설명의 일부가 됩니다.

## 그림과 보고서가 같은 질문에 답하게 합니다

만들 결과: **단위가 맞는 그래프, 항목별 SQL 심사, 출처가 연결된 두 보고서, 내 반복 절차 스킬**

오늘부터 만들기 전에 무엇을 보면 됐다고 할지 적습니다. 명세(spec)는 구현 방법을 길게 지시하는 글이 아니라 원하는 행동과 확인 기준입니다. 예를 들어 ‘쿠션을 보여 줘’보다 ‘LOT를 바꿔도 축 단위와 선택 범위가 보인다’가 확인하기 좋습니다.

### 5. 축부터 정하고 그래프를 만듭니다 · 약 25분

시각 열이 없는 샷 자료를 시간 그래프라고 부르면 안 됩니다. 가로축은 행 또는 샷 순서, 세로축은 값과 단위입니다. LOT 경계를 잇는 선은 서로 다른 생산 묶음을 연속 변화처럼 보이게 할 수 있습니다.

쿠션 열과 LOT 하나를 고르고 그래프의 확인 기준을 spec에 적습니다. 에이전트에게 선택 범위·단위·누락 구간이 보이는 그래프를 요청합니다. 교육용 LOT 4의 급변과 LOT 5의 완만한 변화를 나란히 봅니다. 원본이라면 확인된 LOT 358·92를 사용하되 실제 관측을 먼저 확인합니다.

**결과를 읽습니다.** LOT 경계와 결측을 가로질러 선을 긋지 않아야 합니다. 큰 자료는 범위 선택 또는 다운샘플링 사실을 표시하고, 확대했을 때 원래 행과 대조할 수 있어야 합니다.

**막히면 여기서 확인합니다.** 그래프가 평평하면 잘못된 열, 전체 범위, 단위를 먼저 봅니다. 모양을 극적으로 만들려고 축 범위를 숨기지 않습니다.

그림이 분명해졌지만 질문의 집계가 맞는지는 별도 확인이 필요합니다.

### 6. SQL을 대상·범위·계산·의미로 심사합니다 · 약 25분

루브릭은 답이 지켜야 할 항목별 확인표입니다. SQL이 실행된다는 것과 질문에 맞는다는 것을 분리합니다. UNKNOWN은 애매한 합격이 아니라 아직 판단하지 못했다는 표시입니다.

‘LOT별 쿠션 평균’ 질문의 대상·범위·계산·의미를 먼저 써 봅니다. 모델은 항목마다 PASS/FAIL/UNKNOWN과 이유를 내고, 코드는 통과 여부를 정하도록 요청합니다. 실패하면 실패 항목을 지목한 최소 변경을 한 번 시도하고, 변경 뒤 전체 필수 항목을 다시 확인하게 합니다.

**결과를 읽습니다.** 같은 질문을 반복했을 때 SQL 문자 모양보다 결과와 필수 조건이 같은지 봅니다. 이미 맞았던 LOT 묶음이 수리 과정에서 빠졌다면 개선으로 보지 않습니다. 검사 점수만으로 정답을 확정하지 않습니다.

**막히면 여기서 확인합니다.** 모델 심사가 흔들리면 질문·원천·표본·루브릭 버전을 먼저 고정합니다. 정답을 고정 SQL로 몰래 바꿔 놓고 모델이 나아졌다고 말하지 않습니다.

검토한 수치를 읽는 사람에 맞춰 두 보고서로 옮깁니다.

### 7. 현장과 관리자의 보고서를 나눕니다 · 약 25분

현장 보고서는 어떤 대상에서 무엇을 보고 무엇을 확인할지 담습니다. 관리자 요약은 범위와 중요한 변화, 아직 모르는 것을 짧게 보여 줍니다. 독자는 달라도 숫자의 출처는 같아야 합니다.

리포트 화면에서 원천과 LOT를 정하고 모델 설명 없이 먼저 작성합니다. 행·LOT·규칙 버전별 건수가 코드의 계산으로 나오는지 봅니다. 그다음 근거 번호가 붙은 문장만 모델이 덧붙이게 합니다. 현장 기록 형식과 한 장 요약을 구분하고 현재 화면을 인쇄하여 PDF로 저장합니다.

**결과를 읽습니다.** 두 보고서의 대상과 분모가 같고 출처가 연결되어야 합니다. 원인 미확정은 그대로 남습니다. 규칙 버전별 경보를 더해 고유 불량 수로 부르지 않습니다.

**막히면 여기서 확인합니다.** 설명이 숫자와 다르면 문장을 먼저 보류하고 집계 근거를 확인합니다. 실제 현장 서식이 없으면 교육용 서식이라고 표시합니다.

여러 번 반복한 마무리 절차를 이제 다음 작업에서도 사용할 수 있게 정리합니다.

### 8. 반복 절차를 첫 스킬로 만듭니다 · 약 25분

스킬은 특정 상황에서 수행할 절차와 확인 방법을 적은 안내입니다. 함수명을 잔뜩 적으면 코드가 바뀔 때 깨집니다. 언제 쓰고 무엇을 확인할지를 중심으로 씁니다.

오늘 반복한 결과 정리 또는 리포트 확인 절차를 골라 leave-notes 스킬로 작성해 달라고 요청합니다. 개인 노트 제출은 없습니다. 스킬을 써 보고 싶은 사람은 ‘오늘 작업 정리해 줘’처럼 자신의 표현으로 요청하고 실제 수행 내용을 확인합니다. 과장된 완료 문장이 나오면 확인한 것과 못 확인한 것을 구분하게 고칩니다.

**결과를 읽습니다.** 스킬 파일이 있다는 사실과 코딩 에이전트가 실제로 읽었다는 사실을 나눕니다. 읽은 경로와 수행 결과를 확인합니다. 보고서·그래프·SQL의 같은 대상을 설명할 수 있으면 오늘 목적에 도달했습니다.

**막히면 여기서 확인합니다.** 호스트가 스킬을 자동 발견하지 못하면 파일을 명시해서 읽게 할 수 있습니다. 이를 자동 발견 성공이라고 기록하지 않습니다.

지금은 사람이 그래프를 봐야 이상을 압니다. 다음에는 규칙이 먼저 관측을 표시합니다.
