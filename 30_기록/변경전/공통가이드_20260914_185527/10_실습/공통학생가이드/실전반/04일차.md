## 경보를 만들고 경보가 모르는 것을 찾습니다

만들 결과: **설정으로 바꾸는 규칙과 경보, 통지 억제, LOT와 연결한 사건, 놓친 변화의 설명**

규칙은 ‘이 조건이면 표시한다’는 계산입니다. 고장 원인을 알아낸 것이 아닙니다. 오늘 바꾸는 기준은 교육용 기준입니다. 현장 설정값으로 쓰려면 그 설비의 승인된 조건표가 필요합니다.

참고 구현의 세 규칙은 LOT 조건표 기준 ±1.5 mm, LOT 첫 200행 평균 대비 2.5% 초과 변화, 쿠션 2.5% 초과 상승 AND 계량시간 2.5% 초과 하락입니다. 교육용 기준입니다. 절대 기준은 조건표가 적용되는 모든 행을 비교합니다. 상대·조합 기준은 LOT 첫 200행으로 기준을 만들고 그 뒤의 관측을 판정합니다.

### 1. 세 종류 기준을 같은 입력에 댑니다 · 약 25분

절대 기준은 정해 둔 범위, 상대 기준은 기준 구간에서 얼마나 달라졌는지, 조합 기준은 여러 조건의 결합입니다. 상대 기준의 배수가 표준편차 배수인지 퍼센트인지는 반드시 구분해야 합니다.

먼저 코딩 에이전트에게 세 규칙을 설정 파일과 감지 화면으로 구현하도록 요청합니다. 생성된 rules.json에서 mode·column_id·baseline_count·폭의 뜻을 확인합니다. 샷과 조건표를 먼저 적재한 뒤 감지 화면에서 cushion-absolute, cushion-relative, cushion-combined를 비교합니다. 조합은 같은 LOT·행 번호의 쿠션 상승과 계량시간 하락을 AND로 묶습니다. 한 채널만 변한 경우도 만들어 조합의 뜻을 확인합니다.

**실행 전에 오늘 기능을 만듭니다.** 출발본에는 분류까지 들어 있고 rules.json·seed_rules.py·감지 화면은 오늘 추가합니다. 입력은 synthetic의 shots로 되돌리고 conditions도 먼저 적재합니다. labeled는 어제의 분류표이며 오늘 규칙의 원천이 아닙니다. 쿠션은 열22, 계량시간은 열18, 조건표의 쿠션 기준은 열102입니다. 다른 원본에서는 자기 열 사전을 따릅니다.

세 규칙과 등록 스크립트가 만들어지면 프로젝트 루트에서 `uv run --env-file .env python scripts/seed_rules.py`를 실행합니다. created는 새 규칙 등록, preserved는 기존 규칙 보존입니다. rules.json을 고쳤다고 이미 등록된 규칙이 바뀌지는 않습니다. 서버와 화면을 다시 빌드/시작한 뒤 ‘현재 규칙 보기’로 실제 등록 정의와 버전을 읽고 감지합니다.

절대 기준은 각 LOT 조건표의 기준±1.5 mm를 모든 유효 관측에 댑니다. 상대·조합의 첫200행은 기준을 만드는 구간이고 판정 대상에서 제외합니다. 따라서 규칙별 비교에 포함된 행 범위가 다를 수 있습니다. evaluated 숫자만으로 판정 분모가 같다고 결론내리지 않습니다.

**결과를 읽습니다.** 입력과 규칙 버전이 결과에 남고, 같은 LOT의 기준을 다른 LOT에서 가져오지 않아야 합니다. 기준 구간이 부족하면 판단 부족으로 끝나야 합니다.

**막히면 여기서 확인합니다.** 규칙이 없으면 seed_rules로 최초 규칙을 등록합니다. 기존 규칙은 이 명령으로 덮지 않습니다. 요청 원천과 규칙 원천이 다르면 먼저 선택을 맞춥니다.

조건에 걸린 행 수와 사람이 받는 통지 수를 나눕니다.

### 2. 억제 전후를 같은 분모로 비교합니다 · 약 25분

억제는 비슷한 경보를 매번 통지하지 않는 운영 규칙입니다. 관측을 삭제하는 것이 아닙니다. 경보 100개를 통지 5개로 줄여도 불량이 줄었다고 말할 수 없습니다.

우선순위와 억제 간격을 설정에서 읽게 하고, flagged·notified·suppressed를 화면에 같이 표시하도록 요청합니다. 같은 입력과 규칙으로 억제 전후를 비교합니다. 경보가 확인됐는지 조치됐는지도 관측값과 별도 상태로 표현할 방법을 정합니다.

**비교할 설정 두 개를 보존합니다.** 참고 규칙의 suppression_shots는 10입니다. 억제 없는 비교본은 같은 definition을 복사하고 새 id(예: cushion-relative-no-suppression)와 suppression_shots=0만 바꿔 추가합니다. seed_rules로 새 ID를 등록하고 두 ID의 정의를 다시 읽습니다. 이미 등록된 ID를 덮거나 뒤의 사람 승인 기능을 오늘 사용할 필요는 없습니다.

같은 원천·같은 규칙 계산·같은 행 구간에서 두 결과의 flagged를 비교하고 각 결과의 notified+suppressed=flagged를 확인합니다. 우선순위는 검토 순서를 위한 표시이며 값의 이상 여부를 바꾸는 계수가 아닙니다. 규칙 ID가 다르면 저장 사건의 method도 다릅니다. 이벤트 목록 전체 개수를 합쳐 통지가 두 배가 됐다고 해석하지 않습니다.

**결과를 읽습니다.** 걸린 행 수는 같고 통지·억제의 합이 그 수와 맞아야 합니다. 표시하지 않은 통지도 원래 관측에서 찾을 수 있어야 합니다.

**막히면 여기서 확인합니다.** 통지가 0이면 경보도 0인지, 모두 억제인지, 입력 자체가 없는지 먼저 나눕니다. 빈 화면 하나로 세 상태를 표현하지 않습니다.

통지를 눌렀을 때 어떤 생산 묶음인지 찾아가도록 연결합니다.

### 3. 경보에서 LOT와 작업 기록으로 갑니다 · 약 25분

사건은 값·조건·대상·규칙 버전이 함께 있는 기록입니다. 그래프에 저장하는 것은 이 사건과 대상의 관계입니다. 표 저장과 그래프 저장은 동시에 성공한다는 보장이 없어 반영 대기 기록을 둡니다.

경보를 조회하고 해당 LOT ID를 복사합니다. 오늘은 관계표에서 LOT와 작업일지의 경로를 찾습니다. 이후 그래프 DB 단계에서는 outbox 동기화와 적용 수·남은 수를 확인합니다. 경보를 누르면 같은 LOT의 조건표·일지를 보여 주도록 화면 동선을 확장합니다.

**번호를 관계 대상 ID로 바꿉니다.** 합성 shots의 LOT4라면 시작은 `synthetic:shots:lot:4`, 끝은 `synthetic:worklog:lot:4` 또는 `synthetic:conditions:lot:4`입니다. 숫자4만 입력하지 않습니다. 먼저 관계표를 적재·대조하고 이 ID로 경로를 찾습니다.

오늘 패키지는 Neo4j 동기화 버튼을 제공하지 않습니다. 경보의 graph_status=queued는 나중에 반영할 기록을 만들었다는 뜻입니다. 관계표 경로가 보이는 것과 경보 노드가 그래프 DB에 반영된 것은 별개입니다. 오늘은 사건의 실제 LOT와 관계표 대상이 일치하는지 확인하고, DB 동기화는 RAG 단계에서 추가합니다.

**결과를 읽습니다.** 다른 프로필의 같은 LOT 번호와 섞이지 않아야 합니다. 그래프가 실패해도 표에 저장한 사건을 지우지 않고, 대기 건수가 남아야 합니다.

**막히면 여기서 확인합니다.** 경로가 없으면 사건의 대상 ID와 기존 관계표의 ID를 맞춥니다. 남은 반영이 있는데 완료 표시만 고치지 않습니다.

경보가 있는 사례를 봤으니 이번에는 없는 사례를 읽습니다.

### 4. 잡히지 않은 변화를 설명합니다 · 약 25분

한 번에 크게 벗어나는 급변과 작게 계속 움직이는 추세는 다릅니다. 넓은 고정 범위 안에서 천천히 움직이면 경보가 없을 수 있습니다. 이것은 규칙이 보는 조건의 한계입니다.

급변 LOT와 완만한 변화 LOT를 그래프에서 비교합니다. 교육용 자료는 LOT 4·5를 사용하되 어느 규칙에 실제로 걸렸는지는 화면에서 확인합니다. 특정 결과가 반드시 나오게 기준을 몰래 맞추지 않습니다. 추세를 보려면 어떤 과거 구간과 비교해야 할지 명세 한 줄을 더합니다.

**결과를 읽습니다.** ‘경보 없음’과 ‘정상 확인’을 구분해서 설명할 수 있어야 합니다. 검출하지 못한 변화도 버리지 않고 다음 분석 방법의 입력으로 남깁니다.

**막히면 여기서 확인합니다.** 모든 사례가 잡히면 기준이 너무 민감해졌을 수 있습니다. 정상으로 놓아둔 합성 구간의 통지 수도 같이 봅니다.

다음에는 같은 절차를 새 파일에도 돌리고, 규칙과 추세 방법을 비교합니다.

## 새 입력이 와도 같은 절차로 확인합니다

만들 결과: **단계 계약이 있는 파이프라인, 실패 조건 검사, 규칙·PyOD·Chronos 비교**

파이프라인은 적재→검사→감지처럼 순서가 있는 처리입니다. 매번 버튼을 누르는 일을 줄이되 중간이 비었을 때 다음으로 넘어가지 않아야 합니다. 두 반 모두 오늘 앞에서 만든 규칙 기능을 이 흐름에 연결합니다. absolute는 LOT 조건표의 기준 ±폭, relative는 LOT 앞 200행 평균 대비 변화율입니다.

### 5. 한 명령 안에서 단계별 상태를 봅니다 · 약 25분

단계 계약은 들어올 입력과 나가야 할 결과의 조건입니다. ‘프로그램 종료’와 ‘필요한 단계 성공’을 구분합니다. 같은 파일을 다시 넣어도 중복되지 않는 성질을 멱등성이라고 합니다.

적재·규칙 감지·관계 반영 상태 확인을 하나의 reload 명령으로 묶는 명세를 씁니다. 입력 해시, 읽은 행, 저장한 사건, 반영 대기 수를 요청 번호로 연결하게 합니다. 같은 파일을 다시 넣었을 때 import 기록은 재사용하되 필요한 다음 단계가 무엇인지는 명시하게 합니다.

**먼저 예측 없는 연결을 만듭니다.** 코딩 에이전트에게 현재 적재와 규칙 함수를 순서대로 호출하는 scripts/reload.py를 작성하도록 요청합니다. 조건표 적재와 규칙 등록은 앞 단계에서 마친 상태여야 합니다. 참고 reload는 선택한 shots를 적재하며 conditions를 대신 적재하지 않습니다.

구현 후 프로젝트 루트에서 `uv run --env-file .env python scripts/reload.py --profile synthetic --source shots --rule cushion-relative`로 연결합니다. 최초 적재와 같은 파일 재실행을 구별하고, ingest의 duplicate와 감지 결과를 함께 봅니다. 현재 CSV 단계의 graph.status=not_applicable는 그래프 DB 반영 대상이 아니라는 뜻이며 ‘동기화 성공 0건’으로 바꾸지 않습니다. 이후 Neo4j 단계에서만 applied·remaining을 읽습니다.

파일 내용이나 매핑이 달라진 입력은 같은 source_id로 덮어 적재할 수 없습니다. 새 CSV를 등록하려면 새 원천 ID와 중복되지 않는 table 이름, 그 원천을 가리키는 새 규칙 ID를 정합니다. 이 정책은 기존 결과를 보존하기 위한 것이며 자동 증분 적재를 구현한 것으로 표현하지 않습니다.

**결과를 읽습니다.** 입력과 설정이 같으면 중복 사건이 늘지 않고, 그래프 반영이 남으면 남은 수가 보입니다. 한 단계 실패 뒤 다음 단계의 성공 표시가 만들어지지 않아야 합니다.

**막히면 여기서 확인합니다.** 전체가 실패했다는 문장만 보이면 첫 실패 단계와 이유를 보여 달라고 요청합니다. 로그에는 키나 원문 전체 대신 단계와 개수를 남깁니다.

정상 입력 다음에는 일부러 전제 하나가 없는 입력을 넣어 봅니다.

### 6. 빈 설정을 이상 없음으로 읽지 않습니다 · 약 25분

입력이 없거나 기준이 없으면 계산할 수 없습니다. insufficient는 계산이 완료된 none과 다릅니다. 이 차이는 화면의 색보다 먼저 응답 계약에 있어야 합니다.

별도의 새 폴더에서 조건이 누락된 교육용 입력을 만듭니다. cushion-absolute는 해당 LOT의 조건표 행이 없거나 적용 행이 여러 개이면 멈춰야 합니다. 어떤 개정을 쓸지 정하지 않고 임의의 한 행을 고르지 않습니다. 실패 조건 하나와 정상 조건 하나를 검사로 만들도록 요청합니다.

**누락 사례는 현재 자료를 건드리지 않고 만듭니다.** 에이전트에게 작은 조건표 행 목록을 넣는 검사를 요청하면 DB를 새로 만들지 않고도 누락·중복 조건에서 뒤 단계가 호출되지 않는지 확인할 수 있습니다. 서비스 입력으로 직접 비교하려면 별도 원천 ID·table·규칙 ID로 등록하고 원래 정상 원천을 유지합니다.

규칙 자체가 없는 경우, 조건표의 적용 행이 없는 경우, 감지가 끝났지만 경보가 없는 경우를 서로 다른 사례로 봅니다. 실패 뒤에는 예측·관계 반영의 성공 표시가 생기면 안 됩니다. 예외 메시지만 보고 불량이 없다고 해석하지 않습니다.

**결과를 읽습니다.** 설정 누락을 0이나 기본값으로 바꾸지 않습니다. 조건을 채운 뒤 같은 요청을 다시 실행할 수 있고, 이전 실패 기록은 그대로 남아야 합니다.

**막히면 여기서 확인합니다.** 검사가 항상 초록이면 어떤 입력을 바꿨는지 확인합니다. 구현과 같은 문장을 반복하는 검사 대신 누락 시 다음 단계가 실행되지 않는지 봅니다.

데이터 흐름을 믿을 수 있게 했으니 다른 감지 방법을 연결합니다.

### 7. 현재 분포와 미래 예측을 나눠 봅니다 · 약 25분

PyOD의 이상 점수는 기준 분포와 얼마나 다른지 나타내고, Chronos는 과거 값에서 다음 값을 예측합니다. 이상 점수는 불량 확률이 아니고, 미래 예측을 현재 정답과 섞어 학습하면 비교가 무너집니다.

분석 화면에서 한 LOT·쿠션 열·기준 행 수를 정해 PyOD를 실행합니다. 학습 앞 구간과 평가 뒤 구간을 분리합니다. Chronos는 같은 LOT에서 예측할 마지막 부분을 따로 남기고 과거 구간만 입력하도록 명세를 작성합니다. 모델 준비와 CPU 실행 시간은 실제로 관측한 값을 사용합니다.

**분석 기능과 입력을 함께 연결합니다.** 분류 화면만 있던 프로젝트에 PyOD와 Chronos 선택을 추가하도록 요청합니다. 의존성과 잠금 파일을 갱신한 뒤 `uv sync --frozen --extra models --extra dev`를 적용합니다. PyOD는 선택 LOT의 앞 구간을 기준으로 쓰고, Chronos는 config.yaml의 forecast_model을 사용합니다. 필요한 로컬 가중치가 없으면 준비 여부를 확인합니다. 서비스 답변용 API 모델을 켜는 설정과 이 CPU 분석은 별개입니다.

예측 매개변수 파일 forecast.json을 프로젝트 루트에 만듭니다. 합성 LOT4·쿠션22의 마지막20행을 남기는 첫 설정은 다음과 같습니다.

```json
{"column_id":22,"lot_id":"4","horizon":20,"evaluate_last":true}
```

화면에서 먼저 같은 설정의 결과를 읽고, 파이프라인에도 `uv run --env-file .env python scripts/reload.py --profile synthetic --source shots --rule cushion-relative --predict forecast --parameters forecast.json`으로 연결합니다. 참고 코드의 예측 입력 최소200개는 평가로 남긴20개를 제외한 뒤의 개수입니다. 원천 전체 행 수가 충분해도 선택 LOT가 짧으면 실행할 수 없습니다. 예측을 선택하지 않은 실행과 선택했지만 실패한 실행은 구분합니다.

**결과를 읽습니다.** 방법마다 사용 구간·점수 뜻·실행 시간이 보여야 합니다. 예측이 불가능한 짧은 구간을 자동으로 다른 모델에 넘기지 않습니다.

**막히면 여기서 확인합니다.** 가중치가 없으면 모델 파일 준비 문제입니다. 다운로드를 허용할지 정한 뒤 준비하고, 추론 중 공급자를 바꿔 성공처럼 만들지 않습니다.

방법 이름보다 어떤 변화를 찾고 놓쳤는지 비교합니다.

### 8. 같은 사례의 비교표를 읽습니다 · 약 25분

비교하려면 입력·구간·기준을 맞춰야 합니다. 정답 라벨이 없는 실제 자료에서는 참·거짓 경보를 확정할 수 없습니다. 합성 자료에서는 심어 둔 변화와 비교할 수 있지만 현장 성능으로 일반화할 수 없습니다.

급변·완만한 변화·변화를 넣지 않은 구간을 골라 규칙과 모델의 결과를 나란히 둡니다. 잡은 구간·놓친 구간·통지 수·실행 시간을 표시합니다. 합성의 생성 조건을 아는 평가와 원본에서의 탐색 결과를 표에서 분리합니다.

**평가할 행부터 맞춥니다.** 기본 PyOD는 앞200행 뒤를 평가하고 Chronos 예시는 마지막20행을 남깁니다. 이 두 출력 전체를 그대로 같은 분모라고 비교하지 않습니다. 합성 LOT가240행이면 마지막20행을 공통 관찰 구간으로 정하고, PyOD 기준220행/평가20행과 Chronos 과거220행/평가20행을 대조할 수 있습니다. 규칙은 자기 기준200행을 유지하되 비교표에는 공통 마지막20행에서의 관측만 따로 집계합니다. 학습/기준 구간의 차이도 표에 남깁니다.

원본 행 번호는 LOT 안의 상대 순서와 다를 수 있습니다. 점수 배열의 첫 항목이 원본 어느 행인지 연결하는 출력을 요청하고 실제 배열 길이를 대조합니다. 현재 참고 PyOD 출력에는 원본 행 번호가 직접 붙지 않으므로 이 연결을 추가하지 않았다면 ‘행별 비교 완료’로 표시하지 않습니다. 실행 시간은 같은 요청의 trace에서 측정한 단계 시간을 사용하고, 측정하지 않은 모델은 미실행으로 남깁니다.

**결과를 읽습니다.** 가장 높은 숫자 하나로 승자를 정하지 않고, 어떤 입력에서 어떤 방법을 쓸지 이유를 설명하면 됩니다. 다음 단계에 넘길 것은 확정 원인이 아니라 근거가 붙은 의심 사건입니다.

**막히면 여기서 확인합니다.** 서로 다른 행 수를 비교했다면 점수 해석을 멈추고 범위를 맞춥니다. 누락된 실행은 0점이나 0초가 아니라 미실행으로 둡니다.

이제 표의 변화를 읽는 기준이 생겼습니다. 다음에는 이미지와 수명 자료에서 관측 대상과 정답이 어떻게 달라지는지 살펴봅니다.

## 오늘 만든 것을 이어갈 준비 · 20분

현재 폴더와 실행 설정을 저장하고 오늘 확인한 대표 입력을 다시 찾을 수 있게 둡니다. 아직 실행하지 않은 모델이나 부족한 자료는 성공 결과로 바꾸지 않습니다. 다음 시간에는 자기 프로젝트를 이어가거나 그날 출발본으로 합류할 수 있습니다.

참고 완성본과 화면이나 코드가 같을 필요는 없습니다. 원하는 입력과 결과가 연결되고, 근거와 한계를 설명할 수 있는지 확인합니다. 별도 회고문 제출이나 정해진 모양의 개인 노트는 요구하지 않습니다.
