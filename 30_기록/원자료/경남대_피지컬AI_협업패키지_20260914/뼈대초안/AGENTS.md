# AGENTS.md — 이 저장소에서 일하는 법

세션마다 이 순서로 읽는다: `AGENTS.md` → `constitution.md` → `.agent/decisions.md` → `.agent/invariants.md` → `.agent/failures.md`. 요약이나 기억이 아니라 파일과 현재 코드가 사실이다.

## 1. 요청을 받으면
1. 도구를 실행하기 전에 **세 줄**을 먼저 쓴다 — 이렇게 이해했다 / 이렇게 만들겠다 / 되면 화면에 이것이 보인다. 이 세 줄은 채팅에 자연어로 나온다. 작업 로그에 섞지 않는다.
2. 요청은 요구이자 가설이다. 요청 안의 원인 진단·사실 주장은 코드·실행 결과·로그로 확인한 뒤에만 받아들인다. 다르면 근거와 함께 짧게 바로잡는다. 목표·선호는 존중한다.
3. 진행 중 확인이 필요한 것은 물음이 아니라 가정으로 적고(`가정: …`) 계속 간다. 파괴적 작업·되돌릴 수 없는 삭제만 멈춘다.
4. 막히면 우회하지 않고 멈춰 보고한다.

## 2. 착수 관문 (만들기 전에)
- 배선 한 줄을 적는다: `입력 → 층 → 저장 → API → 화면`. 지목된 파일만 보지 않는다.
- 영향도: 바꾸려는 이름·계약·필드·라우트·환경변수를 저장소 전체에서 검색해 생산자와 소비자를 같은 작업에서 고친다. 옛 이름 grep 0.
- 만드는 요청은 `spec` 스킬을 거친다(§7). 고치는 요청은 `debug` 스킬을 거친다(§5).
- **요청이 말하지 않아도 헌법대로 만든다** — 표 설계는 마이그레이션 파일, 키 열 인덱스, 업로드 파일 해시, 모델 SQL은 파싱 검사·읽기 전용·실행 계층 행 제한, 요청 번호·로그, 응답 형식, 멱등 스크립트, 그래프 적재는 한 트랜잭션 안 되읽기 대조. 요청자가 이 단어를 모른다고 빼지 않는다. 다 만든 뒤 「헌법대로 같이 한 것」을 한 줄로 알린다.

## 3. 폴더와 이름
- 층 = 폴더: `backend/{data,ontology,detect,rag,eval,agent,process,common}` · `frontend/` · `mcp_server/` · `scripts/` · `specs/` · `.agent/`.
- 각 층에 `gateway.py`(밖으로 나가는 모든 호출: 모델·저장소·파일·도구)와 `service.py`. 나머지 파일명은 자유.
- 응답은 `backend/common/response.py`, 로그는 `backend/common/log.py`, 설정 읽기는 `backend/common/config.py`에서만.
- 임시 산출물은 `_runs/`에만. 저장소 루트에 로그·캡처·실험 파일을 두지 않는다.

## 4. 로그 어휘 (이 목록 밖의 값은 쓰지 않는다)
- `layer`: `data ontology detect rag eval tools agent process ui`
- `step`(층.단계): `data.upload data.catalog data.query data.probe data.series data.quality data.report` · `ontology.load ontology.path` · `detect.rule detect.alarm detect.model detect.event` · `rag.parse rag.chunk rag.embed rag.search rag.rerank rag.router.select rag.sql rag.graph rag.answer rag.judge rag.repair` · `eval.run` · `tools.call.<도구명>` · `agent.plan agent.step agent.guard agent.resume` · `process.propose process.approval process.record` · `ui.request`
- 모델을 부른 줄은 `model tokens_in tokens_out`을 가진다. 폴백·저품질 경로를 탔으면 `status`는 그대로 두고 `reason`에 `fallback:<이유>`를 적고 응답 `meta.warnings`에도 남긴다.
- 새 단계를 만들면 이 목록과 `.agent/invariants.md`에 같은 커밋으로 추가한다.

## 5. 원인 찾기 — 7단계, 건너뛰기 없음 (`debug` 스킬이 산출물을 요구한다)
1. **재현**: 같은 입력으로 같은 증상 2회. 재현 없이는 수정 없다.
2. **경계 확인**: 코드보다 먼저 밖 — 입력 데이터가 `mapping.json`과 맞나(열·단위·비었나), 설정값이 무엇으로 들어갔나, 호출자가 계약(주소·형식)을 지켰나.
3. **경로 추적, 처음부터**: `/trace/{rid}`를 첫 줄부터 읽는다. 마지막 오류 줄에서 시작하지 않는다. 단계마다 출력이 다음 단계의 입력 조건(`invariants.md`)을 만족했나 본다. **처음으로 조건이 깨진 단계**가 원인 후보, 그 뒤는 결과.
4. **이분**: 후보 단계 안에서 게이트웨이 입력을 고정하고 절반씩 확인. 추측으로 고쳐 보지 않는다.
5. **분류**: 데이터 / 설정 / 계약 위반(호출자) / 로직 / 저장 / 모델. 이 순서로 의심하고 **모델은 마지막 용의자**다. 검사 결과가 이상하면 제품보다 검사기를 먼저 연다.
6. **수정**: 원인이 있는 자리에서. 같은 원인의 다른 자리도 grep. 증상 단계에 조건문을 넣지 않는다. 데이터가 원인이면 코드를 고치지 않는다.
7. **검증·기록**: 재현 케이스 통과 + 회귀 전체 통과. `.agent/failures.md`에 한 줄(증상 · 처음 깨진 단계 · 분류 · 고친 자리).

## 6. 코드 규범
**고친다 = 원인을 고친다.** 예외 삼키기(`except: pass`), 특정 입력만 통과시키는 분기, 검사 통과용 조건문, 실패를 성공으로 바꾸는 기본값, 재시도로 오류 숨기기, 옛 경로를 놔두는 우회 — 금지. 계약 입력이 없으면 좌표(대상 ID·파일·행)를 담은 오류로 실패한다.
**남기지 않는다.** 미사용 코드·주석 처리한 코드·옛 구현·「나중에 지울」 파일·같은 일 하는 함수 둘·복붙·임시 파일·디버그 출력·하드코딩 값. 대체했으면 옛것은 지우고 옛 심볼 grep 0.
**해피패스 금지.** 특정 파일명·번호·값·샘플에 맞춘 로직을 만들지 않는다. 검증은 빈값·경계·중복·순서 변화·재실행·부분 실패를 포함한다.
**단일 핀트 금지.** 한 증상에서 시작하되 같은 생산자·계약·소비자를 공유하는 전체를 검색해 한 자리에서 고친다.
**깨끗하게.** 이름이 하는 일을 말한다. 한 함수 한 일. 층을 섞지 않는다. 타입 힌트·입력 검증. 오류는 상태와 이유로. 측정 없는 최적화 금지. 분기·맵·병합이 늘어나면 멈추고 설계를 다시 본다.
**주석.** 코드가 무엇을·왜 하는지만. 작업 주석 금지(`TODO FIXME HACK XXX 임시 나중에 테스트용 회차 사용자 요청 이전 버전 workaround temp`). 자명한 코드에 주석 없음. 파일 머리 한 줄: 어느 층의 무엇.
**입력 충분성.** 모델에게 판단을 시키기 전에 입력만으로 판단 가능한지 먼저 본다. 부족하면 채우지 말고 `insufficient`와 부족한 것을 돌려준다.
**모델은 관측하고 코드가 판정한다.** 모델의 출력은 닫힌 형식(번호·항목별 PASS/FAIL/UNKNOWN·의미 문자열)만 받고, 합격·점수·충분성·공개 여부는 코드가 정한다. 모델에게 이름(표·열·문서)을 출력하게 하지 않고 번호로 받는다.
**요청 구조.** 고정 지시를 앞에, 대상별 입력을 뒤에. 빈 항목은 이름조차 보내지 않는다. 상한은 임의 숫자가 아니라 config의 모델별 실측 한계에서 읽는다.

## 7. 만들기 절차 (`spec` 스킬)
Specify(목적·범위·입출력·정상/실패/경계 시나리오) → Clarify(코드로 확인 가능한 것은 묻지 않고 조사) → Plan(현재 흐름·목표 흐름·책임 경계·계약·검증 방법) → Tasks(계약 양쪽 변경과 검사를 함께, 완료 증거 명시) → Implement(계획 범위만, 구조 결함은 계획 갱신 후 근본 정리) → Verify(실행·화면·로그·DB 대조, 반대 사례 포함). 산출물은 `specs/NNN-이름/{spec,plan,tasks}.md`. 체크박스가 아니라 증거로 완료.

## 8. 종료 감사 (커밋 전)
`git diff`를 처음부터 다시 읽는다 · 옛 심볼·경로·중복·임시 파일 grep 0 · 관련 없는 파일 미변경 · 검사 통과·미검증 항목 구분 · `.agent/decisions.md`에 구조 결정 한 줄(있을 때) · 커밋은 요청 범위만 · 비밀 0.

## 9. 스킬 라우팅
| 요청이 이런 말이면 | 스킬 |
|---|---|
| 만들어·추가해·바꿔·붙여·화면에 보이게 | `spec` |
| 왜·안 돼·틀려·이상해·다르게 나와·느려 | `debug` |
| 그래프에 넣어·노드·관계·잇기·지도 | `ontology-extend` (있을 때) |
| 검사로 만들어·성질·참인지·회귀 | `verify-property` (있을 때) |
| 남길 것·오늘 정리·캡처 목록·커밋 메시지 | `leave-notes` (있을 때) |
스킬은 계약 표면(API·`/trace`·`mapping.json`·`ontology.csv`·`invariants.md`·`scripts/`)만 만진다. 파일명·함수명을 전제하지 않는다.

## 10. 메모리
`.agent/decisions.md`(왜 이렇게 했나) · `.agent/invariants.md`(층·단계별 입력/출력 조건 표) · `.agent/failures.md`(고장 카탈로그). 작업 메모·임시 생각은 저장소 밖. 코드·주석에 쓰지 않는다. 컨텍스트가 압축되거나 새 세션이면 §0의 순서로 다시 읽고 현재 코드와 대조한 뒤 이어간다.

## 11. 표현
결론 먼저. 비개발자가 읽을 말로, 원인·영향·검증은 생략하지 않는다. `.env`의 값은 출력하지 않는다. 검증하지 않은 것은 「미검증」이라고 쓴다.
