# 1일차 · 숫자를 읽고, 같은 기준으로 바꾸기

오늘은 설비가 고장 났는지 맞히는 날이 아닙니다. 온도·압력·유량을 비교하려면 먼저 숫자가 무엇을 뜻하는지 알아야 합니다. 이미 준비된 플랫폼에서 완성 모습을 보고, 그 안에 필요한 작은 데이터 기능을 AI와 만들어 봅니다. 코드를 직접 입력하거나 문법을 외우지 않아도 됩니다.

수업 전 코딩 에이전트 연결과 플랫폼 기본 구동을 준비합니다. 접속 문제는 설치 안내에서 해결하고, 오늘 가이드는 자료를 읽고 결과를 판단하는 데 집중합니다. 플랫폼 구동이 지연돼도 작은 표본 작업부터 이어갈 수 있습니다.

## 먼저 끝 모습을 봅니다

준비된 관제 화면에서 온도·압력·유량을 찾아보세요. 지금 화면이 시뮬레이터라면 교육용으로 만든 값입니다. 잠시 후 사용할 파일은 실제 UCI 센서 데이터의 일부입니다. 화면의 값과 파일의 값이 반드시 같아야 하는 것은 아닙니다.

오늘 확인할 질문은 세 가지입니다. ‘무슨 값을 쟀을까?’, ‘1초에 몇 번 쟀을까?’, ‘결과에서 원본으로 돌아갈 수 있을까?’

## AI에게 자료를 먼저 설명하게 합니다

`시작코드` 폴더를 코딩 에이전트의 작업 폴더로 엽니다. 아래 요청은 예시입니다. 그대로 사용해도 됩니다.

> README와 data/sensor_windows.json을 읽어 줘. 아직 코드를 만들지 말고 온도·압력·유량의 단위와 1초 측정 개수를 표로 설명해 줘. origin_cycle_id와 elapsed_s가 무엇인지도 짧게 설명해 줘. 입력 자료는 바꾸지 마.

온도 TS1은 1초에 1번, 압력 PS1은 100번, 유량 FS1은 10번 측정했습니다. 이 횟수를 Hz라고 합니다. 압력 숫자가 더 많은 것은 반드시 압력이 더 중요해서가 아니라 측정 간격이 더 짧기 때문입니다.

`origin_cycle_id`는 원본에서 몇 번째 사이클인지 알려 주는 번호입니다. 여기서는 0부터 세었습니다. `elapsed_s`는 그 60초 사이클 안에서 몇 초가 지났는지입니다. 실제 수집 날짜가 아니므로 임의 날짜를 만들어 붙이지 않습니다.

AI의 설명에서 단위와 횟수가 파일과 맞는지 보세요. ‘모든 센서의 단위는 °C’처럼 설명했다면 수정 요청을 해야 합니다. AI가 설명했다는 사실과 설명이 맞다는 것은 다릅니다.

## 만들 기능을 짧게 정합니다

센서마다 측정 개수가 달라 그대로 한 줄씩 나란히 붙이면 서로 다른 시점을 비교할 수 있습니다. 오늘은 같은 1초 구간을 한 줄로 요약하겠습니다. 평균은 구간의 대표값이고, 최솟값과 최댓값은 그 안에서 얼마나 움직였는지 보여 줍니다. 측정 개수는 요약에 몇 개가 쓰였는지 알려 줍니다.

> 1초 구간마다 평균·최솟값·최댓값·개수를 계산하는 기능을 만들고 싶어. 센서 이름·원본 사이클·사이클 내 초·단위도 남겨 줘. 데이터가 비었거나 개수가 맞지 않으면 0으로 채우지 말고 어떤 구간이 문제인지 알려 줘. 이 요구를 ‘만들 것, 지킬 조건, 확인 방법’으로 짧게 정리해 줘. 아직 구현은 하지 마.

이 짧은 약속이 명세입니다. 명세로 원하는 동작을 정한 뒤 구현하는 방식을 SDD라고 부릅니다. 긴 문서를 쓰는 것이 목적은 아닙니다. AI가 다른 것을 만들지 않도록 뜻을 맞추는 데 사용합니다.

확인 방법에 ‘오류가 안 나면 성공’만 적혀 있다면 부족합니다. 원본 일부와 계산 결과가 맞는지, 단위와 출처가 남는지도 넣어 달라고 요청하세요.

## 구현은 AI에게 맡깁니다

> 방금 정리한 명세대로 student-work 안에 기능을 구현하고 실행해 줘. 필요한 환경도 네가 준비해 줘. 외부 모델 호출은 필요 없어. 원본 파일은 보존하고 결과를 CSV나 읽기 쉬운 로컬 표로 보여 줘. 사용한 입력 경로와 결과 경로를 알려 줘. 실행하지 못한 것은 실행했다고 하지 마.

학생이 설치 명령을 외울 필요는 없습니다. 에이전트가 완료했다고 하면 결과 파일이나 화면을 직접 엽니다. 출력의 한 행은 ‘한 센서의 한 사이클 안 1초 구간’입니다. 전체 27행이 있어야 하지만 행 수만 맞는다고 성공은 아닙니다.

온도 행은 개수 1이므로 평균·최솟값·최댓값이 같습니다. 압력 행은 개수 100, 유량 행은 개수 10이어야 합니다. 서로 다른 센서의 평균을 합쳐 한 숫자로 만들면 단위도 섞이므로 오늘의 요구와 다릅니다.

## 원본과 한 구간을 비교합니다

> PS1의 origin_cycle_id 100, elapsed_s 0 구간을 골라 원본 측정 개수·첫 값·최솟값·최댓값·평균을 결과 행과 나란히 보여 줘. 결과 CSV를 다시 읽어서 비교해 줘. 계산식을 설명하되 코드 문법 설명은 길게 하지 마.

원본에서 100개를 썼는지, 첫 값 하나만 평균처럼 표시하지 않았는지 봅니다. 눈으로 100개를 모두 더하라는 뜻은 아닙니다. 어떤 구간을 어떻게 요약했고 무엇과 비교했는지를 이해하는 것이 중요합니다.

표에 원하는 행이 없다면 입력 경로와 센서/사이클/초 조건부터 확인하게 하세요. 실행 오류가 났다면 에이전트에게 오류 메시지와 작업 폴더를 확인하게 합니다. 다른 데이터를 임의로 만들어 성공 화면으로 대체하게 하지 않습니다.

## 작은 변화 하나를 요청합니다

> 결과 표에서 센서 하나를 선택해 볼 수 있게 해 줘. 요약 계산과 원본은 바꾸지 마. 센서를 바꿀 때 단위와 측정 개수도 함께 확인할 수 있어야 해.

이것은 새로운 기술을 하나 더 외우는 과제가 아닙니다. 이미 만든 기능을 내가 보기 편하게 바꾸는 연습입니다. 결과가 보여야 하는 조건을 말하고 실제로 그렇게 됐는지 확인하면 됩니다.

마지막으로 ‘평균만 보면 놓칠 수 있는 것은 무엇인가’를 생각해 보세요. 다음 시간에는 값의 변화와 센서 오류를 구분합니다. 오늘의 원본·범위·측정 개수는 그 판단의 재료가 됩니다.

## 작업을 잃었거나 중간에 합류했다면

기존 작업 폴더는 그대로 두고 `시작코드`을 다른 폴더에 복사해 시작합니다. 명세와 구현 요청을 이어서 사용하면 됩니다. 다음 날에는 그날 시작에 필요한 완성 출발본을 제공하는 방식으로 구성합니다. 현재 문서는 제작 초안이며 실제 학생 소요시간·모델 작업 완주는 아직 측정하지 않았습니다.
