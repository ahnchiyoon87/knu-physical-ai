# 3일차 설비와 근거 연결하기

온도 값을 읽었다면 다음 질문은 “어느 설비의 센서이며, 어떤 점검 절차를 적용할까?”입니다. 오늘은 **설비·센서·절차의 관계를 찾고, 그 관계에 실제 측정값을 연결**합니다.

Neo4j는 대상 사이의 관계를, PostgreSQL은 시간에 따라 쌓이는 측정값을 저장합니다. SOP는 설비를 점검하고 조치하는 표준 절차서입니다. 코딩 에이전트가 질의를 구현하고, 여러분은 대상·조건·결과가 맞는지 확인합니다.

## 1. 작업 시작하기

실전반은 `시작본/practical/context_queries.py`, 통합반은 `시작본/integrated/graph_lab.py`를 사용합니다. 두 파일 모두 **자신의 작업 폴더로 복사**합니다. 지난 작업과 원본은 보존하세요.

> 내 반의 3일차 시작본을 새 개인 작업 폴더로 복사해 줘. 제공 플랫폼코드에 연결하고 PostgreSQL과 Neo4j가 실행 중인지 확인해 줘. 그래프에 설비3개·센서9개·SOP7개가 있는지 조회해 줘. 없거나 다르면 이유를 알려 주고, 기존 데이터를 초기화하지 마. 아직 과제 코드는 고치지 마.

통합반은 인용이 연결된 준비 사건도 필요합니다. 사건이 없다면 강사에게 준비 상태를 확인받습니다. 사건 조회가 비거나 검사가 건너뛰어졌다면 그 활동을 완료한 것은 아닙니다.

지난 수업을 놓쳤다면 제공된 2일차 완성본으로 관측의 `asset_id`·센서 코드·단위·품질 표시를 먼저 확인합니다. 오늘 마지막 활동은 별도의 사이클100을 읽으므로 지난 오류 주입 CSV를 덮어쓰지 않습니다.

## 2. 질문에서 관계 찾기

노드는 대상이고, 관계는 두 대상을 연결하는 방향 있는 화살표입니다. 예를 들어 `설비 → 센서`는 “이 설비에 이 센서가 달려 있다”는 뜻입니다.

팀에서 다음 세 질문을 나누어 맡습니다. 설비·센서·SOP·절·조치·사건 카드를 놓고 필요한 화살표를 연결하세요. 결과 표를 만들 때 **그래프만으로 답할 수 없는 부분**도 표시합니다.

| 질문 | 찾아볼 관계 | 그래프 밖에서 확인할 것 |
|---|---|---|
| 최근 온도가 믿을 만하고 계속 높은가? | 설비 → 센서 | 최근 관측의 값·시간·품질 |
| 이 설비의 현재 절차와 허용 조치는? | SOP → 적용 설비, SOP → 허용 조치 | 해당 SOP 본문의 적용 범위 |
| 사건은 어떤 근거를 사용했고 이후 어떻게 됐나? | 사건 → 설비, 사건 → 인용 절, SOP → 절 | 승인·실행·재측정 기록 |

에이전트에게 Neo4j Browser를 열고, 현재 유효한 SOP에서 적용 설비와 센서로 이어지는 **조회 질의**를 준비하도록 요청합니다. 접속 주소는 `http://localhost:57474`, DB 연결 주소는 `bolt://localhost:57687`입니다. 로컬 수업 계정은 `neo4j`, 암호는 `hydops-lecture`입니다.

> 현재 유효한 SOP → 적용 설비 → 센서 경로를 조회하는 문장을 준비해 줘. 무엇을 찾고 어떤 결과를 반환하는지 짧게 설명해 줘. 데이터를 만드는 명령은 넣지 마. 내가 Browser에서 실행한 결과와 우리가 만든 관계 표를 대조하자.

Browser 결과에서 HYD-01과 HYD-02를 찾습니다. HYD-03이 보이지 않는 이유도 확인하세요. **경로에 없다는 사실만으로 설비 자체가 없다고 결론 내리면 안 됩니다.** 별도로 설비 존재를 조회해야 합니다.

## 3. 같은 대상을 같은 ID로 연결하기

세 설비 모두 TS1이라는 온도 센서 코드가 있습니다. 그래프는 `HYD-01.TS1`처럼 설비까지 붙여 센서를 구분합니다. PostgreSQL은 설비 열의 `HYD-01`과 센서 열의 `TS1`을 함께 사용합니다.

| 구분 | 예 | 의미 |
|---|---|---|
| 설비 ID | `HYD-01` | 어느 설비인가 |
| 그래프 센서 ID | `HYD-01.TS1` | 어느 설비의 어느 센서인가 |
| 관측의 센서 코드 | `TS1` | 같은 행의 설비 ID와 함께 읽음 |
| SOP 판 식별자 | `SOP-COOL-001@v2` | 같은 문서의 2판 |

`MERGE`는 같은 ID가 있으면 찾고 없으면 만듭니다. ID의 점 하나가 하이픈으로 바뀌면 다른 센서로 취급될 수 있습니다.

**실전반**

> 제공 그래프 적재 코드에서 Asset·Resource, Sensor·Measure 라벨이 어떻게 함께 붙는지 설명해 줘. 기존 그래프를 조회해 설비·센서 ID와 라벨을 보여 줘. 같은 ID를 중복 저장하지 못하게 하는 제약도 확인해 줘. 적재 코드와 DB 전체를 수정하지 마.

Asset은 수업의 설비 유형이고 Resource는 더 넓은 자원 분류입니다. Sensor와 Measure도 같은 센서 노드에 붙은 구체 유형과 측정 분류입니다. 같은 대상이 두 개로 복제됐다는 뜻은 아닙니다.

이어서 SOP 2판이 1판을 대체하는 관계와 `AFFECTS` 관계의 근거를 확인합니다.

> SOP-COOL-001의 1판·2판 상태와 대체 관계를 조회해 줘. 냉각 성능·부하가 온도 센서에 영향을 준다는 관계는 설비별로 basis·source·verified_causal를 보여 줘. 문서 근거인지 시뮬레이터 가정인지 구분하자.

문서에 적힌 관계와 실측으로 입증한 인과관계는 다릅니다. `verified_causal=false`인 관계를 실제 공장에서 검증된 법칙이라고 설명하지 마세요.

**통합반**

> 센서 ID와 SOP 판 식별자가 제공 그래프의 ID와 같아야 해. graph_lab.py의 해당 빈칸을 구현하고, 제공된 되돌리기 함수를 유지해 줘. 같은 ID로 실행했을 때 생성된 노드·관계가 각각0인지 보여 줘. 테스트는 수정하지 마.

네 확인 결과가 모두 `committed=True`, 생성 수0인지 봅니다. 이어서 강사와 함께 별도 임시 질의에서 센서 ID의 점을 하이픈으로 바꿔 실행합니다. 제공 함수가 변경을 되돌렸는지 확인하고, 원래 작업본에는 올바른 ID를 유지합니다.

- 잘못된 ID의 시험 결과: 생성될 노드1개·관계1개, `committed=False`.
- 되돌린 뒤 조회: `HYD-01-TS1` 센서는0개.

이는 제공된 시험 함수의 보호 동작입니다. 임의의 쓰기 명령까지 안전하게 되돌려 준다는 뜻은 아닙니다.

## 4. 대상과 조건을 바꾸어 SOP 찾기

“냉각 이상”이라는 말만 같아도 설비마다 적용할 조치가 다를 수 있습니다. **설비·사건 유형·현재 유효한 판**을 함께 조건으로 사용합니다.

> 설비와 사건 유형을 입력받아 센서 목록과 적용 가능한 현재 SOP·허용 조치를 조회하고 싶어. 특정 설비를 코드에 고정하지 말고 입력만 바꾸어 조회하게 해 줘. 허용 조치가 없는 SOP도 결과에 남겨 줘. 입력·동작·확인 기준을 먼저 정리하고 내 작업본을 구현해 줘. 제공 테스트는 바꾸지 마.

실전반은 설비 맥락 조회도 구현합니다. 설비 존재, 냉각 구성품, 현재 SOP, 허용 조치를 함께 보되 SOP가 없어도 설비 정보는 남겨야 합니다. 통합반은 사건의 설비와 인용한 SOP 절을 찾는 질의까지 구현합니다.

결과를 다음 조건으로 비교합니다.

| 조회 조건 | 확인할 결과 |
|---|---|
| HYD-01 / 냉각 이상 | 냉각 SOP-COOL-001 2판, 부하 감소 REDUCE_LOAD |
| HYD-02 / 냉각 이상 | 냉각 SOP-COOL-002 1판, 팬 증속 FAN_BOOST |
| HYD-03 / 냉각 이상 | 적용 SOP 없음. 다른 설비의 SOP를 대신 붙이지 않음 |
| HYD-01 / 센서 오류 | SOP-SEN-001, 센서 점검 SENSOR_CHECK |

냉각 이상 조회에는 재점검·이관 등 관련 절차도 함께 나옵니다. 위 표는 냉각 조치의 차이를 확인하는 기준이며 전체 SOP 목록은 아닙니다. HYD-02의 팬 증속 허용 범위는1.0~1.5, 기본값은1.3입니다. 적용 문서 본문과도 대조하세요. **허용 조치를 조회한 것만으로 조치를 실행하지는 않습니다.**

> 원래 질의는 보존하고, 비교용 읽기 질의에서 active 조건만 제거해 줘. HYD-01의 냉각 SOP 결과에 어떤 판이 추가되는지 보여 줘.

폐기된1판이 섞이는지 확인합니다. 옛 판을 보존하는 이유는 과거 사건의 근거를 추적하기 위해서입니다. 오늘의 조치에 옛 판을 사용하라는 뜻은 아닙니다.

통합반은 준비된 사건 ID로 인용을 조회합니다. 문서 ID·판·절을 읽고 해당 SOP 절을 엽니다. 인용이 존재한다는 사실과, 사람이 승인했다는 사실을 구분하세요. 승인 대기 사건은 아직 조치·회복이 끝난 사건이 아닙니다.

## 5. 관계에 최근 값을 붙이기

관계는 센서가 어디에 속하는지 알려 주지만 지금 측정값이 얼마인지는 알려 주지 않습니다. 이번에는 그래프의 센서 목록에 PostgreSQL의 최근60초를 붙입니다.

> 별도 LAB- 실행으로 제공 UCI 사이클100을 읽고 품질 검사 후 PostgreSQL에 적재해 줘. 그래프 센서의 code와 관측의 sensor_id를 연결하되 asset_id와 run_id도 반드시 조건에 넣어 줘. 센서 ID·그래프 단위·DB 단위·관측 개수·품질·값을 나란히 보여 줘. 결과를 저장한 뒤 이번 임시 실행의 관측만 정리해 줘.

실전반은 `join_recent`, 통합반은 `sensors_with_recent_values`의 결과를 확인합니다. 통합반 제공 함수 `load_lab_cycle`과 `cleanup`은 이번 임시 실행을 만들고 정리합니다.

| 센서 | 양쪽 단위 | 조회 개수 | 사이클100 마지막 원시 값 |
|---|---|---|---|
| HYD-01.FS1 | L/min | 60 | 7.884 |
| HYD-01.PS1 | bar | 60 | 147.345 |
| HYD-01.TS1 | °C | 60 | 53.395 |

현재 제공 품질 기준에서는 세 센서 모두60개가 OK입니다. 이 표는 사이클100의 결과이며, 지난 시간 사이클1500의 온도 오류 주입 결과와 구분합니다. 품질OK를 설비 정상 판정으로 읽지 마세요.

팀에서 한 행을 골라 어느 칸이 그래프에서 왔고 어느 칸이 PostgreSQL에서 왔는지 표시합니다. 이어서 다음 두 가지를 확인합니다.

- `HYD-01.TS1`을 관측의 센서 코드 조건에 넣으면 왜0행이 되는가?
- `run_id`를 빼면 왜 다른 실행의 최신 데이터가 섞일 수 있는가?

답은 에이전트의 설명만 듣지 말고 조회 조건과 실제 결과에서 찾으세요. 다음 시간에는 이 관측이 얼마나 오래 기준을 벗어났는지 계산해 사건으로 만듭니다. 오늘 만든 설비·SOP 연결은 이후 사건의 근거 조회에 사용합니다.

## 6. 확인하고 저장하기

자신의 작업 코드, 세 질문의 관계 표, 설비별 SOP 비교 결과, 관계와 수치를 합친 결과를 저장합니다. 결과에서 설비·센서·문서 판·원본 사이클을 다시 찾을 수 있어야 합니다.

> 내 작업본의 제공 테스트를 실행하고 통과·실패·건너뜀을 각각 알려 줘. 실패했다면 해당 입력과 실제 출력을 먼저 보여 줘. 테스트를 약하게 바꾸거나 빈 결과를 성공으로 처리하지 마.

통합반은 SOP 절 목록을 더 조회하는 확장 과제를 선택할 수 있습니다. 선택한 문서의 판을 지정하고, 각 절의 번호·제목을 조회해 문서와 비교합니다.

| 막힌 지점 | 확인할 내용 |
|---|---|
| Neo4j 접속 실패 | 컨테이너 상태, Browser 주소와 DB 연결 주소의 차이 |
| 관계 조회가 빈 목록 | 설비 존재, 관계 이름·방향, active 철자, 사건 유형 |
| HYD-03의 SOP가 없음 | 의도된 준비 상태. HYD-03 설비 자체는 별도로 조회 |
| 잘못된 ID가 반영되지 않음 | 제공 함수가 새 노드 생성을 감지해 되돌렸는지 |
| 최근 값이0행 | 센서 전체 ID 대신 코드 사용 여부, asset_id·run_id |
| 사건 인용이 없거나 검사 건너뜀 | 사전 준비 사건이 있는지 강사와 확인 후 재실행 |
| 단위가 서로 다름 | 첫날 매핑과 양쪽 센서 식별 기준 비교 |

복구할 때 그래프 전체나 다른 실행의 데이터를 삭제하지 않습니다. 수정한 부분은 같은 입력으로 다시 조회해 확인합니다.
