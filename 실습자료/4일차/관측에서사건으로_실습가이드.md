# 4일차 관측에서 사건으로

높은 온도 한 점과 대응해야 할 사건은 다릅니다. 오늘은 **어떤 관측을 얼마나 기다려 사건으로 만들지**, 그리고 같은 이상을 중복 등록하지 않는 방법을 확인합니다.

코딩 에이전트가 구현하고 여러분은 입력·판정 조건·실제 사건을 비교합니다. 원본 데이터와 제공 플랫폼 코드는 보존합니다.

## 시작 상태 확인

> 내 반의 4일차 시작본을 새로운 개인 작업 폴더로 복사해 줘. 제공 UCI 축약본과 시뮬레이터를 불러올 수 있는지 확인해 줘. 지난 작업은 보존하고, 제공 테스트를 수정하지 마. 과제의 미완성 부분과 환경 문제를 구분해서 알려 줘.

실전반은 `detector_lab.py`, 통합반은 `detect_config.py`와 `event_types.py`를 사용합니다. 관제 활동에는 로컬 서버 `http://localhost:8800`도 필요합니다. 메모리에서 도는 과제 테스트와 실제 서버의 사건 확인은 따로 수행합니다.

| 순서 | 실전반 | 통합반 |
|---|---|---|
| 활동1 | 정상 위상과 이동 통계 | 정상 위상과 이동 통계 |
| 활동2 | 지속 조건과 중복 억제 | 설정별 오탐·지연 비교 |
| 활동3 | 사건 저장과 관제 표시 | 센서·설비·제품 사건 구분 |
| 활동4 | 고정 시험 평가와 체크포인트 | 관제 표시와 평가 결과 확인 |

## 활동1. 비교할 기준부터 확인하기

UCI의 한 사이클은60초입니다. 시작 직후 값과 끝날 때 값이 다를 수 있으므로 **같은 경과 초끼리 비교**합니다. 이 위치를 위상이라고 부릅니다. 이동평균은 주변의 연속된 값을 묶어 짧은 흔들림을 완화한 값입니다.

> 제공 fixed_split과 PhaseBaseline을 사용해 기준 사이클과 시험 사이클을 확인해 줘. 기준은 냉각기100%·안정 상태인 구간에서 만들고, 시험 구간과 겹치지 않아야 해. 고정 시드2026과 시험180개를 보존해 줘. 같은 경과 초의 기준 온도와 비교 대상 온도, 잔차와 허용 한계를 보여 줘. profile 라벨은 평가할 때만 사용해 줘.

잔차는 비교 대상과 기준의 차이입니다. 제공 한계는 `max(k_sigma × 표준편차, min_delta_c)`입니다. 정상 기준의 흔들림과 최소 차이를 함께 고려합니다. 어떤 값이 한계를 넘었는지 그래프에서 찾아보세요.

UCI 위상 비교와 합성 시뮬레이터의 고정 온도 규칙은 서로 다른 입력에 쓰입니다. 시뮬레이터의60°C를 UCI 설비의 실제 운전 기준이라고 설명하지 않습니다.

## 실전 활동2. 유효 관측을 세고 사건을 묶기

> SustainDetector가 품질OK인 value만 세도록 구현해 줘. 유효 값이 기준 이하이거나 GAP이면 다시 세고, 단발 MISSING·SPIKE는 세지도 초기화하지도 않게 해 줘. 같은 설비·유형의 열린 사건은 EventBook에서 새로 만들지 말고 기존 사건을 반환해 줘. 닫힌 사건 뒤의 새 신호는 새 사건으로 구분해 줘.

다음 입력의 결과를 직접 확인합니다.

- 높은 유효값6개 → 짧은 결측1개 → 높은 유효값4개: 유효값10개를 센 사건1개.
- 높은 유효값9개 → SPIKE1개: 유효값이10개가 되지 않으므로 사건 없음.
- 높은 유효값 사이에 GAP: 이전 카운트를 이어 쓰지 않음.

> 제공 seed7·냉각효율0.5·300초 스트림을 같은 입력으로 고정하고 지속1·5·10·20초를 비교해 줘. 신호 수, 새 사건 수, 중복 억제 수를 각각 보여 줘.

실제 비교에서 지속1초는 신호65개·사건1개·억제64개였습니다. 지속5·10·20초는 신호0개였습니다. 신호를 줄이는 조건과 이미 열린 사건을 중복 등록하지 않는 조건은 다른 역할입니다. 사건0개를 곧바로 설비 정상 판정으로 해석하지 마세요.

## 설정을 비교해 오탐과 지연 읽기

통합반은 활동2에서, 실전반은 관제 확인 뒤 활동4에서 진행합니다.

> 시험 구간은 고정하고 제공 기본 설정과 비교 설정을 실행해 줘. 각 행에 k_sigma·min_delta_c·sustain_s·smooth_s를 모두 적어 줘. 먼저 기본/느슨한 설정의 차이를 보고, 그다음 한 변수만 바꿔 원인을 구분하자. 결과가 좋게 나오도록 시험 사이클을 다시 뽑지 마.

| 비교 | 조건 | 오탐 | 평균 감지 지연 |
|---|---|---:|---:|
| 기본 | 4σ·3°C·지속10초·평활5초 | 1 | 9초 |
| 느슨한 설정 | 2σ·1°C·지속1초·평활1초 | 4 | 0초 |
| 지속만1초 | 기본에서 지속만 변경 | 1 | 0초 |
| 지속만20초 | 기본에서 지속만 변경 | 1 | 19초 |

첫 두 행은 여러 설정이 다르므로 오탐 감소를 지속 조건 하나의 효과라고 말할 수 없습니다. 같은 고정 시험에서 지속1·5·10·20초는 오탐1개로 같고 지연만0·4·9·19초였습니다.

통합반은 다음 다섯 설정을 비교합니다. 표의 순서는 `k_sigma·min_delta_c·sustain_s·smooth_s`입니다.

| 비교 설정 | 네 입력값 |
|---|---|
| 기본 | 4·3·10·5 |
| 짧은 지속·평활 | 4·3·1·1 |
| 긴 지속 | 4·3·30·5 |
| 낮은 허용 한계 | 2·1·10·5 |
| 낮은 한계·짧은 지속·평활 | 2·1·1·1 |

시뮬레이터에서도 지속1·10·30초를 비교합니다. 실전반은 `fixed_test_ids`와 `compare_sustain`을 구현하고 호출할 때마다 시험 ID가 같은지 확인합니다.

> 한계 비교도 다른 조건을 고정해 줘. 지속10초·평활5초에서 k_sigma2와4 각각에 대해 최소 차이1°C·3°C를 비교해 줘.

실제 오탐은2σ에서4→1, 4σ에서3→1이었습니다. 비교 조건을 함께 남겨야 같은 결과를 다시 설명할 수 있습니다. 시험 결과는 설정의 효과를 학습하기 위한 비교이며, 같은 시험 결과로 설정을 고르고 독립 평가 성능이라고 주장하지 않습니다.

## 통합 활동3. 세 가지 사건을 구분하기

> event_types.py에서 센서 품질을 먼저 확인하고 유효 온도의 지속 조건을 판단하도록 구현해 줘. 긴 결측·고착·낮은 유효 비율이 있는 구간을 높은 온도만으로 냉각 이상이라고 분류하지 마. 합성 로트의 규격 이탈은 별도 제품 품질 사건으로 구분해 줘.

| 자료·상황 | 구분 |
|---|---|
| 관측의 결측·고착 | SENSOR_FAULT: 센서 오류 |
| 유효 온도의 지속 이탈 | COOLING_ANOMALY: 냉각 이상 |
| 합성 검사 치수의 규격 이탈 | PRODUCT_QUALITY: 제품 품질(합성) |
| profile의 냉각기 상태 | 설비 상태 평가 라벨, 제품 불량 아님 |

정상·급등·결측·고착·냉각 저하의 다섯 상황을 같은 시드로 실행합니다. 고착 비교는 제공된 종료 시점50초를 유지하세요. 과제의 단순 분류는 전체 구간을 보지만 플랫폼의 현재 센서 상태는 최근15초를 봅니다. 고착이 끝난 뒤 관찰 시점을 바꾸면 두 판정이 달라질 수 있습니다.

합성 로트는6번째만5개 중5개가 규격을 벗어납니다. 로트 보류 제안이 실제 제품 불량 입증이나 설비 부하 감소 명령을 뜻하지는 않습니다.

## 관제에서 같은 사건 확인하기

실전반은 활동3, 통합반은 활동4입니다. 강사와 함께 관제 화면을 열고 단발 급등·센서 결측·냉각 성능 저하의 결과를 비교합니다. 시나리오를 바꿀 때 이전 사건과 실행 ID를 보존·구분합니다.

> 관제 서버 상태와 현재 실행 ID를 확인해 줘. 강사가 준비한 각 시나리오에서 화면의 사건 목록과 API 응답을 비교해 줘. event_id·asset_id·event_type·status·탐지 구간·규칙 버전·근거 요약을 보여 줘. 승인과 조치는 이번 확인에서 실행하지 마.

- 단발 급등: 품질 표시는 생기지만 냉각 이상 사건은 생기지 않는지 확인합니다.
- 긴 결측: 센서 오류 사건과 GAP 근거를 확인합니다.
- 냉각 저하: 유효 온도 초과10개가 쌓인 감지 구간을 읽습니다.
- 같은 이상이 계속될 때: 사건이 매초 새로 생기지 않는지 확인합니다.

`/api/events`는 기본적으로 현재 실행의 사건을 보여 줍니다. 이전 실행은 `all_runs=true`로 조회하되 현재 사건과 섞어 세지 않습니다. 초기화로 끝난 이전 사건의 `RUN_ENDED`는 회복을 뜻하지 않습니다.

실전반은 제공 데이터소스의 읽기 질의로 `ux_event_open` 인덱스를 확인하고 EventBook의 열린 사건 기준과 대조합니다. 통합반은 `EVENT_DISPLAY`와 `TYPICAL_END_STATUS`를 관제 표시 매핑에 맞추고 제품 품질의 “합성” 표시를 확인합니다.

## 저장하고 다음 수업 준비하기

실전반은 학기 중 마지막 실습입니다. 방학에 같은 상태로 돌아올 수 있도록 코드뿐 아니라 **입력과 설정**을 보관합니다.

> 개인 체크포인트 폴더에 1~4일차 작업 코드, 품질·탐지 설정, 시드, 기준/시험 사이클 수, 시험ID 해시, 비교표를 저장해 줘. 내 실행의 사건·이력도 강사 안내에 따라 읽기 전용으로 내보내 줘. API 키와 .env는 포함하지 마. 저장 파일을 다시 열어 누락과 재개 경로를 확인해 줘.

같은 이름의 코드도 회차별 폴더에 두어 구분합니다. 비교표에는 사용한 네 설정값과 결과를 함께 남기세요. **플랫폼 기본값, 내가 평가에 넣은 값, 관제 사건을 만든 실행의 값**이 같은지는 따로 확인해야 합니다. 기본값을 저장했다는 이유로 내 실행 설정까지 보존됐다고 판단하지 않습니다.

저장본을 다시 열어 코드 파일과 비교표를 확인한 뒤, 재개할 때는 입력 경로와 실행 환경도 확인합니다. 사건·이력 내보내기는 당시 기록을 읽기 위한 것이며 DB를 이전 상태로 되돌리는 기능은 아닙니다.

실전반은 준비된 제로샷 예측 환경이 있을 때 선택 비교를 수행할 수 있습니다. 미래값을 입력하지 않고, 예측 이탈과 정상 위상 이탈이 서로 다른 질문임을 결과에서 설명합니다. 실행하지 않은 비교는 실행 결과로 기록하지 않습니다.

통합반은 설정별 평가표와 세 유형 분류, 화면 비교 결과를 저장합니다. 다음 시간의 SOP 검색은 오늘 만든 사건의 설비·유형을 입력으로 사용합니다.

| 막힌 지점 | 확인·복구 |
|---|---|
| 설정 빈칸 오류 | 해당 설정의 뜻을 확인한 뒤 개인 작업본만 구현 |
| 실행마다 평가 결과가 다름 | 시험 ID·시드·네 설정값 대조 |
| 급등이 냉각 사건으로 생성 | raw_value 대신 품질OK인 value를 세는지 |
| 사건 목록이 비어 있음 | 현재 run_id, 이전 사건, 감지 조건을 각각 확인 |
| 관제 연결 실패 | 서버 복구 후 실제 화면 확인을 다시 수행 |
| 고착 종료 후 분류 차이 | 전체60초와 현재15초의 판단 범위 구분 |
| 체크포인트를 다시 열 수 없음 | 코드·데이터 경로·설정·실행 기록을 하나씩 확인 |

제공 테스트의 통과·실패·건너뜀과 실제 관제 확인 결과를 구분합니다. 화면 확인이 남았다면 테스트 통과만으로 그 활동을 완료했다고 기록하지 않습니다.
