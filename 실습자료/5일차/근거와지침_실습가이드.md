# 5일차 · 근거를 찾고 판단 순서를 정하기

냉각 이상 사건이 생겼습니다. 이제 **이 설비에 어떤 조치를 제안해도 되는지** 확인합니다. 문서를 검색하고, 적용 대상과 버전을 확인한 뒤, 근거가 없을 때 멈추게 만듭니다.

| 구분 | 오늘 사용하는 것 | 학생이 확인할 질문 |
|---|---|---|
| SOP | 조치 절차를 담은 문서 | 이 설비와 사건에 적용되는 현행 문서인가? |
| Skill | 에이전트의 판단 순서와 중단 지침 | 무엇부터 확인하고 언제 멈추는가? |
| 도구 | 데이터를 조회하고 조건을 검사하는 함수 | 실제 입력과 검사 결과는 무엇인가? |

## 시작 상태 확인

프로젝트 폴더를 코딩 에이전트에서 엽니다. 다음 요청에서 자신의 반을 선택합니다.

> 나는 [실전반 / 통합반]이다. `실습자료/5일차/시작본` 아래 내 반 폴더를 개인 작업 폴더로 복사해 줘. 실전반은 `practical`, 통합반은 `integrated`다. 기존 개인 작업이 있으면 덮어쓰지 말고 그 위치를 확인해 줘. 제공 테스트와 플랫폼 코드는 유지하고 개인 작업 파일만 수정한다. 오늘은 `HYDOPS_AGENT_MODE=offline` 환경으로 실행한다. PostgreSQL·Neo4j와 관제 서버의 상태를 확인하고, 과제 코드가 `플랫폼코드`의 hydops를 불러올 수 있게 연결해 줘. 실행 명령과 결과를 내 작업 폴더에 기록해 줘.

## 활동 1 · 내 반의 출발점 확인하기

### 실전반 — 이전 작업과 네 도구

저장 파일이 있다는 것과 같은 조건으로 실행된다는 것은 다릅니다. 지난 실습의 코드·데이터·설비 관계를 확인합니다.

> 지난 체크포인트와 현재 환경을 비교해 줘. `hydops.b5_detect.evaluate.fixed_split()`의 기준·시험 개수와 시험 ID 목록 SHA-256, 4일차 개인 코드의 제공 테스트 결과, `graph.graph_stats()`의 SOP·SOPSection·APPLIES_TO·SUPERSEDES 수를 보여 줘. 체크포인트가 없거나 값이 다르면 차이와 원인을 먼저 설명해 줘. 공유 DB를 비우는 시스템 전체 테스트를 실행하지 마.

제공 데이터의 기준은 244개, 시험은 180개입니다. 시험 ID 해시 앞 16자리는 `2bb1593b85bc83a9`입니다. 기본 SOP 구성은 문서 7개·절 42개·적용 관계 10개·개정 관계 1개입니다. 개인적으로 문서를 추가했다면 개수만 보고 삭제하지 말고 추가한 내용을 대조합니다.

네 도구를 한 번씩 직접 호출해 입력과 출력을 읽습니다.

> `hydops.b7_agent.tools.build_tools()`에서 도구 이름과 입력 필드를 읽고, 아래 네 도구를 `.invoke()`로 호출해 JSON 결과를 보여 줘. 사건 ID는 `/api/events?all_runs=true`에서 현재 DB의 사건을 확인해 선택한다. `propose_action`에는 해당 사건의 설비·적용 조치와 실제 검색 인용을 넣고, 허용 범위 안의 값과 밖의 값을 비교한다. 승인이나 조치 실행은 하지 않는다.

| 도구 | 넣는 값 | 읽을 결과 |
|---|---|---|
| `get_recent_window` | 설비 ID, 최근 60초 | 센서 품질·유효 비율·지속 시간 등 계산된 요약 |
| `get_asset_context` | 설비 ID | 적용 SOP, 허용 조치와 값 범위 |
| `search_sop` | 설비 ID, 사건 유형, 검색 문장 | 문서 ID·버전·절·본문 |
| `propose_action` | 사건 ID, 조치, 값, 인용 | `ok`와 개별 `checks`의 통과·실패 이유 |

**판단:** 원시 센서 배열을 읽어 LLM이 고장을 추측하는 구조인가요? 범위 밖 값을 넣었을 때 어느 검사가 막았나요? 닫힌 사건이라면 값이 맞아도 사건 상태 검사가 실패할 수 있습니다.

사건이 없으면 앞 회차의 사건 생성 단계에서 합류합니다. 예전 예시의 사건 ID를 복사해 존재하는 사건처럼 사용하지 않습니다.

### 통합반 — 문서 7개와 검색 결과

`플랫폼코드/hydops/b6_sop/docs`의 SOP 파일을 엽니다. 문서 머리말에서 `status`, `applies_to`, `event_type`, `allows`를 찾아 **문서·버전 / 유효 상태 / 설비 / 사건 유형 / 허용 조치** 표를 작성합니다.

읽을 파일은 `SOP-COOL-001_v1.md`, `SOP-COOL-001_v2.md`, `SOP-COOL-002_v1.md`, `SOP-ESC-001_v1.md`, `SOP-LOAD-001_v1.md`, `SOP-SEN-001_v1.md`, `SOP-VER-001_v1.md`입니다. 한 문서의 여섯 절도 각각 한 줄로 요약합니다.

| 절 | 찾을 내용 |
|---|---|
| 1 | 적용 설비 |
| 2 | 발동 조건 |
| 3 | 확인할 관측 |
| 4 | 허용 조치 |
| 5 | 승인 주체 |
| 6 | 재점검 기준 |

> 관제 서버 `http://localhost:8800/api/sop/SOP-COOL-001`을 읽어 1판과 2판의 상태, 2절과 4절을 나란히 보여 줘. 그다음 `hydops.b6_sop.search.search_sop`으로 냉각 이상을 검색해 줘. HYD-01·HYD-02·HYD-03의 기본 질의, HYD-01의 ‘부하를 얼마로 낮추나 허용 조치’ 질의, 같은 질의에서 `include_superseded=True`인 경우를 비교한다. 각 검색은 `k=5`로 하고 필터·문서·버전·절·본문·점수를 저장해 줘.

**판단:** HYD-02 검색에 HYD-01 전용 SOP가 들어왔나요? HYD-03에 적용할 문서가 있나요? 폐기본을 포함한 조회와 현행 문서 조회는 무엇이 다른가요?

`offline`은 로컬 해시 임베딩을 사용합니다. 다른 임베딩의 예시와 순위·점수가 달라도 곧바로 오류는 아닙니다. **적용 대상·유효 버전·사건 유형**을 먼저 확인합니다. 검색에 필요한 조치 설명이 없으면 질문을 구체화해 다시 검색합니다.

## 활동 2 · 비슷한 문장과 적용 가능한 근거 구분하기

검색 점수는 적용 허가가 아닙니다. 아래 세 조건을 연결합니다.

| 확인 | 조건 | 막으려는 문제 |
|---|---|---|
| 설비 범위 | `asset_scope`에 `|설비 ID|` 포함 | 다른 설비 문서 혼입 |
| 현행 버전 | 기본 조회는 `status = active` | 폐기된 판 사용 |
| 그래프 관계 | `APPLIES_TO`와 사건 유형 일치 | 같은 설비의 다른 사건 문서 혼입 |

`|HYD-01|`처럼 경계를 붙이면 HYD-010 등 비슷한 ID와 구분할 수 있습니다. 개정 이력 비교를 위해 폐기본을 포함하는 조회는 별도 옵션으로 남깁니다.

### 에이전트에게 구현 요청하기

> 내 과제의 검색 필터를 구현해 줘. 설비 ID 경계를 지키고, 기본 검색은 active만 포함하며, `include_superseded=True`일 때는 폐기본 비교를 허용한다. 실전반은 `search_lab.py`의 `build_filter`, `confirm_with_graph`를 수정해 적용 관계·사건 유형을 검사하고 같은 절을 중복 반환하지 않게 한다. 통합반은 `evidence.py`의 `build_sop_filter`를 구현하고 `test_graph_check_removes_other_event_type`에서 필터만으로 부족한 이유를 설명한다. 제공 테스트를 바꾸지 말고 변경 전후 출력으로 확인해 줘.

실전반은 HYD-01 `k=4`, HYD-02 `k=8`로 개인 코드의 `search_sop_lab`을 수정 전후 실행합니다. 같은 인자로 플랫폼의 `search_sop`도 호출해 문서·버전·절을 대조합니다. 통합반은 활동 1의 검색 결과와 구현한 필터를 대조합니다.

**판단:** 냉각 이상 검색에서 센서 오류 문서 `SOP-SEN-001`이 제외되는 이유를 설명합니다. 검색 결과가 비었을 때 필터를 없애기 전에 설비·사건 유형·적용 관계·인덱스 상태를 확인합니다. 검색 후보를 먼저 잘 고르지 않으면 그래프 검사에서 모두 버려질 수도 있습니다.

## 활동 3 · Skill에 확인 순서와 멈출 조건 적기

개인 작업 폴더의 `skills/hydraulic-cooling-response/SKILL.md`를 엽니다. 이 파일은 유압설비 업무 에이전트에 전달할 지침입니다.

> 내 Skill을 다음 요구에 맞게 수정해 줘. 센서 품질 → 대상 설비 → SOP 검색 → 제안 검사의 순서로 확인한다. 센서 품질이 나쁘면 센서 점검 근거를 찾고, 적용 SOP나 검색 근거가 없으면 HOLD한다. 조치 값은 설비 맥락의 허용 범위와 기본값에서 가져온다. 인용은 이번 검색에 나온 doc_id·version·section으로만 구성한다. 필요한 조치 설명이 없으면 질문을 바꿔 재검색한다. 에이전트는 승인하지 않고 조치 실행 도구를 호출하지 않는다. 승인 확인과 조치 후 재측정에 관한 지침은 유지한다. 변경한 각 규칙이 어떤 잘못된 판단을 막는지 설명해 줘.

에이전트에게 실제 `hydops.b7_agent.skill_loader.build_system_prompt`로 **개인 Skill 폴더**를 읽게 합니다. 결과의 `[할당된 스킬 가이드]` 아래에 수정한 본문이 들어가는지 확인합니다. 통합반은 개인 폴더의 `skill_checker.py`도 실행합니다.

오늘의 offline 실행은 판단 순서를 코드로 수행합니다. Skill 문장을 바꿨다고 offline 코드의 행동이 자동으로 바뀌지는 않습니다. 개인 Skill의 로더 반영과 실제 제안 결과를 각각 확인합니다.

**판단:** ‘항상 특정 문서의 4절을 인용하라’와 ‘이번 검색에 나온 근거를 인용하라’는 어떻게 다른가요? Skill에 승인 지침을 적었다고 승인 검사 코드까지 생기는 것은 아닙니다. `execute_sim_action`이 오늘 에이전트의 도구 목록에 들어가 있지 않은지 확인합니다.

## 활동 4 · 근거가 없을 때 멈추는지 확인하기

### 공통 — 인용 세 값 검사

실제 문서에 있는 절도 **이번 검색에서 가져오지 않았다면** 이 제안의 검색 근거로 인정하지 않습니다.

> 인용 검증을 구현해 줘. 실전반은 `verify_citations_lab`, 통합반은 `retrieved_keys`와 `decide_after_citation_check`를 수정한다. 이번 실행의 search_sop hits에서 문서 ID·버전·절을 함께 비교하고 자료형을 맞춘다. PROPOSE 또는 SENSOR_CHECK에 인용이 없거나 검색되지 않은 인용이 있으면 HOLD한다. 아래 세 사례를 동일한 검색 기록으로 실행하고 입력·최종 결정·이유를 저장해 줘.

| 비교 입력 | 확인할 결과 |
|---|---|
| 이번 검색에 실제로 나온 문서·버전·절 | 인용 검증을 통과하는가? |
| 같은 문서지만 다른 버전 또는 검색되지 않은 절 | HOLD와 문제 인용을 보여 주는가? |
| 인용 없음 | HOLD하는가? |

인용 검증 통과만으로 조치가 허용되는 것은 아닙니다. 설비의 허용 조치·값 범위·사건 상태도 확인해야 합니다.

### 실전반 — 네 분기와 실제 사건 비교

> 개인 `search_lab.offline_proposal`을 HYD-01 정상 센서, HYD-02 정상 센서, HYD-03 정상 센서, HYD-01 센서 오류에 각각 실행해 줘. decision·action_id·value·citations·rationale와 trace를 저장한다. 각 인용이 이번 검색 결과에 있는지 대조해 줘.

| 입력 | 제공 구성에서 확인할 결정 |
|---|---|
| HYD-01 냉각 이상·센서 유효 | REDUCE_LOAD 제안 |
| HYD-02 냉각 이상·센서 유효 | FAN_BOOST 제안 |
| HYD-03 냉각 이상 | 적용 근거 없음으로 HOLD |
| HYD-01 센서 오류 | SENSOR_CHECK |

이 과제 함수는 DB 사건 없이 분기를 비교합니다. 이제 실제 사건으로 넘어갑니다.

> 현재 DB에서 냉각 이상·센서 오류·근거 없는 설비의 사건을 확인하고, `hydops.b7_agent.agent.propose_for_event(event_id, mode='offline')`로 제안을 계산해 줘. 사건이 없는 유형은 앞 회차의 해당 시나리오로 합류해야 한다고 표시한다. 현재 사건 상태, tool_trace, 제안과 검사 결과를 읽고 과제 함수의 결과와 비교한다. 승인이나 실행은 하지 않는다. 기록된 LLM 제안이 있다면 호출 순서와 인용을 비교하되, 새 유료 호출을 수행하지 않는다.

**판단:** 센서 품질을 실제 조회했나요? 닫혔거나 이미 조치한 사건은 어떤 검사에서 멈추나요? 같은 사건의 오프라인 제안과 기록된 LLM 제안이 다른 절을 인용했다면, 각각 검색 기록에 있고 판단에 충분한 내용인지 읽습니다. 비교할 LLM 기록이 없으면 비교를 완료한 것으로 적지 않습니다.

### 통합반 — 두 보류와 예측의 역할

1. HYD-03의 검색 결과가 비어 있는지 확인합니다. 관제 화면 `http://localhost:8800`에서 해당 냉각 이상 사건의 제안·사유·도구 기록을 열어 적용 SOP가 없어 보류했는지 읽습니다. 사건이 없으면 해당 시나리오의 출발 상태부터 준비합니다.
2. 앞의 인용 검증 결과를 읽습니다. ‘적용 문서 없음’과 ‘이번 검색에 없는 인용’은 서로 다른 보류 이유입니다.
3. 수업의 짧은 예측 비교 시연에서 시뮬레이터 급변 구간과 UCI 구간의 결과를 각각 기록합니다. 실행 모듈은 `hydops.b5_detect.zeroshot`이며 준비된 모델 환경에서 실행합니다. 예측 이탈 시점과 규칙 경보 시점, UCI 상태별 경보 수를 비교합니다. 실행하지 않은 결과는 실측으로 적지 않습니다.
4. 비교한 뒤 에이전트에게 `roles.py`의 역할 표를 구현하도록 요청하고 각 역할을 자신의 말로 설명합니다.

| 역할 | 판단할 질문 |
|---|---|
| FORECAST · 예측 | 이전 관측으로 다음 구간을 예상하는가? |
| DETECT · 이상감지 | 규칙·위상 기준으로 사건을 만드는가? |
| EVIDENCE · SOP | 조치의 적용 근거를 제공하는가? |
| GUIDE · Skill | 확인 순서와 중단 조건을 정하는가? |
| TOOL · 도구 | 실제 조회와 검사를 수행하는가? |

예측이 급격한 변화를 빨리 알리더라도, 처음부터 온도가 높은 구간까지 구별한다고 결론 내리지 않습니다. 추가 학습 없이 준비된 모델로 예측한 것이 zero-shot입니다. 예측 비교는 선택 시연이며 근거·지침·보류 판단은 필수입니다.

## 막혔을 때

| 증상 | 확인과 복구 |
|---|---|
| hydops를 불러오지 못함 | 개인 과제의 실행 환경과 `플랫폼코드` 연결을 확인합니다. 빈칸 오류와 환경 오류를 구분합니다. |
| DB에 연결하지 못함 | Docker 서비스 상태와 컨테이너 안/밖의 접속 주소를 확인합니다. DB를 초기화하지 않습니다. |
| 검색 인덱스가 없다고 나옴 | 현재 모드와 인덱스를 확인하고 같은 offline 모드의 SOP 인덱스를 준비합니다. |
| 검색 결과의 순위가 예시와 다름 | 모드·질의·k를 확인한 뒤 문서 적용 조건과 인용 본문을 비교합니다. |
| HYD-03 결과가 비어 있음 | 적용 SOP가 없는 교육용 설정인지 확인합니다. 근거를 지어내지 않습니다. |
| Skill 점검만 통과하고 제안은 이상함 | 실제 로더에 전달한 개인 폴더와 도구 기록을 확인합니다. 지침 점검과 실제 실행은 다릅니다. |
| 사건이 없거나 이미 닫힘 | 현재 사건 목록과 상태를 읽고 출발 상태를 확인합니다. 검사 실패를 숨기기 위해 사건 상태를 고치지 않습니다. |

## 내 결과 저장하기

개인 코드와 Skill, 검색 비교 출력, 인용 검증 결과, 자신이 확인한 사건 ID·제안·도구 기록, 테스트 출력을 저장합니다. 실전반의 제공 검사는 13개, 통합반은 18개입니다. 통과 여부와 함께 **내가 직접 읽고 판단한 결과**를 남깁니다.

마지막으로 한 사례를 골라 2분 안에 설명합니다. ‘다른 사건 유형을 거른 이유’, ‘검색되지 않은 인용을 보류한 이유’, ‘센서 오류에서 설비 조치를 멈춘 이유’ 중 선택할 수 있습니다.

실전반은 다음 회차에 이 데이터와 관계를 교육용 플랫폼에 발행합니다. 통합반은 다음 회차에 오늘의 SOP·Skill을 사용하는 로컬 에이전트와 승인 흐름을 연결합니다.
