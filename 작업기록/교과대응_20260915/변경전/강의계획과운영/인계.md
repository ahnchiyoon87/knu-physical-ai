# 새 세션 인계 — 경남대 피지컬 AI 플랫폼 기반 개편

2026-09-15. 현재 전체 작업은 **진행 중**이다. 이 문서가 새 작업본의 재개 입구다. 파일 수·이전 검사·원저자 리허설로 전체 완료를 주장하지 않는다. 다음 세션은 실제 Git/파일 상태를 확인하고 미완료부터 이어간다.

## 1. 최신 확정과 변경 승인 원칙

1. **대표님이 공유한 실라버스가 새 커리큘럼 기준이다.** 기존 엑셀 커리큘럼 내용은 팀장님이 임의 생성한 기본안으로 내용·흐름이 맞지 않는다고 지적했다. 센서신호에서 사내 문서로 갑자기 넘어가는 문제가 있었고, 대안으로 대표님 결과물을 전달했다. 대표님 자료는 단순 영감 자료가 아니다.
2. 대표님 플랫폼·UI·냉각 이상 대응 시나리오를 토대로 간다. 맹신하거나 그대로 복제하지 않는다. 하지만 **에이전트가 별도 커리큘럼을 임의로 만들어 기준으로 삼지 않는다.**
3. 사용자의 최신 승인 절차: **구성의 문제·변경·기존 리뉴얼 혼합을 발견하면 적용 전에 ‘원래 구성 → 문제 → 변경 제안 → 영향 → 어떻게 생각하는지’로 질문하고 의견을 받은 뒤 반영한다.** 보고만 하고 바로 바꾸는 것이 아니다. 순서 변경, 기술 추가/제외, 운영 방식 변경, 기존 자산 혼합은 특히 이 절차를 따른다. 이미 승인된 범위의 제작은 계속할 수 있다.
4. 아래 로컬 운영·AI 코딩·학생 친화적 설명 방향은 이미 논의하고 수락한 사항이다. 이를 매번 재승인 요청하지 않는다. 추가 변경만 구체적으로 제안한다.
5. 인계 작성 중 최신 추가 지시: **고가 모델 사용해도 됨.** 과거의 고가 모델 절대 금지를 현재 금지로 되살리지 않는다. 실제 호출은 이번에 하지 않았다. 학생 60명 운영 모델/예산은 별도이며 일괄 고가 모델 전환 지시는 아니다.

## 2. 수업의 목적과 학생 역할

- 보고 초점 정정: 개편의 핵심은 전체 난이도를 낮추는 것이 아니라 **기본 스택의 역할 이해 → 직접 사용하며 사용법 습득 → 개인 PBL에서 같은 스택을 활용한 자기 산출물 제작 역량**이다. 맨땅에서 플랫폼을 구현하는 것을 목표로 삼지 않는다. 기존 구현·기능 축적 중심에서 이 교육 목표로 초점을 되맞췄다는 뜻이며, 실제 강의 개편 완료를 뜻하지 않는다.
- 코딩을 모르는 학생이다. 설치·환경 세팅·MCP 설정·코드 작성·수정·실행은 **코딩 에이전트에 맡긴다.** 학생이 직접 코드나 JSON·명령을 작성하도록 수업을 설계하지 않는다.
- 학생은 무엇을 만들지 설명하고, 요구와 확인 기준을 이해·조정하고, 실제 출력·화면·근거가 맞는지 판단한다. ‘알아서 해줘 → 완료 보고 읽기’만으로 끝내지 않는다.
- SDD는 요구·입력·동작·확인 기준을 짧게 정하고 구현과 비교하는 방식이다. 명세 초안도 AI가 쓸 수 있고 학생이 뜻을 확인한다. 빈 프로젝트에서 시작해야만 SDD인 것은 아니다.
- 처음에는 플랫폼과 명세·요청 예시·확인 지점을 충분히 준다. 점차 도움을 줄여 개인이 자기 기능을 명세로 정하고 같은 스택으로 응용하도록 한다.
- 대표님 냉각 이상 대응을 공통 학습 사례로 유지한다. 우리 실제 제조 데이터는 후반 응용 후보다. 초반부터 두 시나리오를 병행하거나 우리 데이터로 강제 전환하는 이전 제안은 폐기한다. 구체적 혼합은 사전 제안·의견 수렴 대상이다.
- PBL은 마지막 날 갑자기 새 스택을 배우는 과제가 아니다. 익숙한 데이터·관계·근거·업무 흐름을 다른 문제에 적용하는 능력이 목적이다. 결과와 코드가 학생마다 같을 필요는 없다.
- 고급 기능 자체를 목표로 하지 않는다. 그렇다고 기존 HyDE·리랭커·크로스 인코더 등 기법을 모두 제외하는 것도 승인된 방향이 아니다. 설치 난이도보다 필요성·학생의 이해/판단 가능성·효과·비용을 보고 후보를 제안한다. 최종 포함 목록은 아직 미정이다.
- 부정행위 감시, 불필요한 제출·반성문·의무 회고를 추가하지 않는다.
- 가이드는 행동하는 자리에서 배경·용어·입력·관찰·판단·복구를 설명한다. 위로 돌아가 읽게 하지 않는다. 이론을 못 봐도 실습 흐름을 이해할 수 있도록 하되 긴 별도 이론 장을 붙이지 않는다.

## 3. 유지할 학교 조건과 산출물

- 실전반 = 4학년, 통합반 = 2·3학년. **두 반의 핵심 내용은 같다.** 원저자의 반별 빈칸/코드 난도 차이를 그대로 가져와 핵심 주제를 달리하지 않는다.
- 이론은 온라인, 실습은 오프라인 고정. 대본은 **온라인 이론만** 작성한다. 현장 실습·설치 대본과 자동 실습 영상 제작을 임의로 추가하지 않는다.
- 실전 온라인 8편/32시간, 오프라인 9일/36시간. 통합 온라인 11편/44시간, 오프라인 10일/40시간. 합동 OT 실제 2시간(엑셀 중복 행을 합산하지 않음).
- 실전 실습 14~18시: 2026-10-31, 11-07, 11-21, 11-28; 2027-01-25~29.
- 통합 실습 09~13시: 2026-11-14; 2027-01-25~29, 02-01~04.
- 세부 일정 원천은 `강의계획과운영/받은자료/학교편성_기존초안.json`과 그 파일에 적힌 원본 엑셀. JSON의 기존 챕터/제목은 새 실라버스 기준이 아니다. 날짜/시수와 제목을 구분한다.
- 최종 제작 범위: 챕터별 실라버스, 상세 Markdown 이론 덱, 온라인 대본, 친절한 실습가이드, 실습 코드, 일차별 합류 출발본/완성본, 학생 배포 ZIP, 운영안에 맞는 설치 안내.
- PPTX는 사용자가 NotebookLM으로 만들 계획이었다. 화면에 핵심 설명이 충분히 남고, 제목→결론→다음 장이 이어져야 한다. 용어는 처음 설명하고 이후 정확한 용어를 쓴다. 리허설 2일차 PPTX는 연결·설명 방식만 참고하며 디자인을 복제하지 않는다.
- 자료는 ESNS에서 Google Drive의 당일 링크로 전달할 계획. 개인 작업 보존, 결석/중단자는 이전 단계 완성 출발본으로 합류. 모든 날의 학생 출발본에 전체 최종 정답을 넣지 않는다.

## 4. 운영·비용 확정과 미결

- **학생별 로컬 실행 + 중앙 모델 중계**가 합의된 기본 방향이다. 학생 PC에 플랫폼·분석/시뮬레이터·PostgreSQL·Neo4j, 중앙에는 모델 요청/학생별 키/사용량 관리. 강사는 같은 로컬 환경으로 시연한다.
- 중앙 실습 서버에서 60명 플랫폼을 상시 운영하는 구성을 필수로 두지 않는다. 중계 운영에 부속 DB 등이 필요할 수 있어 ‘물리 서버 하나·비용 한 항목’으로 확정하지 않는다.
- 학생에게 결제 카드 등록을 강제할 수 없다. Provider 원키를 학생에게 배포하는 방식으로 돌아가지 않는다. 코딩 에이전트와 앱 LLM/임베딩의 요청 경로를 각각 검토해야 한다.
- LiteLLM 운영안은 `강의계획과운영/운영안/60명_AI이용운영안.md`. 모델·토큰·비용 가정은 실측이 아니다. 기존 110~155만원, Luna 모델 74만원 추산은 참고치이며 더해서 총액으로 만들지 않는다.
- 비용 측정·실습 완주는 **사용자가 수행**, 에이전트는 환경·일차별 기록·환산 시트를 준비한다. 최신 사용자 답변이 과거 ‘직접 완주하고 측정’ 요구를 대체했다. 고가 모델 사용은 허용됐으나 이번 인계·검토에서 새 호출은 하지 않았다. 실제 TTS/영상 제작 범위는 별도 확인 대상이다.
- 기존 리뉴얼의 `20_도구/hydops_review_20260915`에 측정용 Python/워크북 생성기가 있으나 기존 equipment-assistant를 기준으로 준비한 미완료 도구다. 새 플랫폼용 준비 완료라고 하지 않는다. 기존 리뉴얼의 `30_기록/비용측정_20260915/일차별_60명_비용환산.xlsx`도 미측정 상태다. 60명×19일로 계산하면 안 된다(반별 9일/10일, 반별 인원 미확정).
- 로컬 GCP ADC/gcloud와 Vertex VS Code 확장 존재를 확인한 적이 있으나 측정 프로젝트는 확인되지 않았다. 키 값·인증 정보는 인계/커밋에 넣지 않는다. 당시 Docker CLI는 있으나 daemon 미실행. 최소 PC 사양·사용량·중계 호환성 미검증.
- 설치 PDF는 운영 방식과 실행 흐름이 확정된 뒤 수정한다. 지금 개인 카드 전제의 기존 PDF를 그대로 학생에게 주면 안 된다.

## 7. 대표님 구현에서 확인한 사실

- 교육용 Lab Platform이다. 실제 Process GPT/Data Fabric/Ontology Studio 제품 전체를 설치한 것이 아니다. 기능·API 모양을 구현했다. 실제 제품 연동으로 확대하지 않는다.
- Data Fabric: PostgreSQL 등록·메타데이터·읽기 전용 질의. 의미 미상 열을 LLM이 분석해 확정하는 기능은 없다. 해당 기능 추가는 미승인 후보다.
- Studio: graph/virtual 바인딩, 정의 JSON/API, 검증·발행·질문 조회. 범용 자연어 생성·드래그 편집기가 있다고 하지 않는다.
- SOP 검색: Neo4j 벡터 검색 + 설비/active 필터 + 그래프 적용 대상/사건 확인. HyDE·리랭커·크로스 인코더는 확인한 코드에 없음.
- 모델 기본값은 원천 `gpt-4.1-mini`, 임베딩 `text-embedding-3-small`; 강사 키/강사 서버 안내가 있다. 학생 코딩 에이전트·LiteLLM·학생별 키 발급 운영안은 확인되지 않음.
- MCP 서버는 강사가 실행, 학생이 제공 curl/JSON으로 등록·도구 조회. 학생 코딩 에이전트의 MCP 설정과 플랫폼 업무 에이전트의 MCP 연결을 혼동하지 않는다.
- 학생 자료는 틀린 코드/매핑·빈칸 수정과 검사 중심. 학생 SDD/바이브 코딩 절차가 명시된 자료는 찾지 못했지만 실제 강사가 AI 사용을 안 했다고 단정할 수는 없다.
- UCI는 실제 센서 데이터, 냉각 반응과 제품 검사 일부는 합성. 원본 replay 시간은 실제 수집 시각이 아님. 같은 CSV 재조회/경보 감소는 조치 후 설비 회복이 아님.
