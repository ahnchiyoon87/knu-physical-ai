P44: 3. 어떤 근거로 누가 승인했으며 조치 후 새 관측은 회복했는가?
P45: 이 세 가지 Golden Question을 먼저 정하고 필요한 클래스·관계·질의를 만든다. 질문마다 새 클래스를 만드는 방식은 피한다. 플랫폼에서는 수치 데이터는 원천 DB와 가상 연결하고, 문서 지식은 그래프에 적재하는 방식으로 역할을 나눈다. Ontology Studio 설계 원칙
P46: Ontologic의 개념을 적용할 때 Resource는 유압설비·냉각기, Measure는 온도·유량, Driver는 부하·냉각 성능, Process는 운전·점검, KPI는 이상 지속 시간·불필요 조치 건수로 대응한다. Asset은 Resource의 수업용 구체 클래스다. ‘냉각 성능이 온도에 영향을 준다’는 관계에는 문서 근거 또는 시뮬레이터 가정을 표시한다. 관계를 그렸다는 이유로 실측 인과관계가 확인된 것으로 평가하지 않는다.

P52: Zero shot의 적용 위치
P53: 사전학습 LLM과 임베딩 모델은 추가 학습 없이 사용한다. SOP 검색은 학습이 아니라 실행 시 근거를 제공하는 RAG다. 규칙 기반 감지도 학습이 필요 없지만 이를 zero-shot 모델이라고 부르지는 않는다. 시계열 모델은 Chronos 계열 등 기존 체크포인트로 미래 구간을 예측하는 선택 실습으로 둔다. 예측 오차·구간 이탈을 이상 점수로 바꾸는 기준과 지속 조건은 별도 설계해야 한다. 설치와 추론은 강사가 미리 준비한다. Chronos 공식 저장소
P54: 필수 과정에서 LSTM·Transformer 재학습, RUL 회귀, AutoML 인과 분석, Kubernetes 구축, 복수 에이전트 프레임워크 비교를 제외한다. Ontologic의 What-if와 Robo Architect는 시간이 남는 실전반에서 제공 시나리오를 관찰하는 확장으로 둔다.

P178: Skill과 조치 프로세스 계약
P179: Skill은 업무 지침이고 도구는 실행 기능이다
P180: Skill에는 ‘센서 품질 확인 → 대상 설비 확인 → SOP 검색 → 제안 → 승인 확인 → 실행 → 재측정’의 순서와 중단 규칙을 작성한다. SOP는 실제 근거를 제공하고, 도구는 DB 조회나 시뮬레이터 조치를 수행한다. SKILL.md에 승인 규칙을 썼다는 것만으로 승인 검사가 구현되지는 않는다.

P183: 조치 도구는 허용 조치 목록, 값 범위, 승인 상태, 사건의 유효성, 중복 키를 코드에서 확인한다. LLM이 만든 approved=true를 승인으로 인정하지 않는다. 교육 기본 조치는 부하 감소 한 가지로 제한하고 승인값과 다른 값의 실행을 거부한다.
P184: 예시 설정은 시뮬레이터 온도 60°C 초과가 유효 관측 10초 동안 지속되면 경보, 승인 후 부하 1.0에서 0.8로 한 번 감소, 30초 후 새 관측에서 55°C 이하가 10초 유지되면 회복으로 둔다. 이는 교육용 가정값이며 UCI의 설비 운전 기준이 아니다. 학생은 설정값을 바꿔 오탐과 미개선 분기를 비교한다.
P185: 상태 흐름
P186: 감지 → 근거 확인 → 승인 대기 → 실행 → 재측정 → 종결. 근거 없음은 보류, 승인 거부는 미실행 종료, 도구 실패나 미개선은 이관, 데이터 부족은 재측정 보류로 분기한다. 명령 성공과 회복 성공은 별도 필드로 저장한다. 재시작 후 동일 사건을 다시 읽어도 이미 승인·실행한 조치를 반복하지 않는다.
P187: Process GPT에서는 접수 폼과 조치 승인 태스크를 분리한다. event_id, asset_id, run_id, 제안값, 근거 참조를 실제 프로세스 입력 폼에 매핑한다. 프로세스의 완료 상태는 업무 진행을 나타내며 설비 회복을 대체하지 않는다.
P188: 플랫폼 개발 지원용 Skill과 업무 에이전트가 실행 시 읽는 Skill은 별개다. 수업에서는 업무 에이전트에 할당한 짧은 SKILL.md를 사용하고, 긴 SOP 본문은 검색 도구로 불러온다.
P190: 플랫폼 연결 준비와 평가
