# 1일차 관측에서 원본까지

온도 그래프의 숫자 하나를 골랐을 때, 어느 설비의 어떤 센서가 측정한 값인지 원본까지 찾아갈 수 있게 만듭니다. 제공된 프로그램과 플랫폼을 사용하고, 코드를 고치는 일은 코딩 에이전트에 맡깁니다. 여러분은 무엇을 요구했고 결과가 그 요구에 맞는지 확인합니다.

오늘 사용하는 센서는 온도 TS1, 압력 PS1, 유량 FS1입니다. 모두 같은 60초 운전 사이클을 관측하지만 측정 횟수와 단위가 다릅니다. 먼저 이것을 같은 시간 구간으로 정리하고, 출처를 잃지 않았는지 확인하겠습니다.

## 시작할 때

강사가 안내한 개인 작업 폴더를 코딩 에이전트에서 엽니다. 첫날 원문 시작 파일은 `실습자료/1일차/원문시작본`에 있습니다. 실전반은 `practical/mapping.py`, 통합반은 `integrated/S01_sensor_flow.ipynb`를 사용합니다. 두 반 모두 센서·단위·출처와 같은 시간 구간을 배우며, 실전반은 오늘 DB 저장·조회까지 이어갑니다. 통합반은 오늘 재생·저장본을 만들고 다음 회차에 DB로 연결합니다.

에이전트에게 먼저 요청합니다.

> 내 반의 첫날 시작 파일을 별도 student-work 폴더에 복사해 줘. 기존 개인 작업이 있으면 덮어쓰지 말고 먼저 위치를 알려 줘. 이 프로젝트의 플랫폼코드와 data/raw, data/reduced 위치를 확인하고, 복사본이 그 제공 코드를 읽도록 환경과 경로를 맞춰 줘. 원본 시작 파일과 원본 데이터는 바꾸지 마. 아직 실습의 빈칸이나 잘못된 동작을 고치지는 마. 실행에 필요한 것이 준비됐는지, 무엇이 부족한지 알려 줘.

실행 환경은 에이전트가 준비합니다. 설치 명령이나 Python 문법을 외우는 활동이 아닙니다. 에이전트가 준비됐다고 하면 작업 복사본과 데이터 위치를 직접 확인하세요. 통합반 노트북의 커널은 이 수업에 필요한 패키지가 설치된 Python이어야 합니다. 실전반 DB는 자신의 로컬 DB를 사용합니다.

## 1. 완성 화면에서 오늘의 경로 찾기

강사가 연 교육용 관제 화면에서 설비 이름과 온도 그래프를 찾습니다. 전체 수업에서는 이 값으로 이상을 찾고, 해당 설비의 절차를 확인하고, 사람의 승인을 받아 조치한 뒤 새 관측을 확인하게 됩니다.

개인 로컬 환경이 준비됐다면 브라우저에서 `http://localhost:8800/`을 엽니다. `localhost`는 지금 사용하는 자신의 컴퓨터를 뜻합니다. 에이전트가 다른 포트로 준비했다면 확인된 접속 주소를 사용하세요.

![실제 관제 화면: 왼쪽 설비 목록, 가운데 온도 그래프, 상단 데이터 출처](그림/관제_설비와출처.png)

왼쪽의 **HYD-01**과 가운데 그래프 제목의 설비가 같은지 확인합니다. 상단의 **교육용 합성 데이터**는 프로그램이 만든 관측이라는 뜻입니다. `run_id`는 현재 실행 묶음을 구분합니다. 위 그림의 실행 이름·시각·온도는 캡처 당시 값이므로 여러분의 화면과 같을 필요는 없습니다.

지금은 화면을 읽는 단계입니다. 왼쪽 아래의 ‘강사용 시나리오 주입’과 ‘초기화’ 버튼은 누르지 않습니다.

오늘 담당할 경로는 **데이터 → 품질 확인 → 저장된 관측**입니다. 화면에 보이는 온도가 시뮬레이터의 값이라면 교육용 프로그램이 만든 값입니다. 오늘 파일에서 읽을 UCI 센서값과 같은 출처라고 생각하지 마세요.

에이전트에게 요청합니다.

> 제공 코드와 화면의 데이터 출처를 확인해 줘. 지금 화면의 값이 UCI 파일 재생인지, 시뮬레이터에서 생성한 값인지 근거 필드와 함께 설명해 줘. 화면을 못 열면 열었다고 하지 마. 오늘 사용할 원본 파일과 시뮬레이터 값이 어디서 나뉘는지도 짚어 줘.

여러분이 확인할 것은 두 가지입니다. 화면이 가리키는 설비가 무엇인지, 그리고 그 값의 출처가 무엇인지입니다. 화면을 읽을 수 있어도 출처를 모르면 아직 원본을 확인한 것이 아닙니다.

화면 접속에 실패하면 에이전트에게 로컬 서비스와 주소를 확인하게 하세요. 파일 활동을 진행할 수는 있지만 화면 관찰까지 완료했다고 표시하지 않습니다.

## 2. 센서 파일의 한 줄 읽기

TS1.txt, PS1.txt, FS1.txt의 한 줄은 각각 같은 길이인 60초의 운전 사이클입니다. 한 줄에 들어 있는 숫자 개수는 다릅니다.

| 센서 | 측정하는 것 | 단위 | 1초 측정 횟수 | 60초 한 줄의 값 개수 |
|---|---|---|---:|---:|
| TS1 | 온도 | °C | 1 | 60 |
| PS1 | 압력 | bar | 100 | 6,000 |
| FS1 | 유량 | L/min | 10 | 600 |

1초에 몇 번 측정하는지를 **샘플링 주파수**라고 하며 단위는 Hz입니다. PS1의 100Hz는 압력을 1초에100번 측정했다는 뜻입니다. 숫자가 많다고 측정 시간이 더 긴 것은 아닙니다.

> 세 원본 파일에서 사이클100을 읽어 줘. 사이클 번호는0부터 세므로 파일의101번째 줄이야. 각 파일의 값 개수와 단위를 확인하고, 60초와 측정 횟수가 맞는지 보여 줘. 원본 파일 전체를 채팅에 출력하지 말고 모양을 이해할 부분만 보여 줘.

TS1의 두 번째 값과 PS1의 두 번째 값은 같은 경과 시점을 뜻하지 않습니다. 두 센서의 측정 간격이 다르기 때문입니다. 같은 열 번호끼리 붙이면 같은 시간의 온도·압력이라고 할 수 없습니다.

파일을 찾지 못하면 파일 위치부터 고칩니다. 실제 값 대신 임의 숫자를 만들어 계속하지 않습니다.

## 3. 같은 1초 구간으로 바꾸기

PS1은 첫1초 안에100개 값이 있습니다. 화면에서 이 구간을 보여 주려면 어떤 요약을 남길지 정해야 합니다. 평균은 구간을 요약하지만 그 안의 변화 폭까지 보여 주지는 않습니다. 따라서 압력에는 최솟값·최댓값과 몇 개를 사용했는지도 남깁니다.

이번에 사용할 관측 레코드는 다음 정보를 담습니다. 레코드는 프로그램이 함께 다루는 한 묶음의 정보입니다.

| 정보 | 의미 |
|---|---|
| `asset_id`, `sensor_id` | 어떤 설비의 어떤 센서인가 |
| `raw_value`, `unit` | 어떤 값이고 단위는 무엇인가. 여기서 raw_value는 제공 관측 형식의1초 값 |
| `origin_cycle_id`, `elapsed_s` | 원본의 어느 사이클, 그 안의 어느 초인가 |
| `ts` | 실습에서 정한 재생 시각. 실제 수집 날짜가 아님 |
| `agg` | 고주파 센서의1초 최솟값·최댓값·샘플 수·원래 Hz |
| `is_synthetic` | 합성으로 생성한 관측인지 구분 |

**실전반 요청**

> 작업 복사본 mapping.py가 만들 관측의 요구를 정리해 줘. 센서별60초를1초 구간60개로 바꾸고, 각 구간의 평균·최솟값·최댓값·측정 개수를 정확히 계산해야 해. 단위와 원본 사이클, 경과 초를 남겨야 하고, UCI 재생을 합성으로 표시하면 안 돼. 현재 함수가 이 요구와 다른 부분을 설명하고, 내가 확인할 수 있는 비교 방법을 제시해 줘. 아직 DB 적재는 하지 마.

요구를 읽고 뜻을 확인한 다음 구현을 요청합니다.

> 확인한 요구대로 작업 복사본을 수정하고 사이클100을 변환해 줘. 입력과 결과를 구분해 저장하고, 결과를 다시 읽어서 확인해 줘. 원본과 제공 플랫폼 코드는 보존해 줘.

**통합반 요청**

> 작업 노트북에서 센서 매핑 표를 설명해 줘. 각 센서의 설비ID·센서ID·단위·Hz·원본 파일이 무엇을 뜻하는지 원본과 제공 코드로 확인해 줘. 내가 내용을 확인하면 노트북의 매핑 빈칸을 채우고 관측 레코드를 생성해 줘. 노트북 셀과 변수 이름은 유지해 줘.

실전반은 제공 함수의 동작을, 통합반은 제공 노트북의 매핑을 에이전트가 고칩니다. 학생이 직접 코드를 채우는 대신 원하는 결과를 확인하고 수정 내용을 이해합니다.

## 4. 결과에서 원본으로 돌아가기

완료 메시지만 읽지 말고 결과 표나 노트북 출력을 엽니다. 한 사이클을 변환한 결과는 센서3개×60초로180개 관측입니다. 행 수와 별도로 단위·출처·시간도 확인해야 합니다.

실전반은 다음 비교를 요청합니다.

> 사이클100의 PS1 첫1초를 원본에서 다시 읽고, 저장된 변환 결과의 같은 구간과 나란히 보여 줘. 첫 측정값과 평균을 구분하고, 사용한 값 개수·최솟값·최댓값도 비교해 줘. 결과가 다르면 어떤 값이 다르고 어디서 생긴 차이인지 설명해 줘.

통합반은 다음 확인을 요청합니다.

> 사이클100의 TS1, elapsed_s=30인 관측 하나를 찾아 줘. 설비·센서·값·단위·원본 파일·사이클·경과 초를 한 문장으로 설명해 줘. 원본 파일의 해당 위치와 대조한 다음, 내가 확인한 내용을 노트북의 ONE_VALUE에 반영해 줘.

여러분은 에이전트가 **같은 센서·같은 사이클·같은 구간**을 비교하는지 봅니다. 숫자만 같고 비교한 구간이 다르면 출처 추적이 아닙니다. 계산을 맡기더라도 어떤 입력과 어떤 결과를 대조했는지는 판단할 수 있어야 합니다.

## 5. 여러 사이클을 이어서 사용하기

이번에는 사이클100·101·102를 이어 붙입니다. 세 사이클 모두60초이므로 재생 길이는180초입니다. 센서3개를1초 단위로 보관하면 총540개 관측이 됩니다. 원본 파일의 길이나 측정값을 바꾸는 것이 아니라, 실습에서 재생할 구간을 선택하는 것입니다.

### 통합반은 재생하고 저장합니다

> 노트북의 제공 재생 기능으로 사이클100·101·102를 순서대로 실행해 줘. 세 센서 그래프의 단위와 재생 경과 초가 보이는지 확인하고, 노트북과 saved의 관측·센서표·마지막 그래프를 저장해 줘. 재생 시각은 실습용임을 표시하고, 파일을 다시 열어 결과가 남았는지 확인해 줘.

그래프에서60초와120초는 원본 사이클이 바뀌는 경계입니다. 시간이 넘어가도 어떤 사이클에서 왔는지 찾을 수 있어야 합니다. 재생이 빨리 끝났다고 원래 측정도 그만큼 짧았다고 해석하지 마세요.

저장할 이름은 제공 노트북의 `S01_replay_observations.csv`, `S01_sensor_table.csv`, `S01_replay_last_frame.png`입니다. 같은 개인 폴더에서 파일과 노트북을 다시 열어 확인합니다.

![세 센서의 180초 재생을 실행해 저장한 그래프](그림/센서_180초_재생.png)

위쪽부터 온도·압력·유량입니다. 세로 점선은 사이클이 바뀌는 60초·120초를 표시합니다. 압력 그래프의 급격한 변화만 보고 센서 오류라고 단정하지 마세요. 원본 운전 사이클에도 이런 변화가 있으며, 품질 기준은 다음 시간에 확인합니다.

다음 시간에는 이 노트북과 저장본을 다시 열어 환경이 복구됐는지 확인합니다. 그다음 같은 관측 형식으로 사이클1500의 오류 주입본을 읽어 품질 검사와 DB 저장을 연습합니다. 오늘의 CSV를 그대로 다음 과제의 오류 입력으로 사용하는 것은 아닙니다.

### 실전반은 PostgreSQL에 저장하고 조회합니다

PostgreSQL은 표 형태의 데이터를 저장하고 조건으로 찾아오는 DB입니다. 오늘은 직접 테이블을 설계하지 않습니다. 제공된 품질 검사기와 저장 함수를 사용하고, 내가 저장한 관측을 정확히 찾을 수 있는지 확인합니다.

`run_id`는 이번 실행 묶음의 이름입니다. 같은 HYD-01이라도 UCI 파일 재생과 시뮬레이터 실행이 함께 있을 수 있으므로 설비 이름만으로는 부족합니다.

> 사이클100·101·102를 제공 품질 검사기를 거쳐 내 로컬 PostgreSQL에 적재하도록 load_cycles를 수정해 줘. 새 LAB- 접두사 run_id를 만들고, source는 uci_replay로 기록해 줘. 각 사이클의 재생 시작을60초씩 이어 붙여 줘. 기존 run과 데이터는 보존하고, 생성한 run_id와 실제 적재 결과를 알려 줘.

이어서 조회를 요청합니다.

> 내가 방금 만든 run_id와 HYD-01을 모두 조건으로 써서 최근60초를 조회해 줘. 센서별 개수·단위·원본 사이클·경과 초·합성 여부를 보여 줘. window_with_origin이 실제로 run_id를 전달하는지 확인하고, 제공 테스트와 별도 조회 결과를 구분해서 보여 줘.

마지막 사이클까지 적재했다면 최근60초는 사이클102의0~59초에 해당합니다. 각 센서에60개 관측이 있어야 합니다. 다른 run_id, 빈 원본 사이클 또는 합성 표시가 나오면 에이전트에 조회 조건과 원천을 다시 확인하게 합니다.

재생 시작+90초를 끝으로 하는60초도 조회합니다. 이 구간에는 사이클100의31~59초와 사이클101의0~30초가 들어갑니다. ‘최근60초’와 ‘사이클 하나’가 언제나 같은 뜻은 아니라는 것을 확인합니다.

## 6. 품질 OK가 뜻하는 것

제공 품질 검사기는 결측·급등·고착·범위 이탈 등의 규칙을 확인합니다. 사이클100~102의540개 관측은 이 규칙에서 모두 OK로 나올 수 있습니다. 이는 **제공 센서 품질 규칙을 통과했다**는 뜻입니다. 설비가 정상이라고 판정한 결과는 아닙니다. 실제 profile에서 이 세 사이클의 냉각기 상태 라벨은3이며, 안정 상태에 아직 도달하지 않았을 가능성을 나타내는 플래그가 붙어 있습니다.

관측값을 믿고 읽을 수 있는지와 그 값이 나타내는 설비 상태가 정상인지는 서로 다른 질문입니다. 다음 시간에는 이 차이를 품질 검사와 이상 판단의 순서로 연결합니다.

## 7. 저장하고 다시 열기

결과를 저장한 뒤 다시 열어 봅니다. 단위와 원본 위치를 다시 찾을 수 있는지 확인하세요.

- 통합반: 작업 노트북과 saved 파일들을 함께 보관합니다. 다음 회차에 새 노트북으로 다시 시작하지 않고 이 상태를 복구합니다.
- 실전반: 작업 코드, 입력 경로, run_id와 조회 결과를 함께 보관합니다. 제공 테스트가 만든 임시 run은 테스트가 정리할 수 있지만 자신의 실습 run을 종료할 때 자동 삭제하지 않습니다.
- 두 반 공통: 원본 시작 파일은 보존합니다. 수정 중 막히면 현재 작업을 남긴 채 새 복사본으로 합류할 수 있습니다.

| 관찰한 문제 | 에이전트에게 확인시킬 것 |
|---|---|
| 파일을 못 찾음 | 현재 작업 폴더와 플랫폼코드/data/raw 경로 |
| 노트북에서 제공 코드를 못 찾음 | 커널 환경과 플랫폼코드의 Python import 경로 |
| 단위나 개수가 예상과 다름 | 센서 매핑,60초 범위,1초 집계에 실제 사용한 샘플 |
| DB 연결 실패 | 개인 Compose의 DB 상태와 호스트/컨테이너 접속 주소 |
| 다른 실행의 값이 나옴 | asset_id와 run_id가 조회에 함께 전달됐는지 |
| 원본 사이클이 사라짐 | 매핑·저장·조회 중 어느 단계에서 필드가 빠졌는지 |

환경을 복구할 때 다른 작업을 종료하거나 DB 전체를 비우지 않습니다. 해결되지 않은 단계는 실제로 확인하지 못한 것으로 남기고 강사에게 현재 파일과 오류를 보여 주세요.
